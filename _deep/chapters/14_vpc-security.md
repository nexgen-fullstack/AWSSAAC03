> 🎬 **Історія Хмаринки.** Минув тиждень після переїзду. Тарас, налагоджуючи сервер, «тимчасово» відкрив порт SSH для всього інтернету — і забув. Через годину в журналах з'явилися тисячі спроб підібрати пароль з усього світу. Ще одна знахідка: база даних приймала з'єднання від будь-якого сервера у VPC, включно з тестовими. Правило, яке ми впровадимо: **кожен компонент приймає трафік лише від того, кому це справді потрібно**, а адміністратори заходять на сервери взагалі без відкритих портів.

> 🖼️ **Образ.** **Security Group** — особистий охоронець біля дверей кожної квартири, що має список гостей і **пам'ятає**, кого випустив: вийшов ти в магазин — назад пропустить без питань (**stateful**). **Network ACL** — пропускний пункт на вході в будинок: перевіряє **кожного** і на вхід, і на вихід за нумерованим списком правил, нікого не пам'ятає (**stateless**), зате вміє **заборонити** конкретним людям.

## Security Groups: файрвол біля кожного ресурсу {#sg}

**Security Group (SG)** — віртуальний файрвол на рівні **мережевого інтерфейсу** (ENI): серверів EC2, балансувальників, баз RDS, функцій Lambda у VPC, VPC endpoints тощо.

Ключові властивості:

- **Лише дозволи (Allow).** Заборонних правил немає: усе, що не дозволено, — заборонено.
- **Stateful.** Якщо вхідне з'єднання дозволене, відповідь на нього автоматично виходить — окреме вихідне правило не потрібне. І навпаки: відповіді на вихідні запити сервера пропускаються всередину.
- **Окремі вхідні (inbound) і вихідні (outbound) правила.** Нова SG за замовчуванням: вхідних правил **немає** (усе заблоковано), вихідні — **все дозволено**.
- **Джерело правила** — діапазон IP (CIDR), **інша Security Group** або список префіксів (prefix list).
- Правила оцінюються **всі разом** (порядку немає); до ресурсу можна прикріпити кілька SG — дозволи додаються.
- Зміни діють **миттєво**.

### Посилання на іншу Security Group — суперсила

Замість «дозволити порт 3306 з діапазону 10.0.10.0/24» пишемо «дозволити порт 3306 **від Security Group серверів застосунку**». Тепер доступ до бази має **будь-який** сервер з цією SG — хоч два, хоч двісті, хоч з новими адресами після Auto Scaling — і **тільки** вони.

## Network ACL: файрвол на рівні підмережі {#nacl}

**Network ACL (NACL)** — файрвол на межі **підмережі**. Діє на весь трафік, що входить у підмережу чи виходить з неї.

- **Allow і Deny.** Можна явно заборонити, наприклад, конкретну IP-адресу зловмисника.
- **Stateless.** Кожен пакет перевіряється окремо, пам'яті про з'єднання немає. Якщо дозволив вхідний запит — треба окремо дозволити **вихідну відповідь**.
- **Нумеровані правила** оцінюються від меншого номера до більшого; спрацьовує **перше**, що збіглося. Решта ігнорується. Останнє правило `*` — заборонити все.
- **Default NACL** (створюється з VPC) — дозволяє весь трафік в обидва боки. **Власна (custom) NACL** — за замовчуванням **забороняє все**, поки не додаси правила.
- Кожна підмережа має рівно одну NACL; одна NACL може обслуговувати кілька підмереж.

| | **Security Group** | **Network ACL** |
|---|---|---|
| Рівень | Мережевий інтерфейс (ресурс) | Підмережа |
| Правила | Лише Allow | Allow і **Deny** |
| Стан | **Stateful** — відповіді автоматично | **Stateless** — відповіді дозволяти окремо |
| Порядок | Усі правила разом | За номером, перше збіжне |
| Джерело | CIDR, **інша SG**, prefix list | Лише CIDR |
| За замовчуванням | Вхід заборонено, вихід дозволено | Default — усе дозволено; custom — усе заборонено |
| Типове застосування | Основний захист кожного ресурсу | Додатковий шар, **блокування конкретних IP** |

### Ephemeral ports: пастка stateless-правил {#ephemeral}

Нагадування з [розділу 3](#ch/it-networks/ports): клієнт відкриває з'єднання зі **свого тимчасового порту** (ephemeral port, приблизно 1024–65535) на порт сервера (наприклад, 443). Відповідь сервера йде **на цей тимчасовий порт**.

<span class="ar">→</span>
<div class="st"><b>Вхід у підмережу</b>NACL inbound: дозволити TCP <b>443</b> з 0.0.0.0/0 ✅</div>
<span class="ar">→</span>
<div class="st"><b>🖥️ Сервер</b>Відповідає на 51734</div>
<span class="ar">→</span>
<div class="st"><b>Вихід з підмережі</b>NACL outbound: дозволити TCP <b>1024–65535</b> до 0.0.0.0/0 — інакше відповідь загубиться ❌</div>
</div>
<figcaption>Security Group цього правила не потребує (stateful). У NACL без діапазону ephemeral ports сайт «зависне»: запит проходить, відповідь — ні.</figcaption>
</figure>

Те саме у зворотний бік: якщо сервер у підмережі сам звертається в інтернет (оновлення з порту 443), то **вхідне** правило NACL має дозволяти відповіді на ephemeral ports.

## Як адміністраторам заходити на сервери {#admin-access}

Відкритий SSH (22) чи RDP (3389) в інтернет — одна з найчастіших причин зламів. Варіанти від старого до найкращого:

1. **Публічна IP + відкритий порт 22** — ❌ ніколи для prod.
2. **Bastion host** (jump box) — окремий захищений сервер у публічній підмережі; SSH на нього дозволено **лише з офісної IP**, а з нього — на приватні сервери. Ще один сервер, який треба латати й захищати.
3. **EC2 Instance Connect** — тимчасовий SSH-ключ «проштовхується» через API на 60 секунд. **EC2 Instance Connect Endpoint** дозволяє так підключатися навіть до серверів **без публічної адреси**, без бастіону.
4. **AWS Systems Manager Session Manager** — ✅ рекомендовано: командний рядок у браузері чи CLI **без відкритих вхідних портів** взагалі, без SSH-ключів, без бастіону. Доступ керується **IAM**, кожна сесія може **записуватися** в S3 чи CloudWatch Logs. На сервері — агент SSM і роль з потрібними правами; для повністю приватних підмереж — interface endpoints для SSM.

:::mnemo 🧠 На іспиті
«Адміністративний доступ до серверів **без відкриття порту 22**, з **аудитом сесій**, з найменшими операційними зусиллями» → **SSM Session Manager**. «Доступ через SSH лише з офісу» → Security Group з CIDR офісу (або бастіон).
:::

## Спостереження за мережею {#visibility}

- **VPC Flow Logs** — журнал **метаданих** IP-трафіку: хто (IP, порт) до кого, протокол, скільки байтів, і головне — **ACCEPT чи REJECT**. Вмикається для VPC, підмережі чи інтерфейсу; пише в **CloudWatch Logs**, **S3** або **Data Firehose**; аналізується CloudWatch Logs Insights чи Athena. Вміст пакетів **не** записує.
- **Traffic Mirroring** — копія **самих пакетів** з інтерфейсу на систему аналізу (IDS, форензика). Коли потрібен вміст.
- **Reachability Analyzer** — перевіряє шлях між двома ресурсами («чому сервер A не бачить базу B?») і показує, **який компонент блокує**: SG, NACL, маршрут.
- **Network Access Analyzer** — шукає **небажані** шляхи доступу («чи є шлях з інтернету до підмереж з базами?»).

:::example 🧩 Діагностика з Flow Logs
Сайт не бачить базу. У Flow Logs інтерфейсу бази видно запити з 10.0.10.25 на порт 3306 зі статусом **REJECT**. Отже, трафік доходить, але його блокує SG бази або NACL підмережі даних. Якщо вхідний запис ACCEPT, а вихідна відповідь REJECT — це майже напевно **NACL** без ephemeral ports (бо SG stateful і відповіді не блокує).
:::

## Глибокий захист: шари охорони Хмаринки {#defense}

Жоден окремий механізм не ідеальний, тому захист будують **шарами** (defense in depth):

:::lab 🧪 Спробуй у справжньому AWS: ланцюжок Security Groups
**Вартість:** безкоштовно. **Час:** 15 хвилин. Потрібна VPC з попередньої практики (або default VPC).
1. **VPC → Security groups → Create security group** `sg-alb`: вхідне правило **HTTPS (443)**, джерело `0.0.0.0/0`.
2. Створи `sg-app`: вхідне правило **Custom TCP 8080**, джерело — почни вводити `sg-` і обери **sg-alb**.
3. Створи `sg-db`: вхідне правило **MYSQL/Aurora (3306)**, джерело — **sg-app**.
4. Відкрий `sg-db` → вкладка **Outbound rules**: за замовчуванням дозволено все. Подумай, чи потрібен базі вихід «куди завгодно» (найменші права кажуть — ні).
5. **Network ACLs → Create network ACL** у своїй VPC → відкрий її **Inbound rules**: одне правило `*` **DENY**. Це і є «власна NACL забороняє все за замовчуванням». Не прив'язуй її до підмереж!
6. Відкрий **default NACL** твоєї VPC: правило 100 **ALLOW** усе + `*` DENY. Порівняй.
**Прибери за собою:** видали створену NACL і три Security Groups (спершу `sg-db`, потім `sg-app`, потім `sg-alb` — через посилання між ними).
:::

#### 💡 Запам'ятай

- **Security Group:** рівень ресурсу (ENI), **лише Allow**, **stateful**, джерелом може бути **інша SG**; нова SG — вхід закритий, вихід відкритий.
- **NACL:** рівень підмережі, **Allow і Deny**, **stateless**, нумеровані правила (перше збіжне); default — усе дозволено, custom — усе заборонено.
- NACL мусить дозволяти **ephemeral ports (1024–65535)** для відповідей.
- Заблокувати конкретну IP-адресу → **NACL Deny** (у SG заборон немає) або WAF для HTTP.
- Доступ до серверів без відкритих портів, з аудитом → **SSM Session Manager**; для приватних серверів без бастіону — також **EC2 Instance Connect Endpoint**.
- **Flow Logs** — метадані трафіку (ACCEPT/REJECT), не вміст; вміст — **Traffic Mirroring**.
- **Reachability Analyzer** — «чому не з'єднується»; **Network Access Analyzer** — «чи немає зайвих шляхів».

#### 🎯 Як питають на іспиті

- База має приймати трафік лише від серверів застосунку, кількість яких змінюється → **SG бази з джерелом = SG серверів застосунку**
- Заблокувати конкретну IP-адресу, що атакує підмережу → **NACL з правилом Deny (з меншим номером, ніж Allow)**
- Після налаштування власної NACL запити доходять до сервера, але відповіді клієнти не отримують → **дозволити вихідний трафік на ephemeral ports 1024–65535**
- Адміністративний доступ до приватних серверів без відкриття порту 22 і з журналом сесій → **AWS Systems Manager Session Manager**
- Проаналізувати відхилені з'єднання і хто стукає до сервера → **VPC Flow Logs**
- Потрібна копія пакетів для системи виявлення вторгнень → **Traffic Mirroring**
- З'ясувати, який компонент блокує з'єднання між двома ресурсами → **Reachability Analyzer**
- SSH на бастіон лише з офісу → **Security Group бастіону з CIDR офісної IP**

#### ⚠️ Пастки

- У Security Group **немає Deny** — варіант «додати Deny-правило в SG» завжди неправильний.
- NACL **stateless**: без ephemeral ports ламаються відповіді.
- NACL оцінюється за номерами: Deny з номером 200 не спрацює, якщо Allow з номером 100 уже пропустив трафік.
- Flow Logs не показують вміст пакетів і не блокують трафік.
- Власна (custom) NACL за замовчуванням **забороняє все** — нова підмережа з нею «мертва», поки не додаси правила.

## ✅ Перевір себе

:::quiz
? Три вебсервери за балансувальником масштабуються Auto Scaling, їхні IP-адреси постійно змінюються. Як дозволити доступ до бази RDS лише цим серверам?
- Додати в SG бази IP-адреси серверів і оновлювати їх скриптом
+ У SG бази дозволити порт бази з джерелом — Security Group вебсерверів
- Дозволити порт бази з усієї VPC
- Налаштувати NACL з дозволом на IP вебсерверів
= Посилання на Security Group автоматично охоплює всі ресурси з нею, незалежно від IP. Це і найменші права, і нуль ручної роботи при масштабуванні.

? Служба безпеки виявила атаку з IP 198.51.100.7 на сервери в підмережі. Як заблокувати саме цю адресу?
- Додати правило Deny в Security Group серверів
+ Додати в Network ACL підмережі правило Deny для 198.51.100.7/32 з номером меншим за правила Allow
- Видалити Internet Gateway
- Увімкнути VPC Flow Logs
= Security Groups не мають Deny-правил. NACL має, але правила оцінюються за номерами: Deny має стояти раніше (менший номер), ніж правило, що дозволяє трафік.

? Після прив'язки власної NACL до підмережі вебсервера сайт перестав відповідати. Вхідне правило дозволяє TCP 443 з 0.0.0.0/0, вихідне — TCP 443 до 0.0.0.0/0. Що виправити?
- Додати вхідне правило на порт 80
+ Дозволити у вихідних правилах TCP 1024–65535 до 0.0.0.0/0
- Прикріпити до сервера ще одну Security Group
- Змінити NACL на stateful
= NACL stateless: відповіді сервера йдуть на тимчасові порти клієнтів (ephemeral ports), тож вихідне правило має дозволяти 1024–65535. Зробити NACL stateful неможливо.

? Адміністраторам потрібен доступ до командного рядка приватних серверів Linux без відкритих вхідних портів, без бастіону, із записом усіх сесій. Що обрати?
- Bastion host у публічній підмережі
- Відкрити порт 22 лише для офісу
+ AWS Systems Manager Session Manager
- VPN до кожного сервера
= Session Manager працює через агента SSM без вхідних портів, доступ керується IAM, сесії записуються в S3 або CloudWatch Logs. Бастіон і відкритий порт вимагають відкритого SSH.

? Яке твердження про Security Groups правильне?
+ Вони stateful: відповідь на дозволений вхідний запит пропускається автоматично
- Правила оцінюються за номерами, перше збіжне перемагає
- Вони діють на рівні підмережі
- Нова Security Group за замовчуванням дозволяє весь вхідний трафік
= SG stateful, діють на рівні мережевого інтерфейсу, правила оцінюються разом. Нова SG не має вхідних правил (усе заблоковано), але дозволяє весь вихідний трафік.

? Команда хоче бачити, які з'єднання до серверів відхиляються, щоб знайти помилки в правилах. Вміст пакетів не потрібен. Що увімкнути?
+ VPC Flow Logs
- Traffic Mirroring
- AWS WAF logs
- CloudTrail data events
= Flow Logs записують метадані з'єднань, зокрема статус ACCEPT/REJECT. Traffic Mirroring копіює вміст пакетів (дорожче і зайве тут), WAF бачить лише HTTP на підтримуваних ресурсах, CloudTrail — API-виклики.

? Які два твердження про Network ACL правильні? (Оберіть 2)
+ NACL підтримують правила Allow і Deny
- До одного інстансу можна прикріпити кілька NACL
+ Власна (custom) NACL за замовчуванням забороняє весь трафік
