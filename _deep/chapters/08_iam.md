> 🎬 **Історія Хмаринки.** Перший тиждень у хмарі. Тарас налаштовує сервери, Марта хоче бачити рахунки, Олена — «просто подивитися», а на склад прийшов стажер, якому треба лише завантажувати фото товарів. Раніше всі входили на сервер під одним паролем адміністратора. Одного ранку зникла папка з фото — і ніхто не зміг сказати, хто її видалив. Більше так не буде: у кожного — свій вхід, свої права і повний журнал дій. За це в AWS відповідає **IAM**.

> 🖼️ **Образ.** Бізнес-центр з електронними перепустками. **Користувач** — перепустка конкретної людини. **Група** — відділ: усім бухгалтерам видають однаковий набір дверей. **Політика** — список дверей, які відчиняє перепустка («поверх 3 — так, серверна — ні»). За замовчуванням **нова перепустка не відчиняє нічого** — доступ додають явно. А якщо десь написано «сюди — заборонено», ця заборона сильніша за будь-який дозвіл.

## Що таке IAM

**AWS Identity and Access Management (IAM)** — сервіс, що відповідає на два питання для кожного запиту до AWS:

1. **Хто ти?** — автентифікація: пароль і MFA для людей у консолі, підписані ключами запити для програм.
2. **Що тобі можна?** — авторизація: політики, що дозволяють або забороняють дії з ресурсами.

IAM — **глобальний** і **безкоштовний** сервіс. Будь-який запит в AWS можна розкласти на чотири частини — запам'ятай їх, бо з них складається кожна політика:

- **Principal** — хто просить (користувач, роль, сервіс AWS);
- **Action** — що саме хоче зробити (`s3:GetObject`, `ec2:StartInstances`);
- **Resource** — з яким ресурсом (конкретний bucket, сервер, таблиця);
- **Condition** — за яких умов (з якої IP-адреси, з MFA чи без, в якому регіоні).

## Користувачі, групи і ролі {#identities}

**IAM user** — постійна «особа» в акаунті з довгостроковими обліковими даними:

- **пароль** для входу в консоль (плюс MFA);
- **access keys** — пара ключів (Access Key ID + Secret Access Key) для CLI, SDK і програм.

**IAM group** — набір користувачів. Політики прикріплюють до групи — і всі її учасники отримують ці права. Прийшов новий бухгалтер — додав у групу Finance, звільнився — прибрав. Особливості груп:

- групи **не вкладаються** одна в одну;
- користувач може бути в кількох групах (права додаються);
- група — **не principal**: на неї не можна послатися в політиці ресурсу («дозволити групі Finance доступ до bucket» напряму не вийде).

**IAM role** — «особа без людини»: набір прав, який тимчасово **беруть на себе** (assume) люди, сервіси чи програми, отримуючи **тимчасові** облікові дані. Ролі — найважливіший механізм безпеки AWS, їм присвячений увесь [наступний розділ](#ch/roles).

:::note 📌 Сучасна рекомендація AWS для людей
Для співробітників AWS радить не створювати IAM users у кожному акаунті, а використовувати **єдиний вхід** через **IAM Identity Center** (з тимчасовими обліковими даними). IAM users лишаються для особливих випадків: аварійний доступ, старі інструменти, що не вміють працювати з ролями. На іспиті вимога «керувати доступом співробітників до багатьох акаунтів» майже завжди веде до Identity Center ([розділ 9](#ch/roles)). Але механіка політик однакова для всіх — тож розбираємо її тут.
:::

## Політики: мова дозволів {#policies}

**Політика** — JSON-документ з одним чи кількома **твердженнями** (statements). Кожне твердження каже: «**Дозволити** (або **заборонити**) **такі дії** над **такими ресурсами** за **таких умов**».

Ось політика, що дозволяє стажерові завантажувати й переглядати фото лише в одній «папці» bucket Хмаринки:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListPhotosFolder",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::khmarynka-photos",
      "Condition": { "StringLike": { "s3:prefix": "products/*" } }
    },
    {
      "Sid": "ReadWritePhotos",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::khmarynka-photos/products/*"
    }
  ]
}
```

Розберімо поля:

- **Version** — версія мови політик. Завжди `"2012-10-17"` (це не дата створення твоєї політики!).
- **Sid** — необов'язкова назва твердження для зручності.
- **Effect** — `Allow` або `Deny`.
- **Action** — дії у форматі `сервіс:Дія`. Можна зірочки: `s3:*` (усі дії S3), `s3:Get*` (усі, що починаються на Get).
- **Resource** — на які ресурси діє, у форматі **ARN**.
- **Condition** — додаткові умови (про них нижче).
- **Principal** — «кому» — з'являється лише в політиках, прикріплених до **ресурсів** (resource-based), бо в політиці користувача «кому» і так очевидно.

### ARN — повна адреса ресурсу

**ARN** (Amazon Resource Name) однозначно називає будь-який ресурс в AWS:

```text
arn:aws:<сервіс>:<регіон>:<номер-акаунта>:<ресурс>

arn:aws:iam::111122223333:user/taras                       (IAM глобальний — регіону немає)
arn:aws:s3:::khmarynka-photos                               (bucket — ні регіону, ні акаунта)
arn:aws:s3:::khmarynka-photos/products/mug.jpg              (об'єкт у bucket)
arn:aws:ec2:eu-central-1:111122223333:instance/i-0abc123   (сервер у Франкфурті)
```

Зверни увагу на пастку з S3, яку обожнює іспит: дія `s3:ListBucket` (переглянути список файлів) стосується **самого bucket** — ARN без `/*`. А `s3:GetObject` і `s3:PutObject` стосуються **об'єктів** — ARN з `/*`. Переплутаєш — отримаєш `AccessDenied`.

### Види політик

| Вид | До чого прикріплюється | Хто керує | Коли використовувати |
|---|---|---|---|
| **AWS managed** | До користувачів, груп, ролей | AWS (оновлює сам) | Швидкий старт: `ReadOnlyAccess`, `AdministratorAccess`, `AmazonS3ReadOnlyAccess`, політики за посадами |
| **Customer managed** | До користувачів, груп, ролей | Ти | Точні права під свої ресурси; одна політика — для багатьох; є версії |
| **Inline** | Вбудована в одного користувача/групу/роль | Ти | Рідко: коли права мають жити і видалятися разом з цією «особою» |
| **Resource-based** | До ресурсу (bucket S3, черга SQS, ключ KMS, функція Lambda…) | Власник ресурсу | Дати доступ до ресурсу, зокрема **іншим акаунтам**; має поле Principal |

Ще кілька типів — **permission boundaries**, **SCP** і **RCP** організацій, **session policies** — не дають прав, а **обмежують** їх зверху. Про них — у [розділах 9](#ch/roles) і [10](#ch/organizations).

## Як AWS вирішує: дозволити чи заборонити {#evaluation}

Це серце IAM. Запам'ятай три правила — вони пояснюють 90% питань іспиту про доступ:

1. **За замовчуванням усе заборонено** (implicit deny). Новий користувач без політик не може нічого.
2. **Явний дозвіл** (`Allow`) у будь-якій доречній політиці відкриває дію.
3. **Явна заборона** (`Deny`) у будь-якій політиці **перемагає все**. Жоден Allow її не скасує.

:::example 🧩 Потренуймося
Тарас у двох групах. Група **Developers** має політику `Allow s3:*` на всі bucket. Група **Safety** має `Deny s3:DeleteBucket` на `khmarynka-photos`.
- Чи може Тарас завантажити файл у `khmarynka-photos`? **Так** — є Allow, немає Deny на цю дію.
- Чи може Тарас видалити bucket `khmarynka-photos`? **Ні** — явний Deny перемагає Allow.
- Чи може Тарас запустити сервер EC2? **Ні** — жодного Allow для EC2, спрацьовує неявна заборона.
:::

## Умови: коли дозвіл діє лише за певних обставин {#conditions}

Блок `Condition` робить політики «розумними». Найвідоміші ключі умов:

| Ключ | Що перевіряє | Приклад використання |
|---|---|---|
| `aws:MultiFactorAuthPresent` | Чи увійшла людина з MFA | Дозволити видаляти лише з MFA |
| `aws:SourceIp` | IP-адреса запиту | Доступ лише з офісної мережі |
| `aws:RequestedRegion` | Регіон, у якому виконується дія | Працювати лише в регіонах ЄС |
| `aws:SecureTransport` | Чи запит по HTTPS | Заборонити незашифровані запити до S3 |
| `aws:PrincipalOrgID` | З якої AWS Organization той, хто просить | Пускати в bucket лише акаунти своєї організації |
| `aws:PrincipalTag` / `aws:ResourceTag` | Теги особи й ресурсу | Доступ за тегами (ABAC) |
| `aws:CurrentTime` | Час запиту | Тимчасовий доступ до дати |

Приклад: заборонити будь-кому видаляти об'єкти, якщо вхід виконано без MFA:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Deny",
    "Action": ["s3:DeleteObject", "s3:DeleteObjectVersion"],
    "Resource": "arn:aws:s3:::khmarynka-photos/*",
    "Condition": { "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" } }
  }]
}
```

:::deep 🔬 Глибше: чому часто пишуть Deny з умовою, а не Allow з умовою
Уяви, що потрібно «дозволяти видалення лише з MFA». Якщо написати `Allow` з умовою MFA, то будь-яка **інша** політика з простим `Allow s3:*` відкриє видалення і без MFA — Allow-и додаються. А `Deny` з умовою «без MFA» перекриває **всі** можливі Allow. Тому захисні правила («ніколи без HTTPS», «ніколи поза ЄС», «ніколи без MFA») пишуть як **Deny + умова**. Суфікс **IfExists** (`BoolIfExists`) означає: «якщо ключа в запиті немає — теж вважати умову виконаною» — інакше запити з ключами доступу (де ключа MFA немає взагалі) проскочили б повз заборону.
:::

## Принцип найменших привілеїв {#least-privilege}

**Least privilege** — кожна особа має рівно ті права, що потрібні для її роботи, і не більше. Стажер завантажує фото — йому не потрібен доступ до бази замовлень. Якщо його ключі вкрадуть, шкода буде мінімальною.

Як досягти цього на практиці, не витрачаючи тижні:

1. **Почни з готових політик за посадами** (AWS managed job-function policies: `ReadOnlyAccess`, `PowerUserAccess`, `Billing`, `DatabaseAdministrator`…) — це безпечніше за `AdministratorAccess` для всіх.
2. **Звужуй за даними.** **IAM Access Analyzer** може **згенерувати політику** з реальної активності за журналом CloudTrail: «ось що цей користувач справді робив за 90 днів». Він же знаходить **невикористані** ролі, ключі й дозволи.
3. **Перевіряй останнє використання.** Вкладка **Last accessed** (Access Advisor) показує, коли особа востаннє користувалася кожним сервісом: права на сервіси, яких не торкалися місяцями, можна прибрати.
4. **Шукай зайвий зовнішній доступ.** Access Analyzer також знаходить ресурси (bucket, ключі KMS, ролі, черги), до яких мають доступ **інші акаунти чи весь світ**.
5. **Перевіряй політики до застосування:** валідатор політик Access Analyzer і **IAM Policy Simulator** показують, чи дозволить політика конкретну дію.
6. **Звітуй:** **Credential report** — таблиця всіх користувачів акаунта: чи є MFA, коли змінювали пароль, коли востаннє використовували ключі.

## Облікові дані: паролі, MFA, ключі доступу

- **Політика паролів** акаунта — мінімальна довжина, складність, строк дії, заборона повторів.
- **MFA** — для кожної людини з доступом до консолі. Типи: застосунок-автентифікатор на телефоні, апаратний ключ безпеки (FIDO2/passkey), апаратний генератор кодів.
- **Access keys** — для програмного доступу. Правила:
  - ніколи не вписувати в код і не класти в git-репозиторій (боти шукають ключі в публічних репозиторіях за хвилини);
  - для програм у AWS (на EC2, Lambda, ECS) ключі **не потрібні взагалі** — використовуються **ролі**;
  - регулярно ротувати й видаляти невикористані;
  - якщо ключ «витік»: одразу **деактивувати**, створити новий, перевірити в CloudTrail, що встигли зробити зловмисники.

:::lab 🧪 Спробуй у справжньому AWS: адміністратор замість root і перевірка прав
**Вартість:** безкоштовно (IAM не тарифікується). **Час:** 25 хвилин.
1. Увійди як root → сервіс **IAM** → **User groups** → **Create group** `Admins` → прикріпи політику `AdministratorAccess`.
2. **Users** → **Create user** `admin-твоєім'я` → увімкни **Provide user access to the AWS Management Console** → додай у групу `Admins`. Збережи посилання для входу (Sign-in URL) — воно містить номер акаунта.
3. **Dashboard** → праворуч **Account Alias** → **Create**: наприклад, `khmarynka-learning`. Тепер вхід виглядатиме як `https://khmarynka-learning.signin.aws.amazon.com/console`.
4. Вийди з root і **увійди як новий адміністратор**. Одразу: IAM → Users → свій користувач → **Security credentials** → **Assign MFA device**.
5. Створи групу `ReadOnly` з політикою `ReadOnlyAccess` і користувача `test-reader` у ній (без MFA, лише для тесту).
6. У вікні інкогніто увійди як `test-reader` і спробуй створити bucket S3 — отримаєш помилку доступу. Це **неявна заборона** в дії.
7. Повернись під адміністратора: IAM → **Policy simulator** (посилання на сторінці політик) → обери `test-reader` → сервіс S3 → дії `CreateBucket` і `ListAllMyBuckets` → **Run simulation**: перше — denied, друге — allowed.
8. IAM → **Credential report** → **Download**: подивись таблицю користувачів і стан MFA.
**Прибери за собою:** видали користувача `test-reader` і групу `ReadOnly`. Адміністратора з MFA залиш — надалі працюй під ним, а root поклади «в сейф».
:::

#### 💡 Запам'ятай

- IAM — глобальний і безкоштовний; відповідає на «хто ти» і «що тобі можна».
- **Users** — постійні облікові дані; **groups** — набори користувачів (не вкладаються, не principal); **roles** — тимчасові права.
- Політика: **Effect, Action, Resource, Condition** (+ **Principal** у resource-based). Version — завжди `2012-10-17`.
- Оцінка: **за замовчуванням заборонено → явний Allow дозволяє → явний Deny перемагає все**.
- Крос-акаунтний доступ потребує дозволу з **обох** боків.
- `s3:ListBucket` — на ARN bucket; `s3:GetObject`/`PutObject` — на `bucket/*`.
- Найменші привілеї: готові політики за посадами → звуження за даними (**Access Analyzer**, **Last accessed**) → валідація (Policy Simulator).
- Ключі доступу не зберігають у коді; програмам в AWS потрібні ролі, а не ключі.

#### 🎯 Як питають на іспиті

- Користувач має Allow у одній політиці і Deny на ту ж дію в іншій → **дію заборонено (явний Deny перемагає)**
- Новий IAM-користувач без політик намагається читати S3 → **AccessDenied (неявна заборона)**
- Однакові права для 20 бухгалтерів з простим додаванням нових → **IAM group з політикою**
- Знайти невикористані права і згенерувати мінімальну політику з реальної активності → **IAM Access Analyzer (policy generation, unused access)**
- Знайти bucket і ключі, доступні іншим акаунтам або публічно → **IAM Access Analyzer (external access)**
- Дозволити небезпечну дію лише з MFA → **умова aws:MultiFactorAuthPresent (краще — Deny, якщо MFA немає)**
- Доступ до API лише з офісної мережі → **умова aws:SourceIp**
- Звіт про всіх користувачів, їхні MFA і вік ключів → **IAM credential report**
- Застосунок на EC2 має звертатися до S3, ключі на сервері зберігати заборонено → **IAM role (instance profile)**, не access keys

#### ⚠️ Пастки

- Групу не можна вказати як Principal у політиці ресурсу і не можна вкласти в іншу групу.
- `"Version": "2012-10-17"` — це версія мови, а не дата. Не змінюй її.
- Allow з умовою MFA не захистить, якщо інша політика дає простий Allow — захисні правила пишуть як Deny.
- Розшарені облікові записи («один логін на відділ») руйнують аудит: у CloudTrail не видно, хто саме діяв.

## ✅ Перевір себе

:::quiz
? Користувача додали у дві групи: перша дає `Allow ec2:*`, друга — `Deny ec2:TerminateInstances`. Що він зможе робити з серверами EC2?
- Усе, включно з видаленням серверів, бо Allow ec2:* ширший
+ Усе, крім видалення (термінації) серверів
- Нічого, бо конфлікт політик блокує весь сервіс
- Лише те, що дозволено в першій групі за часом додавання
= Права з усіх політик об'єднуються, а явний Deny завжди перемагає Allow. Тому все з ec2:* дозволено, крім TerminateInstances.

? Політика дає `Allow s3:ListBucket` і `s3:GetObject` з ресурсом `arn:aws:s3:::khmarynka-photos/*`. Користувач може завантажувати файли, але не бачить список об'єктів. Чому?
- ListBucket вимагає MFA
+ ListBucket діє на ARN самого bucket (без /*), а в політиці вказано лише ARN об'єктів
- ListBucket не підтримується в IAM-політиках
- Потрібна окрема політика на рівні регіону
= Дія s3:ListBucket стосується bucket, тому ресурс має бути arn:aws:s3:::khmarynka-photos. Дії над об'єктами (GetObject, PutObject) — на arn:aws:s3:::khmarynka-photos/*. Часто в політиці вказують обидва ARN.

? Служба безпеки хоче знайти в акаунті IAM-ролі й дозволи, якими ніхто не користувався останні 90 днів, і прибрати зайве з найменшими зусиллями. Що використати?
- AWS Config з власними правилами
+ IAM Access Analyzer (unused access) і дані last accessed
- Amazon Inspector
- Вручну переглянути журнали CloudTrail за 90 днів
= IAM Access Analyzer виявляє невикористані ролі, ключі й дозволи, а Last accessed показує, коли сервіси використовувались востаннє. Inspector шукає вразливості ПЗ, Config — відповідність конфігурацій правилам.

? Як найнадійніше гарантувати, що об'єкти в bucket не можна видалити без MFA, навіть якщо користувачеві дали ширші дозволи іншими політиками?
- Додати Allow s3:DeleteObject з умовою MFA
+ Додати Deny s3:DeleteObject з умовою BoolIfExists aws:MultiFactorAuthPresent = false
- Прибрати всі політики з користувачів
- Увімкнути шифрування bucket
= Allow з умовою не допоможе, якщо інша політика дає простий Allow — дозволи додаються. Deny з умовою «немає MFA» перекриває всі Allow. IfExists закриває і запити без ключа MFA (наприклад, з access keys).

? Застосунку на сервері EC2 потрібен доступ до таблиці DynamoDB. Яке рішення найбезпечніше?
- Створити IAM-користувача і записати його access keys у конфігурацію застосунку
- Використати access keys root user
+ Прикріпити до сервера IAM-роль з потрібними правами (instance profile)
- Зробити таблицю публічною
= Роль, прикріплена до EC2 через instance profile, дає застосунку тимчасові облікові дані, що автоматично оновлюються. Жодних довгострокових ключів на сервері — нічого вкрасти.

? Команда з 15 аналітиків має отримати однакові права лише на читання, а нових аналітиків треба додавати швидко. Що зробити?
- Прикріпити inline-політику кожному користувачу окремо
+ Створити групу з потрібною політикою і додавати туди користувачів
- Створити одного спільного користувача для всіх аналітиків
- Дати всім AdministratorAccess, щоб не витрачати час
= Групи — стандартний спосіб видати однакові права багатьом людям. Спільний обліковий запис руйнує аудит, а AdministratorAccess порушує принцип найменших привілеїв.

? Що з цього можна вказати як Principal у resource-based політиці bucket S3? (Оберіть 2)
+ IAM-роль в іншому акаунті
- IAM-групу
+ Увесь AWS-акаунт за номером
- Регіон AWS
- Security Group
= Principal — це той, хто робить запит: акаунт, IAM user, роль, сервіс AWS, федеративний користувач. IAM-група не є principal, а регіон і Security Group — не особи.
:::
