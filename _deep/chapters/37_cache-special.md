> 🎬 **Історія Хмаринки.** Головна сторінка Хмаринки показує «популярні товари» — і щоразу рахує їх заново в базі, тисячі разів на хвилину, хоча список змінюється раз на годину. Пошук за словом «свічка» не знаходить «свічки», «свічок» і «candle». Маркетинг хоче рекомендації «з цим товаром купують», а склад — зберігати показники датчиків температури й вологості. Тарас розуміє: одна універсальна база на все — як один молоток для всіх задач. AWS пропонує **спеціалізовані бази** (purpose-built): кожна найкраща у своїй справі.

> 🖼️ **Образ.** **Кеш** — стікер на моніторі з номером телефону, який ти набираєш двадцять разів на день: не треба щоразу гортати телефонну книгу (базу). **Графова база** — дошка детектива з фотографіями і нитками між ними: головне — зв'язки. **Часові ряди** — щоденник метеостанції. **Пошуковий рушій** — предметний покажчик у кінці книжки, що знає всі форми слова.

## Кешування: навіщо і як {#caching}

Оперативна пам'ять у тисячі разів швидша за диск. **Кеш у пам'яті** зберігає результати, які часто читають, — і відповідає за **мікросекунди–мілісекунди**, знімаючи навантаження з основної бази.

Дві класичні стратегії (і обидві вимагають **змін у коді** застосунку):

## Amazon ElastiCache {#elasticache}

**Amazon ElastiCache** — керований кеш у пам'яті з трьома рушіями:

| | **Valkey / Redis OSS** | **Memcached** |
|---|---|---|
| Структури даних | Рядки, хеші, списки, множини, **sorted sets**, геодані, потоки, pub/sub | Лише прості ключ-значення |
| Реплікація і Multi-AZ | ✅ Репліки й **автоматичний failover** | ❌ |
| Збереження на диск, бекапи | ✅ Знімки | ❌ Дані в пам'яті — зникнуть при перезапуску |
| Масштабування | Шардинг (cluster mode), репліки для читання, **Global Datastore** між регіонами | Шардинг на боці клієнта, **багатопотоковість** |
| Коли | Майже завжди: сесії, лідерборди, лічильники, кеш з HA | Найпростіший багатопотоковий кеш, втрата даних некритична |

**Valkey** — відкрита спільнотою гілка Redis; AWS радить її для нових кешів (сумісна з Redis і дешевша). **ElastiCache Serverless** — кеш без вибору вузлів: масштабується автоматично, оплата за використання.

Типові задачі ElastiCache:

- **кеш запитів до бази** (RDS, Aurora, будь-якої) — lazy loading з TTL;
- **сесії** stateless-серверів ([розділ 23](#ch/autoscaling/stateless));
- **лідерборди** — **sorted sets** (рейтинг гравців, «топ продавців» оновлюється миттєво);
- обмеження частоти запитів (rate limiting), черги, pub/sub.

Безпека: кеш у приватних підмережах VPC, Security Groups, шифрування в дорозі й у спокої, автентифікація (AUTH, RBAC, IAM).

:::note 📌 «Без змін коду»
ElastiCache завжди вимагає логіки кешування в застосунку. Якщо в питанні вимога **«without changing the application code»**, дивись на інше: **read replicas** для RDS, **DAX** для DynamoDB (сумісний API), **CloudFront** для HTTP-контенту.
:::

## Amazon MemoryDB {#memorydb}

**Amazon MemoryDB** — Valkey/Redis-сумісна **основна база даних** (не кеш!) у пам'яті з **довговічністю**: кожен запис фіксується в розподіленому журналі транзакцій у кількох AZ. Читання — мікросекунди, запис — одноцифрові мілісекунди. Коли потрібна швидкість Redis **і** гарантія, що дані не зникнуть: профілі, кошики, стан гри, лічильники як джерело правди.

## Спеціалізовані бази {#purpose-built}

- **Amazon DocumentDB** — документна база, **сумісна з MongoDB**: JSON-документи з гнучкою структурою, архітектура сховища подібна до Aurora (копії в трьох AZ, репліки). Для перенесення MongoDB-застосунків у керований сервіс і каталогів з різною структурою документів.
- **Amazon Neptune** — **графова** база: вузли й зв'язки (Gremlin, openCypher, SPARQL). **Соцмережі** («друзі друзів»), **рекомендації** («хто купив це, купив і те»), **виявлення шахрайства** (зв'язані акаунти, картки, пристрої), графи знань.
- **Amazon Keyspaces** — serverless-база, **сумісна з Apache Cassandra** (мова CQL): для наявних Cassandra-застосунків без керування кластером.
- **Amazon Timestream** — **часові ряди**: мільйони вимірів з мітками часу, автоматичне перенесення старих даних у дешевший рівень, функції для аналізу в часі. **IoT-датчики**, метрики серверів і застосунків, телеметрія. (Є і варіант з керованим InfluxDB.)
- **Amazon OpenSearch Service** — **пошук і аналітика журналів** (відкритий форк Elasticsearch): повнотекстовий пошук з морфологією, синонімами, релевантністю, фасетами; дашборди **OpenSearch Dashboards**; **OpenSearch Serverless**; холодні рівні зберігання. Типово: каталог товарів з DynamoDB/Aurora → OpenSearch для пошуку; журнали → Firehose → OpenSearch для аналізу.
- **Amazon Redshift** — сховище даних для аналітики (OLAP) — [розділ 39](#ch/analytics).
- **Amazon QLDB** (журнальна база) **закрита з 31.07.2025** — не обирай її.

:::lab 🧪 Спробуй у справжньому AWS: кеш Valkey і лідерборд
**Вартість:** ElastiCache Serverless на 30 хвилин і маленький сервер — кілька десятків центів з кредитів. **Час:** 30 хвилин.
1. **ElastiCache → Create cache → Valkey** → **Serverless**. Назва `khmarynka-cache`, твоя VPC і дві приватні або публічні підмережі; Security Group, що дозволяє **TCP 6379** від Security Group сервера. Create.
2. Запусти (або використай наявний) сервер Amazon Linux 2023 у тій самій VPC і підключись до нього.
3. Встанови клієнт і підключись (кеш serverless вимагає TLS; endpoint скопіюй з консолі):
```bash
sudo dnf install -y redis6
redis6-cli --tls -h <endpoint-кешу> -p 6379
```
4. Спробуй кешування з TTL і лідерборд:
```text
SET product:42 "{\"name\":\"Свічка Лаванда\",\"price\":320}" EX 60
GET product:42
TTL product:42
ZADD sellers 1500 "Майстерня Оксани" 2300 "Свічки Львова" 900 "Керамік"
ZREVRANGE sellers 0 2 WITHSCORES
ZINCRBY sellers 1000 "Керамік"
ZREVRANGE sellers 0 2 WITHSCORES
```
Через 60 секунд `GET product:42` поверне порожнечу — TTL спрацював (lazy loading взяв би дані з бази знову).
**Прибери за собою:** видали кеш і сервер, Security Groups.
:::

#### 💡 Запам'ятай

- Кеш у пам'яті — мікросекунди; стратегії **lazy loading (cache-aside)** і **write-through**, **TTL**; потрібні **зміни в коді**.
- **ElastiCache Valkey/Redis:** реплікація, **Multi-AZ failover**, бекапи, **sorted sets** (лідерборди), pub/sub, Global Datastore; **Memcached:** простий, багатопотоковий, **без реплікації й збереження**; є **Serverless**.
- **MemoryDB** — основна Redis-сумісна база в пам'яті з довговічністю.
- **DocumentDB** — MongoDB; **Neptune** — графи; **Keyspaces** — Cassandra; **Timestream** — часові ряди; **OpenSearch** — пошук і журнали; **Redshift** — аналітика; **QLDB** — закрита.
- «Без змін коду» → не ElastiCache, а **read replicas** (RDS) чи **DAX** (DynamoDB).

#### 🎯 Як питають на іспиті

- Лідерборд гри в реальному часі → **ElastiCache for Valkey/Redis (sorted sets)**
- Зберігати сесії для stateless-вебсерверів → **ElastiCache або DynamoDB**
- Зменшити навантаження на RDS для повторюваних запитів → **ElastiCache (lazy loading)**
- Простий багатопотоковий кеш, реплікація не потрібна → **ElastiCache Memcached**
- Кеш має пережити збій вузла без втрати даних → **Valkey/Redis з Multi-AZ і репліками**
- Надшвидка основна база, сумісна з Redis, з довговічністю → **MemoryDB**
- Перенести MongoDB-застосунок у керований сервіс → **DocumentDB**
- Соцмережа «друзі друзів», рекомендації, виявлення шахрайських зв'язків → **Neptune**
- Перенести Cassandra в керований сервіс → **Keyspaces**
- Показники IoT-датчиків з мітками часу → **Timestream**
- Повнотекстовий пошук по каталогу, аналіз журналів з дашбордами → **OpenSearch Service**

#### ⚠️ Пастки

- ElastiCache не прискорить базу «без змін коду».
- Memcached не має реплікації, failover і бекапів — не для даних, які не можна втратити.
- Кеш ≠ основна база: для довговічних даних у пам'яті — MemoryDB.
- QLDB закрита — не обирай її навіть для «журналу незмінних записів».

## ✅ Перевір себе

:::quiz
? Мобільна гра має показувати глобальний рейтинг гравців, що оновлюється в реальному часі при кожному набранні очок. Що обрати?
+ Amazon ElastiCache for Valkey або Redis OSS із sorted sets
- Amazon RDS з ORDER BY при кожному запиті
- ElastiCache Memcached
- Amazon S3 з JSON-файлом рейтингу
= Sorted sets тримають елементи відсортованими за балом: оновлення і вибірка топу — за мікросекунди. Memcached не має таких структур, а сортування в базі при кожному запиті — повільно.

? Аплікація на RDS for MySQL щосекунди виконує тисячі однакових запитів до каталогу, що змінюється раз на годину. Команда готова змінити код. Як зменшити навантаження на базу найефективніше?
+ Кешувати результати в ElastiCache за стратегією lazy loading з TTL
- Додати DAX
- Перейти на Multi-AZ
- Збільшити період зберігання бекапів
= Кеш у пам'яті віддає результати без звернення до бази, а TTL обмежує застарілість. DAX працює лише з DynamoDB, Multi-AZ не допомагає з читанням.

? Кеш сесій має продовжувати роботу при відмові вузла, а сесії не повинні губитися. Що обрати?
- ElastiCache Memcached з кількома вузлами
+ ElastiCache for Valkey/Redis з репліками і Multi-AZ з автоматичним failover
- Instance store на вебсерверах
- Amazon S3 Standard
= Valkey/Redis підтримує реплікацію і автоматичний failover у Multi-AZ. Memcached не реплікує дані — при втраті вузла його дані зникають.

? Фінтех-компанія хоче виявляти мережі пов'язаних шахрайських акаунтів, що ділять пристрої, адреси й картки. Яка база найпридатніша?
+ Amazon Neptune
- Amazon DynamoDB
- Amazon Timestream
- Amazon ElastiCache
= Графова база природно зберігає і швидко обходить зв'язки між сутностями — класичний сценарій виявлення шахрайства. Інші бази не розраховані на глибокі запити по зв'язках.

? Компанія переносить застосунок, що використовує MongoDB, і хоче керований сервіс з мінімальними змінами коду. Що обрати?
- Amazon Keyspaces
+ Amazon DocumentDB
- Amazon Neptune
- Amazon RDS for PostgreSQL
= DocumentDB сумісний з API MongoDB. Keyspaces — для Cassandra, Neptune — графи, PostgreSQL вимагав би переписування.

? Потрібно зберігати й аналізувати мільярди показників датчиків температури з мітками часу, автоматично переносячи старі дані в дешевший рівень. Що обрати?
+ Amazon Timestream
- Amazon DocumentDB
- ElastiCache Memcached
- Amazon Neptune
= Timestream — спеціалізована база часових рядів з рівнями зберігання і функціями аналізу в часі.

? Інтернет-магазин хоче повнотекстовий пошук по каталогу з урахуванням форм слів, синонімів і сортуванням за релевантністю. Що обрати?
+ Amazon OpenSearch Service
- Amazon DynamoDB Scan з фільтром
- Amazon RDS LIKE-запити
- Amazon Keyspaces
= OpenSearch — пошуковий рушій з аналізаторами мови, синонімами, релевантністю і фасетами. Scan і LIKE повільні й не розуміють морфології.

? Які твердження про ElastiCache Memcached правильні? (Оберіть 2)
+ Підтримує багатопотокову роботу
- Має вбудовану реплікацію і автоматичний failover
+ Не зберігає дані на диск і не має бекапів
- Підтримує sorted sets для лідербордів
- Сумісний з API DynamoDB
= Memcached — простий багатопотоковий кеш без реплікації, persistence і складних структур даних. Реплікація, бекапи і sorted sets — у Valkey/Redis.
:::
