> 🎬 **Історія Хмаринки.** Тарас записався на іспит AWS Certified Solutions Architect – Associate. За тиждень до дати він зізнається Олені: «Знаю сервіси, але боюся питань: вони довгі, англійською, і всі варіанти здаються правильними». Олена, яка колись складала бухгалтерські іспити, сміється: «Це не вікторина фактів. Це **65 коротких консультацій**: клієнт описує проблему й обмеження, а ти обираєш найкращу пораду з чотирьох. Навчися читати обмеження — і половина варіантів відпаде сама».

> 🖼️ **Образ.** Кожне питання — **замовлення в ательє**: «костюм на весілля (контекст), до п'ятниці (обмеження часу), недорого (обмеження ціни), щоб не м'явся (вимога)». Чотири кравці пропонують варіанти. Один шиє чудовий костюм, але до наступного місяця. Другий — швидко, але дорого. Третій пропонує джинси. Четвертий виконує **всі** умови. Твоя робота — знайти четвертого.

## Формат іспиту {#format}

| Параметр | Значення |
|---|---|
| Питань | **65**: 50 оцінюються + 15 експериментальних (не знаєш, які саме — відповідай на всі) |
| Типи | **Multiple choice** — 1 правильна з 4; **multiple response** — 2 або більше з 5+ (кількість вказана в питанні) |
| Час | **130 хвилин** (2 хв на питання) |
| Бали | 100–1000, прохідний — **720** |
| Оцінювання | **Компенсаторне**: не треба «здати» кожен домен окремо; **штрафу за неправильну відповідь немає** — ніколи не лишай питання без відповіді |
| Часткові бали | **Немає**: у multiple response треба вибрати всі правильні варіанти |
| Ціна | **$150** (плюс податки) |
| Де | Тестовий центр **Pearson VUE** або онлайн з прокторингом (OnVUE) |
| Мови | Англійська та ще кілька мов (зокрема японська, корейська, китайська); української немає |
| Дійсний | **3 роки** |

:::note 📌 Складаєш англійською, а вона не рідна? Отримай +30 хвилин
AWS дає **ESL +30** — додаткові 30 хвилин для тих, для кого мова іспиту не рідна. Запит подають **до реєстрації на іспит** в акаунті AWS Certification (розділ про пристосування — *exam accommodations*). Це безкоштовно, і 160 хвилин замість 130 — величезна перевага. Обов'язково скористайся.
:::

## Чотири домени {#domains}

| Домен | Вага | Про що | Розділи |
|---|---|---|---|
| **1. Безпечні архітектури** | **30%** | Доступ до ресурсів (IAM, ролі, федерація, кілька акаунтів, SCP); захист застосунків (VPC, SG і NACL, WAF, Shield, endpoints, Cognito, секрети); захист даних (шифрування, KMS, ACM, бекапи, життєвий цикл) | [8–12](#ch/iam), [13–15](#ch/vpc), [27–28](#ch/s3) |
| **2. Стійкі архітектури** | **26%** | Масштабовані й слабко зв'язані системи (черги, події, Lambda, контейнери, кеш); висока доступність і стійкість до збоїв (Multi-AZ, DR, Route 53, бази) | [22–25](#ch/elb), [31–32](#ch/sqs-sns), [34–36](#ch/rds), [42](#ch/resilience) |
| **3. Високопродуктивні архітектури** | **24%** | Сховища, обчислення, бази, мережа, отримання й перетворення даних — обрати найпродуктивніше рішення | [17–21](#ch/route53), [27–30](#ch/s3), [34–40](#ch/rds) |
| **4. Оптимізовані за вартістю** | **20%** | Вартість сховищ, обчислень, баз і мережі | [20](#ch/ec2-pricing), [28](#ch/s3-deep), [43](#ch/cost) |

Висновок: **безпека** — найбільший домен, і вона присутня майже в кожному питанні інших доменів. А «найдешевше» з'являється набагато частіше, ніж 20% питань: у багатьох питаннях це додаткова умова.

## Анатомія питання {#anatomy}

:::example 🔍 Розбираємо питання на частини
*A company runs a web application on Amazon EC2 instances behind an Application Load Balancer. The application stores user-uploaded images on the instances' EBS volumes. **As the company scales**, users report that images are **sometimes missing**. The company needs a solution that is **highly available** and requires the **LEAST operational overhead**. What should a solutions architect do?*

- **Контекст:** EC2 за ALB, картинки на дисках EBS окремих серверів.
- **Симптом:** при масштабуванні картинок «немає» — кожен сервер бачить лише свій диск.
- **Вимоги:** висока доступність + **найменше операційних зусиль**.
- **Кандидати:** спільна файлова система **EFS** (працює, але це все одно файлова система, яку треба монтувати) або **S3** (об'єктне сховище, керований, безмежний, високодоступний).
- **Рішення:** зберігати завантаження в **Amazon S3** — найменше зусиль і найвища доступність. Варіант «синхронізувати диски скриптом через cron» — більше зусиль і ненадійно; «більший EBS» — не розв'язує проблему.
:::

Структура майже завжди однакова: **контекст → проблема → вимоги й обмеження → «What should…?»**. Правильну відповідь визначають **обмеження**, а не контекст.

## Метод чотирьох кроків {#method}

1. **Прочитай останнє речення першим.** Що саме питають: «Which solution meets these requirements…», «What should… do to…», «Which combination of steps…(Choose two)».
2. **Випиши обмеження.** Найдешевше? Найменше зусиль? Без змін коду? У реальному часі? Висока доступність? Безпечно? Часто їх два-три, і правильна відповідь виконує **всі**.
3. **Відкинь очевидно неправильні.** Сервіс не для цієї задачі (Config для «хто видалив»), порушує обмеження (EC2 при «без серверів»), небезпечний (ключі доступу в коді, root), неіснуюча можливість.
4. **З двох, що лишилися,** обери ту, що виконує **всі** вимоги **найпростіше** і найбільше «по-AWS-івськи»: вбудована можливість сервісу перемагає власний скрипт, керований сервіс — самописний на EC2, автоматика — ручні кроки.

:::mnemo 🧠 ВОВК
**В**имога (що питають) → **О**бмеження (дешево, швидко, без коду) → **В**ідкинь зайве → **К**раще з двох. Коли питання здається складним — прожени його через ВОВКа.
:::

## Типи хибних варіантів {#distractors}

| Тип пастки | Як виглядає | Приклад |
|---|---|---|
| Справжній сервіс не на своєму місці | Звучить переконливо, але розв'язує іншу задачу | Config замість CloudTrail для «хто видалив»; Multi-AZ для масштабування читання |
| Надмірна інженерія | Працює, але складніше і дорожче, ніж треба | Власний кластер Kafka на EC2 замість SQS; EKS для однієї простої задачі |
| Частково правильний | Виконує одну вимогу, але не другу | Дешево, але в одній AZ; швидко, але з ручними кроками |
| Ручна робота | «Адміністратор щодня запускає скрипт» при вимозі автоматизації | Cron-скрипт замість lifecycle-правила S3 |
| Антипатерн безпеки | Ключі доступу в коді, публічний bucket, root | «Зберегти access key в конфігураційному файлі на EC2» замість ролі |
| Неіснуюча можливість | Вигадана функція сервісу | «Увімкнути шифрування в Security Group» |

## Розбір трьох питань {#worked}

:::example 🧩 Питання 1: «найменше зусиль»
*Компанія зберігає журнали застосунку в S3. Журнали мають бути доступні для частих запитів 30 днів, потім рідко — протягом року, потім видалятися. Потрібне рішення з найменшими операційними зусиллями.*
- A. Lambda щодня копіює старі файли в інший bucket і видаляє їх через рік.
- B. **Правило S3 Lifecycle: через 30 днів — S3 Standard-IA (або Glacier Instant Retrieval), через 365 днів — видалення.**
- C. Щомісяця адміністратор вручну змінює клас зберігання.
- D. Зберігати журнали на EBS і робити знімки.

**Думаємо:** «найменше зусиль» відкидає A (код) і C (ручна робота); D — не той тип сховища. **B** — вбудована можливість S3, жодного коду.
:::

:::example 🧩 Питання 2: дві вимоги одночасно
*Застосунок у приватних підмережах має завантажувати великі обсяги даних з S3. Трафік не повинен іти через інтернет, а витрати мають бути мінімальними.*
- A. NAT Gateway у кожній AZ.
- B. **Gateway VPC endpoint для S3 і маршрути в таблицях приватних підмереж.**
- C. Interface VPC endpoint для S3.
- D. Перемістити сервери в публічні підмережі.

**Думаємо:** A і D ведуть трафік через інтернет-шлюз — порушують першу вимогу. C — приватно, але платно (погодинно й за гігабайт). **B** — приватно **і** безкоштовно: виконує обидві вимоги.
:::

:::example 🧩 Питання 3: multiple response
*Вебзастосунок на EC2 за ALB має витримувати втрату цілої AZ без простою. Які дві дії потрібні? (Choose two.)*
- A. **Розмістити Auto Scaling group у кількох AZ.**
- B. Використати більший тип інстансу.
- C. **Перевести базу RDS у Multi-AZ.**
- D. Увімкнути detailed monitoring у CloudWatch.
- E. Зробити знімки EBS щогодини.

**Думаємо:** вимога — пережити втрату AZ. Потрібна надлишковість **і** обчислень (A), **і** бази (C). B не прибирає єдину точку відмови, D лише спостерігає, E — бекап, а не доступність (відновлення займе час).
:::

## Пари-близнюки {#pairs}

| Пара | Ключова різниця |
|---|---|
| **SQS** vs **SNS** vs **EventBridge** | Черга (один обробник, буфер) · розсилка (багато підписників, без зберігання) · шина подій з правилами фільтрації, розкладом і SaaS |
| **ALB** vs **NLB** vs **GWLB** | HTTP/HTTPS, шляхи, хости · TCP/UDP, статичні IP, мільйони запитів · вставити файрволи сторонніх виробників |
| **CloudFront** vs **Global Accelerator** | Кешування контенту на краю (HTTP) · мережа AWS для будь-якого TCP/UDP, статичні anycast IP, швидкий failover |
| **Security Group** vs **NACL** | На інтерфейсі, stateful, лише allow · на підмережі, stateless, allow і deny, правила по номерах |
| **Gateway** vs **interface endpoint** | Лише S3 і DynamoDB, безкоштовно, маршрут · більшість сервісів, ENI з приватною IP, платно |
| **VPC peering** vs **Transit Gateway** | Пара VPC, нетранзитивно, дешево · хаб для сотень VPC і офісів, транзитивно |
| **VPN** vs **Direct Connect** | Через інтернет, шифровано, швидко налаштувати · приватний канал, стабільно, тижні на підключення, без шифрування за замовчуванням |
| **Multi-AZ** vs **read replica** | Доступність (standby не читається в класичному режимі) · масштабування читання й DR, асинхронно |
| **Aurora Global Database** vs **cross-region read replica RDS** | RPO ~1 с, до 10 регіонів, швидкий failover · простіше, повільніше, promote вручну |
| **DynamoDB global tables** vs **DAX** | Реплікація між регіонами (запис усюди) · кеш у пам'яті перед таблицею (мікросекунди) |
| **KMS** vs **CloudHSM** | Керований сервіс ключів, інтеграція з сервісами · виділений HSM, ключі повністю під твоїм контролем |
| **Secrets Manager** vs **Parameter Store** | Автоматична ротація, платний · налаштування й прості секрети, standard — безкоштовний |
| **CloudTrail** vs **Config** vs **CloudWatch** | Хто що зробив · яка конфігурація і чи відповідає правилам · як працює (метрики, логи, аларми) |
| **Kinesis Data Streams** vs **Firehose** | Реальний час, свої споживачі, replay · доставка в сховища без коду, near real-time |
| **EFS** vs **FSx** vs **S3** | Спільна NFS для Linux · Windows/SMB, Lustre, NetApp ONTAP, OpenZFS · об'єкти через API |
| **DataSync** vs **Transfer Family** vs **DMS** | Копіювання й синхронізація файлів · SFTP/FTPS/FTP для партнерів · міграція й реплікація баз |
| **Savings Plans** vs **Reserved Instances** | Зобов'язання $/год, гнучкість сімейств і сервісів · конкретний тип інстансу (Convertible — з обміном) |
| **Pilot Light** vs **Warm Standby** | Дані живі, сервери вимкнені · зменшена робоча копія всього застосунку |
| **SCP** vs **permissions boundary** | Межа для всіх у акаунті (Organizations) · межа для конкретного користувача чи ролі |
| **Cognito user pools** vs **identity pools** | Вхід і токени користувачів застосунку · тимчасові AWS-облікові дані для доступу до сервісів |

## Старі назви і закриті сервіси {#renames}

Банк питань оновлюється повільніше, ніж AWS. Ти можеш побачити старі назви — не лякайся:

| На іспиті може бути | Сьогодні |
|---|---|
| Kinesis Data Firehose | **Amazon Data Firehose** |
| Kinesis Data Analytics | **Managed Service for Apache Flink** |
| Amazon QuickSight | **Amazon Quick Sight** (у складі Amazon Quick) |
| Amazon SageMaker | **Amazon SageMaker AI** |
| AWS Security Hub | **Security Hub CSPM** + новий Security Hub (з 2025) |
| Snowball Edge, Snowcone | Закриті для нових клієнтів (Snowcone — з 2024, Snowball Edge — з 11.2025); на іспиті — ще правильна відповідь для офлайн-перенесення терабайтів |
| Amazon Forecast, Fraud Detector | Закриті для нових клієнтів; на іспиті — ще можливі відповіді |
| S3 Select, S3 Object Lambda, Glacier vaults | Закриті для нових клієнтів; сучасні альтернативи — Athena, класи S3 Glacier |
| AWS App Runner | Закритий для нових клієнтів з 30.04.2026 → ECS Express Mode |

Правило: **відповідай так, як задумано в питанні**. Якщо питання описує перенесення 500 TB з дата-центру з повільним каналом за тиждень — очікувана відповідь «Snowball Edge», навіть якщо сьогодні новий клієнт обрав би інший шлях.

## Керування часом {#time}

- **Перший прохід (~90 хв):** відповідай на все; якщо вагаєшся довше 2 хвилин — обери найкращий варіант, **познач (flag)** і рухайся далі.
- **Другий прохід (~30 хв):** лише позначені питання. Часто наступні питання підказують відповідь на попередні.
- **Останні 10 хв:** перевір, що **немає пропущених** питань.
- Змінюй відповідь лише тоді, коли знайшов **конкретну причину**, а не «здається». Перша інтуїція, заснована на знаннях, зазвичай правильна.

## День іспиту {#exam-day}

- **Напередодні:** легке повторення «Як питають на іспиті» і пар-близнюків, **сон** важливіший за ще 50 питань.
- **Онлайн:** тихе приміщення, чистий стіл, стабільний інтернет, вебкамера; **перевірка системи** Pearson VUE заздалегідь; вхід за 30 хвилин. Не можна виходити з кадру, говорити вголос, мати телефон поруч.
- **У тестовому центрі:** прийди за 30 хвилин, документ з фото, ім'я — як в акаунті AWS Certification.
- **Під час:** дихай, пий воду до початку, не зациклюйся на одному питанні.

## Після іспиту {#after}

#### 💡 Запам'ятай

- **65 питань, 130 хвилин (+30 з ESL), 720 з 1000**, штрафу за вгадування немає — відповідай на все.
- Домени: **безпека 30%**, стійкість 26%, продуктивність 24%, вартість 20%.
- Відповідь визначають **обмеження**: least operational overhead, most cost-effective, highly available, real-time, without code changes.
- **ВОВК:** вимога → обмеження → відкинь зайве → краще з двох.
- Вбудована можливість > власний скрипт; керований сервіс > самописний на EC2; автоматика > ручні кроки; роль > ключі доступу.
- Старі назви на іспиті — нормально; відповідай так, як задумано в питанні.

#### 🎯 Як питають на іспиті

- «LEAST operational overhead» → **керований або serverless сервіс, вбудована можливість**
- «MOST cost-effective» для переривних задач → **Spot**; для стабільних → **Savings Plans / RI**
- «Highly available» → **кілька AZ**; «disaster recovery» → **інший регіон**
- «Decouple» / «don't lose requests during spikes» → **SQS**
- «Choose two» → обидві відповіді мають бути **необхідними**, а не просто правильними фактами
- «Without changing application code» → **rehost / той самий рушій / мережеве рішення**, а не переписування

#### ⚠️ Пастки

- Відповідь, **правильна фактично**, але не виконує **всіх** вимог, — неправильна.
- Не додавай у питання власних припущень: якщо вимоги мінімальної ціни немає, найдорожчий варіант може бути правильним.
- У multiple response перевір кількість: «Choose two» — рівно два.
- Не витрачай 8 хвилин на одне питання: познач і повернись.

## ✅ Перевір себе

:::quiz
? Компанія хоче обробляти зображення, які користувачі завантажують у S3, з найменшими операційними зусиллями. Обробка триває до 30 секунд на зображення, навантаження нерівномірне. Що обрати?
+ Подія S3 запускає функцію AWS Lambda
- Постійно працюючий інстанс EC2, що опитує bucket щохвилини
- Кластер Amazon EMR
- Кластер Amazon EKS з автоскейлером вузлів
= Короткі задачі за подією з нерівномірним навантаженням — ідеальний випадок для Lambda: без серверів, масштабування і оплата за виклики. Інші варіанти потребують керування інфраструктурою.

? Застосунок на EC2 має доступ до DynamoDB. Зараз ключі доступу IAM-користувача записані в конфігураційному файлі. Як зробити найбезпечніше?
+ Призначити інстансу роль IAM з потрібними правами і прибрати ключі з файлу
- Зашифрувати конфігураційний файл за допомогою KMS
- Зберігати ключі в змінних середовища
- Ротувати ключі доступу щомісяця вручну
= Роль IAM надає тимчасові облікові дані, що автоматично оновлюються, — жодних довгострокових ключів на сервері.

? Компанії потрібне сховище для щоденних бекапів, які майже ніколи не читають, але мають зберігатися 7 років. Отримання даних за 12–48 годин прийнятне. Що найдешевше?
- S3 Standard-IA
- S3 Glacier Instant Retrieval
+ S3 Glacier Deep Archive
- EBS Cold HDD (sc1)
= Deep Archive — найдешевший клас S3 для даних, які рідко потрібні і можуть відновлюватися до 48 годин.

? Компанія переносить застосунок з власного дата-центру в AWS і хоче зробити це якнайшвидше, без змін коду. Застосунок працює на 40 віртуальних машинах. Що використати?
+ AWS Application Migration Service (rehost)
- Переписати застосунок на контейнери ECS
- AWS Database Migration Service для всіх серверів
- AWS Elastic Beanstalk
= MGN реплікує сервери й запускає їх в AWS без змін коду — найшвидший шлях «lift and shift». DMS призначений для баз даних.

? Вебсайт має витримувати раптові піки трафіку, а замовлення не повинні губитися, навіть якщо сервіс обробки тимчасово недоступний. Які дві дії допоможуть? (Оберіть 2)
+ Додати чергу Amazon SQS між вебшаром і сервісом обробки
+ Розмістити вебшар в Auto Scaling group за балансувальником у кількох AZ
- Збільшити тип інстансу бази даних
- Увімкнути detailed monitoring
- Використати S3 Transfer Acceleration
= Черга зберігає замовлення, поки обробка недоступна, а Auto Scaling у кількох AZ приймає піки трафіку. Інші дії не розв'язують ні проблему піків, ні втрату замовлень.

? Користувачі по всьому світу працюють з ігровим сервером через UDP. Потрібні статичні IP-адреси і швидке перемикання між регіонами при збої. Що обрати?
- Amazon CloudFront
+ AWS Global Accelerator
- Route 53 з простою маршрутизацією
- Application Load Balancer
= Global Accelerator підтримує TCP і UDP, дає статичні anycast IP і перемикає трафік між регіонами за секунди. CloudFront і ALB працюють з HTTP(S).

? Питання вимагає «LEAST operational overhead». Який варіант зазвичай НЕ підходить?
+ Власне рішення на EC2 зі скриптами cron, яке треба патчити й моніторити
- Вбудована можливість сервісу (наприклад, правило S3 Lifecycle)
- Керований сервіс (наприклад, Amazon RDS замість бази на EC2)
- Serverless-сервіс (наприклад, AWS Lambda або Fargate)
= «Найменше операційних зусиль» означає обирати керовані, serverless і вбудовані можливості. Власні сервери й скрипти — це саме те, що створює операційне навантаження.

? Компанія повинна зберігати дані в S3 і автоматично видаляти об'єкти через 90 днів. Також потрібно заборонити будь-кому видаляти об'єкти раніше цього терміну. Які дві дії? (Оберіть 2)
+ Увімкнути S3 Object Lock у режимі compliance з терміном 90 днів
+ Налаштувати правило S3 Lifecycle на видалення через 90 днів
- Увімкнути версіонування без інших налаштувань
- Налаштувати Lambda, що щодня видаляє старі об'єкти
- Використати S3 Transfer Acceleration
= Object Lock у compliance mode забороняє видалення до кінця терміну, а Lifecycle автоматично видаляє об'єкти після нього. Lambda — зайвий код, версіонування саме по собі не забороняє видалення.
:::
