> 🎬 **Історія Хмаринки.** Три неприємні знахідки першого аудиту. Перша: пароль до бази замовлень лежить відкритим текстом у файлі налаштувань на сервері — й у git-репозиторії. Друга: торік сайт «ліг» на пів дня, бо сертифікат HTTPS прострочився, а поновити забули. Третя: юрист питає, чи зашифровані адреси й телефони клієнтів і **хто** має доступ до ключів. Цей розділ — про те, як AWS шифрує все «за замовчуванням», і про те, яку частину роботи все ж треба зробити тобі.

> 🖼️ **Образ.** **KMS** — банківське сховище ключів з охороною і журналом відвідувань: ключі ніколи не залишають сховища, ти лише просиш «зашифруй» чи «розшифруй», і кожен візит записується. **CloudHSM** — власний сейф у банку, код від якого знаєш тільки ти (навіть банк не відчинить). **Secrets Manager** — сейф для паролів, який сам міняє шифр кожні 30 днів. **ACM** — служба, що безкоштовно видає і вчасно поновлює «паспорти» сайтів (сертифікати).

## Два стани даних — два види шифрування

- **In transit** (у дорозі): дані, що летять мережею, — захищає **TLS** (HTTPS). Між браузером і балансувальником, між сервером і базою, між твоїм офісом і AWS (VPN).
- **At rest** (у спокої): дані на дисках, у базах, у S3, у бекапах — захищає шифрування ключами **KMS**.

Well-Architected вимагає **обидва**. На іспиті вимога «encrypt data at rest and in transit» — це два окремі кроки: увімкнути шифрування сховища **і** примусити HTTPS/TLS.

## AWS KMS: керування ключами {#kms}

**AWS Key Management Service (KMS)** — керований сервіс створення і використання ключів шифрування. Головне:

- ключі живуть у **сертифікованих апаратних модулях безпеки** (HSM) і **ніколи не покидають KMS у відкритому вигляді**;
- KMS **інтегрований** з понад сотнею сервісів AWS: увімкнув шифрування в S3, EBS, RDS, DynamoDB — вони самі звертаються до KMS;
- **кожне використання ключа записується в CloudTrail** — видно, хто, коли і яким ключем шифрував чи розшифровував;
- ключі **регіональні**: ключ у Франкфурті не працює в Ірландії (крім multi-region keys, про них нижче).

### Типи ключів

| Тип | Хто керує | Політика ключа | Ротація | Ціна |
|---|---|---|---|---|
| **AWS owned keys** | AWS, невидимі для тебе | — | AWS | Безкоштовно |
| **AWS managed keys** (`aws/s3`, `aws/ebs`, `aws/rds`…) | AWS від твого імені, видно в акаунті | Не можна змінити | Автоматично щороку | Без щомісячної плати |
| **Customer managed keys** | Ти | Повний контроль: хто використовує, хто адмініструє | Автоматично (період від 90 до 2 560 днів, типово рік) або вручну на вимогу | ~$1 на місяць за ключ + запити |

Customer managed key потрібен, коли треба: власна політика доступу до ключа; поділитися зашифрованими даними з **іншим акаунтом**; власний період ротації; можливість вимкнути чи видалити ключ; окремий ключ на кожен проєкт чи клас даних.

Ключі бувають **симетричні** (AES-256 — один ключ шифрує і розшифровує, стандарт для даних в AWS) і **асиметричні** (пари RSA/ECC — для цифрових підписів і шифрування за межами AWS публічним ключем), а також HMAC-ключі для перевірки цілісності.

### Політика ключа (key policy)

Кожен ключ KMS має **key policy** — resource-based політику. Це **головний** механізм доступу до ключа: якщо key policy не дозволяє акаунту делегувати доступ через IAM, жодна IAM-політика не допоможе. Типова key policy довіряє акаунту (його root), і тоді доступ далі керується IAM-політиками. Для **доступу з іншого акаунта** потрібні обидва боки: дозвіл у key policy **і** IAM-політика в іншому акаунті.

Окремо в key policy розділяють **адміністраторів ключа** (можуть керувати, але не шифрувати) і **користувачів ключа** (можуть шифрувати, але не змінювати політику) — принцип розділення обов'язків.

### Envelope encryption: чому KMS не шифрує великі файли напряму {#envelope}

KMS-операція `Encrypt` приймає не більше **4 KB** даних — достатньо для пароля, але не для фото чи бекапу бази. І ганяти гігабайти в KMS по мережі було б повільно. Тому використовують **envelope encryption** («шифрування в конверті»):

### Корисні можливості KMS

- **Multi-Region keys** — «той самий» ключ (однаковий матеріал і ID) у кількох регіонах: дані, зашифровані у Франкфурті, розшифровуються в Ірландії без перешифрування. Корисно для DR і глобальних таблиць. Без них при копіюванні знімка в інший регіон дані перешифровуються ключем цільового регіону.
- **Видалення ключа** — лише з **періодом очікування від 7 до 30 днів** (типово 30). Поки строк не минув, видалення можна **скасувати**. Після видалення всі дані, зашифровані цим ключем, **назавжди недоступні**. Безпечніший крок — спершу **вимкнути** (disable) ключ і подивитися, чи щось не зламалося.
- **Квоти запитів.** KMS має ліміти запитів за секунду. Якщо мільйони об'єктів S3 шифруються з SSE-KMS, можна отримати `ThrottlingException`. Рішення — **S3 Bucket Keys**: S3 бере в KMS ключ рівня bucket і сам генерує з нього ключі об'єктів — запитів до KMS у сотні разів менше (і дешевше).
- **Імпорт власного ключового матеріалу** (BYOK) і **custom key stores** — ключі в твоєму кластері CloudHSM або навіть у зовнішньому менеджері ключів поза AWS.

## CloudHSM: власний апаратний модуль {#cloudhsm}

**AWS CloudHSM** — **виділений** (single-tenant) апаратний модуль безпеки у **твоїй VPC**. Відмінність від KMS — у контролі:

| | AWS KMS | AWS CloudHSM |
|---|---|---|
| Хто володіє модулем | Спільні модулі AWS (multi-tenant) | Виділений модуль лише для тебе |
| Хто керує ключами й користувачами HSM | AWS керує модулями, ти — політиками ключів | **Лише ти**; AWS не має доступу до ключів |
| Інтеграція з сервісами AWS | Нативна з сотнею сервісів | Через KMS custom key store або напряму з застосунку |
| Стандартні API | API KMS | **PKCS#11, JCE, Microsoft CNG** — для наявного ПЗ |
| Висока доступність | Вбудована | Сам будуєш кластер з **2+ HSM у різних AZ** |
| Коли обирати | Майже завжди | Вимоги регулятора до **виділеного** HSM під повним контролем клієнта (FIPS 140 Level 3), SSL/TLS offload, Oracle TDE, власний центр сертифікації |

## Сертифікати: AWS Certificate Manager {#acm}

**ACM** видає **безкоштовні публічні TLS-сертифікати** і **автоматично поновлює** їх (для доменів, підтверджених через DNS) — жодних прострочених сертифікатів, як торік у Хмаринці. Сертифікат ACM ставиться на **інтегровані сервіси**: **Elastic Load Balancing**, **CloudFront**, **API Gateway** (а також App Runner, Amplify тощо).

Правила, які перевіряє іспит:

- для **CloudFront** сертифікат має бути створений у регіоні **us-east-1** (Північна Вірджинія), бо CloudFront — глобальний сервіс; для балансувальника — у регіоні самого балансувальника;
- класичне правило: публічний сертифікат ACM **не встановлюють прямо на EC2** — TLS завершують на балансувальнику чи CloudFront (з 2025 року ACM вміє видавати платні експортовані сертифікати, але на іспиті діє класика);
- **імпортовані** в ACM сторонні сертифікати ACM **не поновлює** — стеж за строком (події ACM в EventBridge, правило AWS Config про строк дії).

Для **внутрішніх** сервісів (мікросервіси всередині VPC, взаємна TLS-автентифікація) є **AWS Private CA** — власний приватний центр сертифікації.

## Секрети: Secrets Manager чи Parameter Store {#secrets}

Паролі до баз, ключі API партнерів, токени — **секрети**. Їх не можна тримати в коді, конфігураційних файлах чи змінних середовища відкритим текстом. Два сервіси:

| | **AWS Secrets Manager** | **SSM Parameter Store** |
|---|---|---|
| Для чого | Секрети, які треба **регулярно міняти** | Конфігурація і секрети без вимоги ротації |
| **Автоматична ротація** | **Так**: вбудована для RDS, Aurora, Redshift, DocumentDB; для інших — через функцію Lambda | Вбудованої немає |
| Шифрування | KMS | SecureString — KMS |
| Реплікація в інші регіони | Так | Ні |
| Політики доступу на самому секреті | Так (resource-based) | Лише IAM |
| Ціна | Плата за кожен секрет на місяць + запити | Standard-параметри безкоштовні; Advanced — платні (більший розмір, політики строку дії) |
| Зручності | Інтеграція з RDS (пароль майстер-користувача керується автоматично) | Ієрархія `/shop/prod/db-url`, версії, простий доступ з EC2, Lambda, ECS |

Правило вибору на іспиті: «**rotate automatically**» → **Secrets Manager**. «Cheapest way to store configuration / connection strings», ротація не згадується → **Parameter Store**.

## Як шифрують дані основні сервіси {#at-rest}

### Amazon S3

| Варіант | Хто керує ключем | Коли |
|---|---|---|
| **SSE-S3** | S3 (AES-256) | **Типово для всіх нових об'єктів з 2023 року** — нічого налаштовувати не треба |
| **SSE-KMS** | KMS (AWS managed або customer managed key) | Потрібен **аудит використання ключа** в CloudTrail, окремий контроль доступу до ключа, власна ротація |
| **DSSE-KMS** | KMS, два шари шифрування | Вимоги до двошарового шифрування |
| **SSE-C** | Клієнт надсилає ключ у кожному запиті, AWS його не зберігає | Ключі мають бути лише в клієнта; **тільки HTTPS** |
| **Client-side** | Клієнт шифрує до завантаження | S3 взагалі не бачить відкритих даних |

Примусити HTTPS для bucket — bucket policy з **Deny**, якщо `aws:SecureTransport` = `false`. Примусити конкретний ключ KMS — Deny на `s3:PutObject`, якщо в запиті інший тип шифрування або інший ключ.

### EBS, RDS, знімки

- **EBS:** увімкни **encryption by default** для регіону — усі нові диски шифруватимуться автоматично. Шифруються і диск, і знімки, і трафік між сервером і диском.
- **RDS / Aurora:** шифрування вмикається **лише при створенні** бази. Для наявної незашифрованої — **знімок → копія знімка з шифруванням → відновлення** з копії. Read replica має той самий стан шифрування, що й основна база.
- **Наявний незашифрований EBS-диск** — так само: знімок → копія з шифруванням → новий диск.
- **Поділитися зашифрованим знімком з іншим акаунтом** можна, лише якщо він зашифрований **customer managed key** (і той акаунт отримав доступ до ключа). Знімок з AWS managed key спершу копіюють, перешифрувавши своїм ключем.
- **DynamoDB** шифрує всі таблиці за замовчуванням (вибір — ключ AWS, AWS managed або customer managed).

:::example 🧩 Рішення для Хмаринки
- База замовлень (RDS) — створюється **зашифрованою** customer managed key `khmarynka-data`; стару незашифровану переносимо через копію знімка.
- Пароль до бази — у **Secrets Manager** з ротацією кожні 30 днів; застосунок читає його через роль, а не з файлу. Старий пароль, що «засвітився» в git, — одразу змінюємо.
- Фото — **SSE-S3** (достатньо); рахунки й договори — **SSE-KMS** з **Bucket Keys** (аудит доступу до ключа).
- HTTPS — сертифікат **ACM** на балансувальнику (регіон eu-central-1) і на CloudFront (**us-east-1**), поновлення автоматичне.
- Юристу — звіт із CloudTrail про використання ключа `khmarynka-data`.
:::

:::lab 🧪 Спробуй у справжньому AWS: секрет у Parameter Store і конверт KMS
**Вартість:** Parameter Store (Standard) — безкоштовно; ключ KMS — кілька центів за день існування. **Час:** 20 хвилин.
1. **CloudShell** → збережи зашифрований параметр (використає безкоштовний AWS managed key `aws/ssm`):
```bash
aws ssm put-parameter --name /khmarynka/dev/db-password --type SecureString --value "S3cret-Test-123"
aws ssm get-parameter --name /khmarynka/dev/db-password
aws ssm get-parameter --name /khmarynka/dev/db-password --with-decryption
```
Без `--with-decryption` бачиш шифротекст, з ним — пароль (бо маєш права на ключ).
2. **KMS** → **Customer managed keys** → **Create key** → Symmetric, Encrypt and decrypt → alias `khmarynka-lab` → адміністратор і користувач ключа — твій адміністратор → Finish.
3. Envelope encryption вручну:
```bash
aws kms generate-data-key --key-id alias/khmarynka-lab --key-spec AES_256 --query CiphertextBlob --output text > datakey.enc
wc -c datakey.enc
aws kms encrypt --key-id alias/khmarynka-lab --plaintext fileb://<(echo -n "Адреса клієнта") --query CiphertextBlob --output text
```
Перша команда отримала зашифрований ключ даних («конверт»), друга — зашифрувала короткий текст прямо в KMS (до 4 KB).
4. **CloudTrail → Event history**: знайди події `GenerateDataKey` і `Encrypt` — хто і коли використовував ключ.
**Прибери за собою:** `aws ssm delete-parameter --name /khmarynka/dev/db-password`; KMS → ключ `khmarynka-lab` → **Key actions → Schedule key deletion** → 7 днів; `rm datakey.enc`.
:::

#### 💡 Запам'ятай

- Шифруємо **at rest** (KMS) і **in transit** (TLS) — це дві окремі вимоги.
- **KMS:** регіональні ключі в HSM, інтеграція з сервісами, аудит у CloudTrail. Типи: AWS owned, AWS managed (щорічна ротація), **customer managed** (свій контроль, ротація 90–2560 днів або вручну).
- **Key policy** — головний контроль доступу до ключа; для іншого акаунта — дозвіл у key policy + IAM.
- `Encrypt` — до **4 KB**; більше — **envelope encryption** (GenerateDataKey).
- **Multi-Region keys** — один ключ у кількох регіонах. **Видалення** — через 7–30 днів очікування.
- Масові SSE-KMS і `ThrottlingException` → **S3 Bucket Keys**.
- **CloudHSM** — виділений HSM, повний контроль клієнта, PKCS#11/JCE/CNG, кластер у 2+ AZ.
- **ACM** — безкоштовні сертифікати з автопоновленням; для CloudFront — **us-east-1**; імпортовані не поновлюються.
- **Secrets Manager** — ротація; **Parameter Store** — дешева конфігурація без ротації.
- Наявні незашифровані RDS/EBS → **знімок → копія з шифруванням → відновлення**.

#### 🎯 Як питають на іспиті

- Аудит, хто і коли використовував ключ шифрування даних S3 → **SSE-KMS (виклики ключа в CloudTrail)**
- Ключі під виключним контролем клієнта в апаратному модулі, AWS не має доступу → **AWS CloudHSM**
- Автоматично змінювати пароль до бази кожні 30 днів → **AWS Secrets Manager з ротацією**
- Найдешевше зберігати рядки підключення і конфігурацію без ротації → **SSM Parameter Store**
- HTTPS для ALB чи CloudFront без ручного поновлення сертифікатів → **AWS Certificate Manager**
- Сертифікат ACM для CloudFront «не видно» при налаштуванні → **сертифікат треба створити в us-east-1**
- Шифрувати в одному регіоні й розшифровувати в іншому тим самим ключем → **KMS Multi-Region keys**
- ThrottlingException від KMS при масовому завантаженні в S3 з SSE-KMS → **S3 Bucket Keys**
- Зашифрувати наявну незашифровану базу RDS → **знімок → копія з шифруванням → відновлення**
- Зашифрувати файл 50 МБ ключем KMS → **envelope encryption (data key)**
- Поділитися зашифрованим знімком RDS з іншим акаунтом → **customer managed key + дозвіл на ключ для того акаунта**
- Ключ KMS випадково запланували на видалення → **скасувати видалення до кінця періоду очікування**
- Усі нові диски EBS в регіоні мають бути зашифровані → **EBS encryption by default**

#### ⚠️ Пастки

- На наявних RDS чи EBS не можна просто «увімкнути шифрування» — лише через копію знімка.
- AWS managed key не можна використати для обміну знімками з іншим акаунтом і не можна змінити його політику.
- Parameter Store не має вбудованої ротації — якщо в питанні «rotate», це Secrets Manager.
- SSE-C працює лише через HTTPS, і якщо загубиш ключ — даних не повернеш.
- Видалений ключ KMS = назавжди втрачені дані, зашифровані ним. Спершу — disable.

## ✅ Перевір себе

:::quiz
? Регулятор вимагає журнал кожного використання ключа, яким шифруються документи клієнтів у S3, і окремий контроль, хто може цим ключем користуватися. Яке шифрування обрати?
- SSE-S3
+ SSE-KMS з customer managed key
- SSE-C
- Шифрування не потрібне, бо S3 і так надійний
= SSE-KMS записує кожне використання ключа в CloudTrail, а customer managed key дає власну key policy — хто може шифрувати й розшифровувати. SSE-S3 не дає окремого аудиту й контролю ключа, SSE-C перекладає керування ключами на клієнта.

? Компанія має незашифровану базу Amazon RDS for MySQL у продакшні. Як її зашифрувати?
- Увімкнути опцію шифрування в налаштуваннях бази без зупинки
+ Зробити знімок, скопіювати його з увімкненим шифруванням і відновити нову базу з копії
- Створити зашифровану read replica і більше нічого не робити
- Увімкнути шифрування EBS за замовчуванням у регіоні
= Шифрування RDS задається лише при створенні. Шлях для наявної бази — знімок → копія з шифруванням → відновлення нової зашифрованої бази й перемикання застосунку. Read replica незашифрованої бази теж буде незашифрованою.

? Застосунок використовує пароль до Amazon Aurora, який має автоматично змінюватися кожні 30 днів без зміни коду й без простою. Що обрати?
+ AWS Secrets Manager з увімкненою ротацією
- SSM Parameter Store SecureString
- Змінну середовища на сервері
- Customer managed key у KMS
= Secrets Manager має вбудовану автоматичну ротацію для Aurora і RDS. Parameter Store не вміє ротувати сам, а KMS керує ключами шифрування, а не паролями баз.

? Архітектор налаштовує HTTPS для CloudFront з власним доменом, але не бачить свого сертифіката ACM у списку. Сертифікат створено в eu-central-1. У чому причина?
- ACM не підтримує CloudFront
+ Для CloudFront сертифікат ACM має бути в регіоні us-east-1
- Потрібно імпортувати сертифікат у CloudFront вручну через CLI
- Сертифікат ще не прострочився
= CloudFront — глобальний сервіс і використовує сертифікати ACM лише з us-east-1. Для балансувальника сертифікат має бути в регіоні балансувальника.

? Потрібно шифрувати ключем KMS файли розміром від 10 до 500 МБ. Як це робиться?
- Викликати KMS Encrypt для кожного файлу цілком
+ Отримати ключ даних через GenerateDataKey, зашифрувати ним файл локально і зберегти поруч зашифрований ключ даних
- Розбити файл на частини по 4 KB і шифрувати кожну через KMS
- Використати хешування SHA-256 замість шифрування
= KMS Encrypt приймає до 4 KB. Великі дані шифрують через envelope encryption: ключ даних від KMS шифрує файл локально, а сам ключ даних зберігається зашифрованим ключем KMS.

? Фінансова компанія за вимогою регулятора має використовувати виділений апаратний модуль безпеки, де лише вона керує ключами, а також інтегрувати його з наявним ПЗ через PKCS#11. Що обрати?
- AWS KMS з AWS managed keys
+ AWS CloudHSM
- AWS Secrets Manager
- AWS Certificate Manager
= CloudHSM — виділений (single-tenant) HSM у VPC клієнта: ключі й користувачі під повним контролем клієнта, стандартні інтерфейси PKCS#11, JCE, CNG. Для HA — кластер з кількох HSM у різних AZ.

? Масове завантаження мільйонів об'єктів у S3 з SSE-KMS завершується помилками ThrottlingException. Як найпростіше це виправити?
- Перейти на SSE-C
+ Увімкнути S3 Bucket Keys
- Створити окремий ключ KMS для кожного об'єкта
- Вимкнути шифрування на час завантаження
= S3 Bucket Keys зменшують кількість запитів до KMS у рази: S3 отримує ключ рівня bucket і сам генерує з нього ключі для об'єктів. Це прибирає тротлінг і знижує вартість.
:::
