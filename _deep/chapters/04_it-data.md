> 🎬 **Історія Хмаринки.** Бухгалтерка Марта веде облік замовлень в Excel-таблиці, яку щодня пересилає поштою. Фото товарів лежать у папці «Фото_НОВІ_остаточні_2», а база сайту — на тому самому сервері в підсобці. Коли Тарас каже: «Замовлення зберігаємо в реляційній базі, фото — в об'єктному сховищі, сесії — в кеші, а паролі — лише хешовані», — Олена просить перекласти це людською мовою. Цей розділ — саме такий переклад. Без нього не зрозуміти половину сервісів AWS.

> 🖼️ **Образ.** Уяви три способи зберігати речі. **Блочне сховище** — порожні полиці, які ти розставляєш як хочеш (диск: розмітиш і впорядкуєш сам). **Файлове сховище** — бібліотека з каталогом, папками і полицями, куди одночасно заходять багато читачів. **Об'єктне сховище** — величезний склад: здаєш коробку, отримуєш номерок, а по номерку будь-коли її забираєш; що всередині — склад не цікавить. Бази даних — це вже не склад, а **картотека з розумним бібліотекарем**, який за секунду знайде «всі замовлення Олени за березень дорожчі за 500 гривень».

## Які бувають дані

- **Структуровані** — таблиці з чіткими колонками: замовлення (номер, дата, клієнт, сума), клієнти, товари. Живуть у реляційних базах.
- **Напівструктуровані** — мають структуру, але гнучку: JSON, XML, CSV, логи. Кожен запис може мати різні поля.
- **Неструктуровані** — фото, відео, аудіо, PDF, скани. Їх не розкладеш по колонках, їх зберігають як файли чи об'єкти.

Хмаринка має всі три: замовлення (структуровані), події з сайту в JSON (напівструктуровані), фото товарів (неструктуровані). Для кожного типу — свій найкращий сервіс.

Порівняймо детальніше:

| | Блочне | Файлове | Об'єктне |
|---|---|---|---|
| Як виглядає | Диск (том) | Дерево папок і файлів | Плоский простір «ключ → об'єкт» |
| Хто підключає | Зазвичай один сервер | Багато серверів одночасно | Будь-хто через HTTP з правами |
| Зміна частини даних | Так, будь-який блок | Так, частину файла | Ні: об'єкт замінюють цілком |
| Обсяг | Обмежений розміром тому | Росте до петабайтів | Практично необмежений |
| Типові дані | ОС, бази даних | Спільні документи, контент для кількох серверів | Фото, відео, бекапи, логи, дата-лейк |
| AWS | EBS, instance store | EFS (NFS), FSx (SMB, Lustre, ONTAP, OpenZFS) | S3 |

:::note 📌 Протоколи файлового доступу
**NFS** — «мова» спільних папок у Linux. **SMB** — у Windows (мережеві диски на кшталт `\\server\share`). **iSCSI** — диск по мережі: сервер бачить віддалене сховище як свій локальний блочний диск. Ці три слова на іспиті одразу підказують сервіс: NFS для Linux у кількох зонах → Amazon EFS; SMB з Active Directory → FSx for Windows File Server.
:::

## Бази даних

Чому не зберігати замовлення просто у файлі? Бо коли тисяча покупців одночасно оформлює замовлення, файл треба блокувати, шукати в ньому повільно, а збій посеред запису зіпсує дані. **База даних (БД)** — спеціальна програма, що вміє швидко шукати, безпечно змінювати дані паралельно і не губити їх при збоях.

### Реляційні бази (SQL)

Дані лежать у **таблицях** з рядками і колонками. Кожен рядок має унікальний **первинний ключ** (primary key). Таблиці пов'язані між собою **зовнішніми ключами**: у таблиці «Замовлення» є колонка «id клієнта», що вказує на рядок у таблиці «Клієнти».

Мова запитів — **SQL**:

```sql
SELECT c.name, o.total
FROM orders o JOIN customers c ON o.customer_id = c.id
WHERE o.created_at >= '2026-03-01' AND o.total > 500;
```

Головна суперсила реляційних баз — **транзакції** з гарантіями **ACID**:

- **Atomicity** (атомарність): усі кроки транзакції виконуються разом або жоден. Списали гроші — обов'язково створили замовлення; якщо щось зламалося — відкат усього.
- **Consistency** (узгодженість): дані завжди відповідають правилам (не буде замовлення неіснуючого клієнта).
- **Isolation** (ізоляція): паралельні транзакції не заважають одна одній.
- **Durability** (довговічність): підтверджене — не загубиться навіть при збої.

Популярні рушії: **MySQL, PostgreSQL, MariaDB, Oracle, Microsoft SQL Server**. В AWS — Amazon RDS і Amazon Aurora ([розділи 34–35](#ch/rds)).

### NoSQL-бази

Реляційні бази чудові, але мають межі: жорстка схема (змінити колонки у величезній таблиці складно), а масштабувати запис на мільйони операцій за секунду важко. **NoSQL** — сімейство баз, що жертвують частиною можливостей (складні JOIN) заради швидкості, масштабу або особливої моделі даних:

| Тип | Як зберігає | Для чого | AWS |
|---|---|---|---|
| **Key-value** | Ключ → значення | Кошики, сесії, профілі, лічильники — мільйони запитів за секунду | DynamoDB |
| **Документна** | JSON-документи | Каталоги, контент із різною структурою | DocumentDB (MongoDB-сумісна) |
| **Графова** | Вузли і зв'язки | Соцмережі, рекомендації, пошук шахрайських зв'язків | Neptune |
| **Широкі колонки** | Рядки з гнучкими колонками | Величезні обсяги запису (Cassandra) | Keyspaces |
| **Часові ряди** | Значення з мітками часу | Метрики, IoT-датчики | Timestream |
| **У пам'яті** | Усе в RAM | Кеш, лідерборди, сесії — мікросекунди | ElastiCache, MemoryDB |

Правило вибору просте: **спершу подивись на запити**. Потрібні складні JOIN, звіти, транзакції між багатьма таблицями → реляційна. Відомі прості запити «за ключем», гігантський масштаб, мілісекунди → key-value. Зв'язки «друзі друзів» → графова.

### OLTP і OLAP: касир і аналітик

- **OLTP** (online transaction processing) — багато маленьких швидких операцій: оформити замовлення, змінити адресу. Це «касир». Реляційні бази (RDS, Aurora) і DynamoDB.
- **OLAP** (online analytical processing) — рідкісні, але важкі запити по мільйонах рядків: «виручка по регіонах за три роки». Це «аналітик». Для OLAP дані зберігають **по колонках** — запит читає лише потрібні колонки. Це **сховище даних** (data warehouse) — в AWS **Redshift**.
- **Data lake** (озеро даних) — усі сирі дані компанії в дешевому об'єктному сховищі (S3) у різних форматах, з яких потім будують аналітику. Формати на кшталт **Parquet** зберігають дані по колонках і стиснено — запити по них у рази дешевші.

Ніколи не запускай важку аналітику на основній OLTP-базі: звіт Марти не повинен гальмувати оформлення замовлень. Для цього є репліки для читання, окремі сховища даних і озера даних.

## Кеш: пам'ять, що економить час

**Кеш** — швидке тимчасове сховище для даних, які часто читають. Каталог товарів Хмаринки змінюється раз на день, а читають його тисячі разів на хвилину — навіщо щоразу питати базу?

- **Cache hit** — відповідь знайшлася в кеші (швидко). **Cache miss** — не знайшлася, йдемо в базу і кладемо результат у кеш.
- **TTL** — скільки часу запис живе в кеші. Задовгий TTL — ризик показати застарілі дані; закороткий — менше користі.
- Кеші бувають скрізь: у браузері, на **CDN** біля користувачів (CloudFront), у пам'яті перед базою (ElastiCache, DAX).

## Синхронно чи асинхронно: черги і події

- **Синхронна** взаємодія: «подзвонив — чекаєш відповіді». Сайт викликає платіжний сервіс і чекає результат.
- **Асинхронна**: «залишив записку — працюєш далі». Сайт кладе замовлення в **чергу**, а склад забирає звідти, коли встигає.

Черга розв'язує (decouples) компоненти: якщо склад на годину впав, замовлення не губляться — вони чекають у черзі. А під час розпродажу черга працює як буфер: сайт приймає тисячі замовлень, склад обробляє їх у своєму темпі. Модель **pub/sub** (публікація — підписка): одна подія «нове замовлення» розсилається всім зацікавленим — складу, бухгалтерії, email-сервісу. В AWS: SQS, SNS, EventBridge ([розділи 31–32](#ch/sqs-sns)).

## API: як програми розмовляють між собою {#api}

**API** (application programming interface) — «меню», через яке одна програма замовляє щось в іншої. Мобільний застосунок Хмаринки не лізе в базу напряму, а викликає API: `GET https://api.khmarynka.ua/orders/1042`. Сервер відповідає даними, найчастіше у форматі **JSON**:

```json
{
  "orderId": 1042,
  "status": "shipped",
  "total": 780.50,
  "items": [ { "sku": "MUG-01", "qty": 2 } ],
  "customer": { "name": "Ірина", "city": "Варшава" }
}
```

- **REST API** — найпоширеніший стиль: ресурси мають адреси (URL), дії — HTTP-методи (GET, POST, PUT, DELETE).
- **Автентифікація API**: ключі API, токени (наприклад, JWT), підписані запити.
- **Throttling** (обмеження частоти) захищає API від перевантаження: «не більше 100 запитів за секунду з одного ключа» — інакше код 429.

Уся AWS — це тисячі API. Коли ти натискаєш кнопку в консолі AWS, вона викликає API. Командний рядок (AWS CLI), SDK для мов програмування, інструменти «інфраструктура як код» — усе це різні способи викликати ті самі API. Тому кожну дію в AWS можна автоматизувати і **записати в журнал** (CloudTrail, [розділ 41](#ch/monitoring)).

## Бекап і реплікація: дві різні страховки

- **Бекап (резервна копія)** — знімок даних на певний момент, збережений окремо. Захищає від **помилок і атак**: випадково видалили таблицю, вірус-шифрувальник — відновлюєшся з учорашньої копії.
- **Реплікація** — постійне копіювання змін на іншу машину. Захищає від **відмови обладнання**: основна база впала — копія вже готова.

Реплікація буває:

- **синхронною** — запис вважається успішним, лише коли його підтвердили обидві копії. Даних не втратиш, але кожен запис трохи довший (тому копії ставлять неподалік — у сусідніх дата-центрах);
- **асинхронною** — основна копія підтверджує запис одразу, а на репліку він доходить із затримкою. Швидко і можна далеко (в інший регіон), але при аварії останні секунди змін можуть загубитися.

Важливо: реплікація **копіює і помилки**. Якщо хтось видалив таблицю, репліка слухняно видалить її теж. Тому реплікація не замінює бекапи.

Два числа, з яких починається будь-яка розмова про аварії:

- **RPO** (Recovery Point Objective) — скільки даних (за часом) можна втратити. RPO = 1 година → бекап щонайменше щогодини.
- **RTO** (Recovery Time Objective) — за скільки часу система має знову запрацювати.

Детально — у [розділі 42](#ch/resilience).

## Шифрування і хешування {#crypto}

**Шифрування** перетворює дані на «кашу», яку можна повернути назад лише з **ключем**.

- **Симетричне** — один ключ шифрує і розшифровує (алгоритм **AES-256**). Швидке, ідеальне для великих обсягів даних. Проблема — як безпечно передати ключ.
- **Асиметричне** — пара ключів: **публічний** (можна роздавати всім) шифрує, **приватний** (тримаєш у секреті) розшифровує. Алгоритми RSA, ECC. Повільніше, але розв'язує проблему передачі ключа. Той самий принцип дає **цифровий підпис**: підписуєш приватним ключем — будь-хто перевіряє публічним.

HTTPS поєднує обидва: асиметричне шифрування використовується, щоб безпечно домовитися про симетричний ключ, а далі дані шифруються швидким симетричним.

Де шифрують дані:

- **In transit** (при передачі) — TLS/HTTPS, VPN. Захищає від підслуховування в мережі.
- **At rest** (при зберіганні) — шифровані диски, бази, об'єкти. Захищає, якщо хтось отримає доступ до носія чи копії.

Найважче в шифруванні — **керування ключами**: де зберігати, хто має доступ, як міняти (ротація), як не загубити. В AWS для цього є **KMS** ([розділ 11](#ch/encryption)).

**Хешування** — інша річ. Хеш-функція (наприклад, **SHA-256**) перетворює будь-які дані на «відбиток» фіксованої довжини, і **назад повернути неможливо**. Зміни одну літеру — отримаєш зовсім інший відбиток. Навіщо:

- **паролі** зберігають не відкритими і не зашифрованими, а **хешованими** (з «сіллю»): навіть якщо базу вкрадуть, паролів там немає;
- **цілісність**: порівнявши хеші, легко перевірити, що файл не змінився при передачі.

:::mnemo 🧠 Шифрування чи хеш?
**Шифрування** — сейф: поклав, зачинив ключем, відчинив ключем. **Хеш** — м'ясорубка: з фаршу котлету назад не зробиш, але з того самого м'яса завжди вийде той самий фарш.
:::

## Автентифікація і авторизація

- **Автентифікація (authentication)** — «хто ти?»: логін і пароль, відбиток пальця, токен.
- **Авторизація (authorization)** — «що тобі можна?»: читати замовлення можна, видаляти — ні.

**MFA** (багатофакторна автентифікація) вимагає двох різних факторів: щось, що ти **знаєш** (пароль), щось, що ти **маєш** (телефон із кодом, ключ безпеки), щось, чим ти **є** (відбиток). Украдений пароль без другого фактора марний. **Федерація** і **SSO** (єдиний вхід) — коли за тебе ручається інша система: «увійти через Google» або корпоративний каталог співробітників. Усе це в AWS — модуль про безпеку, починаючи з [розділу 8](#ch/iam).

:::lab 🧪 Спробуй: справжній JSON від AWS і хеш своїми руками
**Вартість:** безкоштовно, акаунт AWS не потрібен. **Час:** 10 хвилин.
1. Відкрий у браузері `https://ip-ranges.amazonaws.com/ip-ranges.json` — це публічний JSON з усіма діапазонами IP-адрес AWS. Знайди (Ctrl + F) `eu-central-1` — побачиш CIDR-діапазони Франкфурта і назви сервісів. Так виглядає реальний API-відповідь.
2. Створи текстовий файл `test.txt` зі словом «Хмаринка».
3. Порахуй його хеш SHA-256. Windows: `certutil -hashfile test.txt SHA256`. macOS/Linux: `shasum -a 256 test.txt`.
4. Зміни одну літеру у файлі й порахуй ще раз — відбиток зміниться повністю. Поверни літеру — повернеться і старий відбиток.
5. Клацни замочок на будь-якому HTTPS-сайті → сертифікат: знайди, хто його видав (CA) і до якої дати він дійсний.
**Прибери:** видали `test.txt`.
:::

#### 💡 Запам'ятай

- **Блочне** (EBS) — диск одного сервера; **файлове** (EFS, FSx) — спільні папки для багатьох; **об'єктне** (S3) — необмежений склад через HTTP.
- **Реляційні** бази — таблиці, SQL, JOIN, транзакції ACID (RDS, Aurora). **NoSQL** — масштаб і швидкість для простих запитів (DynamoDB) та спеціальні моделі (графи, документи, часові ряди).
- **OLTP** — багато дрібних транзакцій; **OLAP** — важка аналітика в сховищі даних (Redshift).
- **Кеш** прискорює повторні читання; TTL — баланс між свіжістю і швидкістю.
- **Черга** розв'язує компоненти і згладжує піки.
- **Бекап** — від помилок і атак; **реплікація** — від відмов (синхронна — без втрат поруч, асинхронна — далеко з можливою втратою останніх змін).
- Шифрування **in transit** (TLS) і **at rest** (KMS); **хеш** — одностороння функція для паролів і цілісності.
- Автентифікація — «хто ти», авторизація — «що можна»; MFA — два різні фактори.

#### 🎯 Як питають на іспиті

- Зберігати мільйони фото, відео чи бекапів дешево і надійно, доступ через інтернет → **об'єктне сховище (Amazon S3)**
- Спільна файлова система для багатьох Linux-серверів → **файлове сховище по NFS (Amazon EFS)**
- Диск для бази даних на одному сервері з максимальною швидкістю → **блочне сховище (Amazon EBS)**
- Складні запити з JOIN і транзакції → **реляційна база (RDS / Aurora)**, а не key-value
- Мілісекундні відповіді на мільйони простих запитів за ключем, гнучка схема → **NoSQL key-value (DynamoDB)**
- Важкі аналітичні звіти гальмують основну базу → **винести аналітику в окреме сховище даних (Redshift) або на репліку**
- Компоненти мають не губити повідомлення, якщо один із них тимчасово недоступний → **черга між ними (асинхронна взаємодія)**

#### ⚠️ Пастки

- S3 — не диск: його не «монтують» під базу даних і не змінюють частину об'єкта.
- Реплікація не замінює бекапи: випадкове видалення реплікується миттєво.
- Хеш не можна «розшифрувати»; шифрування — можна (з ключем). Паролі зберігають хешованими, а не зашифрованими.
- Асинхронна репліка може не мати останніх змін — при аварії можлива невелика втрата даних.

## ✅ Перевір себе

:::quiz
? Хмаринці треба зберігати 2 мільйони фото товарів, які показуються на сайті й у мобільному застосунку. Обсяг постійно росте. Який тип сховища найкраще підходить?
- Блочне сховище, підключене до вебсервера
- Файлове сховище, змонтоване на кожному сервері
+ Об'єктне сховище з доступом через HTTP
- Реляційна база даних з колонкою для фото
= Фото — неструктуровані дані, які читають застосунки й браузери через інтернет. Об'єктне сховище (S3) практично необмежене, дуже надійне, дешеве і доступне по HTTP. Зберігати великі файли в реляційній базі — повільно й дорого.

? Кілька Linux-серверів у різних дата-центрах мають одночасно читати й записувати ті самі файли як у звичайній папці. Що обрати?
- Блочний диск, підключений до одного сервера
+ Файлове сховище з доступом по NFS
- Об'єктне сховище без монтування
- Кеш у пам'яті
= Спільний одночасний доступ багатьох серверів до файлів як до папки — це файлове сховище. Для Linux протокол — NFS (в AWS — Amazon EFS). Блочний диск зазвичай підключають до одного сервера.

? Банківський переказ має або повністю виконатися (списання й зарахування), або не виконатися зовсім. Яка властивість бази даних це гарантує?
+ Atomicity (атомарність) з ACID
- Eventual consistency
- Горизонтальне масштабування
- TTL у кеші
= Атомарність гарантує, що всі кроки транзакції виконуються разом або жоден. Це частина гарантій ACID, якими славляться реляційні бази.

? Чим хешування відрізняється від шифрування?
- Хешування використовує публічний і приватний ключі
+ Хеш не можна повернути до вихідних даних, а зашифровані дані можна розшифрувати ключем
- Хешування швидше, тому ним захищають дані на дисках
- Різниці немає, це синоніми
= Хеш — одностороння функція: відбиток даних, з якого не відновити оригінал. Тому ним зберігають паролі та перевіряють цілісність. Шифрування оборотне — з правильним ключем дані розшифровуються.

? Основна база реплікується в інший регіон асинхронно. Що може статися при раптовій аварії основної бази?
- Нічого: асинхронна репліка завжди має всі дані
+ Останні зміни, які ще не встигли дійти до репліки, можуть загубитися
- Репліка автоматично стане синхронною
- Дані на репліці будуть зашифровані іншим ключем
= При асинхронній реплікації основна база підтверджує запис одразу, а на репліку він доходить із затримкою. Якщо аварія станеться в цей проміжок, останні зміни загубляться. Це і є ненульовий RPO.

? Звіт бухгалтерії з підсумками за три роки виконується годину і сповільнює оформлення замовлень на сайті. Що змінити в архітектурі?
- Додати в основну базу більше колонок
+ Виконувати аналітику окремо від транзакційної бази — у сховищі даних або на репліці для читання
- Перенести замовлення в кеш
- Вимкнути транзакції в основній базі
= OLTP-база (замовлення) і OLAP-навантаження (важкі звіти) заважають одне одному. Аналітику виносять на репліку для читання або в окреме сховище даних з колонковим зберіганням (Redshift).
:::
