> 🎬 **Історія Хмаринки.** Коли Тарас перевірив старий сервер з підсобки, волосся стало дибки: у нього була публічна IP-адреса, і з інтернету були відкриті не лише сайт, а й **база даних** на порту 3306 і віддалений доступ. Будь-хто у світі міг стукати в базу замовлень — і, судячи з журналів, стукали щодня. У хмарі все буде інакше: база житиме в мережі, **куди з інтернету немає дороги взагалі**. Будуємо власну приватну мережу Хмаринки в AWS — **VPC**.

> 🖼️ **Образ.** **VPC** — огороджений житловий комплекс, твоя приватна територія в місті-регіоні. **Підмережі** — будинки комплексу. Будинки на **першій лінії** мають вихід на вулицю (публічні підмережі), будинки у **внутрішньому дворі** виходу на вулицю не мають (приватні). **Таблиця маршрутів** — вказівники у дворі: «до вулиці — туди». **Internet Gateway** — головна брама на вулицю. **NAT Gateway** — поштове відділення на першій лінії: мешканці внутрішніх будинків відправляють листи через нього й отримують відповіді, але сторонній з вулиці через пошту у двір не пройде.

## Що таке VPC {#what}

**Amazon VPC** (Virtual Private Cloud) — логічно ізольована мережа в AWS, яку ти повністю контролюєш: діапазон адрес, підмережі, маршрути, шлюзи, правила файрволів. Властивості:

- VPC живе в **одному регіоні**, але охоплює **всі його зони доступності**.
- Діапазон IPv4 задається в CIDR — від **/16** (65 536 адрес) до **/28** (16 адрес). Згодом можна додати додаткові діапазони. За бажанням — ще й IPv6.
- Різні VPC ізольовані одна від одної, навіть в одному акаунті. З'єднати їх можна лише явно ([розділ 15](#ch/vpc-connect)).

У кожному регіоні акаунта вже є **default VPC** (`172.31.0.0/16`) з публічною підмережею в кожній зоні — щоб новачок міг одразу запустити сервер з доступом з інтернету. Для реальних систем створюють **власні VPC** з продуманою структурою.

## Підмережі: будинки комплексу {#subnets}

**Підмережа (subnet)** — частина діапазону VPC, прив'язана до **однієї зони доступності**. Ресурси (сервери, бази, балансувальники) запускаються в підмережах. Щоб система пережила втрату зони, ставлять однакові підмережі в кількох зонах.

Нагадування з [розділу 3](#ch/it-networks/cidr): у кожній підмережі AWS резервує **5 адрес** — першу (адреса мережі), другу (маршрутизатор VPC), третю (DNS), четверту (запас) і останню. У `/24` доступно 251 адреса.

**Публічна чи приватна?** Назва підмережі нічого не означає. Підмережа **публічна**, якщо в її таблиці маршрутів є маршрут `0.0.0.0/0 → Internet Gateway`. Немає такого маршруту — **приватна**. Це визначення треба знати напам'ять.

## Таблиці маршрутів {#routes}

**Таблиця маршрутів** (route table) каже, куди відправляти трафік з підмережі. Кожна підмережа прив'язана рівно до однієї таблиці (якщо не прив'язати явно — до головної, main route table).

| Призначення (Destination) | Ціль (Target) | Значення |
|---|---|---|
| `10.0.0.0/16` | `local` | Трафік усередині VPC — є в кожній таблиці, прибрати не можна |
| `0.0.0.0/0` | `igw-…` | Усе інше — в інтернет через Internet Gateway (публічна підмережа) |
| `0.0.0.0/0` | `nat-…` | Усе інше — через NAT Gateway (приватна підмережа з виходом в інтернет) |
| `pl-… (S3)` | `vpce-…` | Трафік до S3 — через gateway endpoint |
| `192.168.0.0/16` | `vgw-…` / `tgw-…` | Трафік в офіс — через VPN або Transit Gateway |

Правило вибору маршруту — **найспецифічніший** (longest prefix match): для адреси `10.0.5.7` маршрут `10.0.0.0/16` (local) переможе `0.0.0.0/0`, бо `/16` точніший за `/0`.

## Internet Gateway: брама на вулицю {#igw}

**Internet Gateway (IGW)** — компонент, що з'єднує VPC з інтернетом. Він керований AWS, горизонтально масштабується і високодоступний — за нього не треба хвилюватися, і він безкоштовний. До VPC прикріплюється **один** IGW.

Щоб сервер був доступний з інтернету, потрібні **всі чотири** умови:

1. До VPC прикріплений **Internet Gateway**.
2. У таблиці маршрутів підмережі є маршрут **`0.0.0.0/0 → IGW`**.
3. Сервер має **публічну IPv4-адресу** (автоматичну або Elastic IP) чи IPv6.
4. **Security Group** і **Network ACL** дозволяють потрібний трафік.

Забудеш хоча б одне — «сервер не відповідає». На іспиті це улюблена задача на діагностику.

### Публічні адреси: автоматичні й Elastic IP

- **Автоматична публічна IPv4** — сервер у публічній підмережі може отримати її при запуску. Але вона **змінюється** після зупинки й запуску сервера.
- **Elastic IP (EIP)** — **статична** публічна IPv4, закріплена за акаунтом. Її можна перечепити на інший сервер (швидка заміна при збої). З лютого 2024 року **кожна публічна IPv4-адреса платна** (близько $0,005 на годину, ~$3,6 на місяць) — і використовувана, і «забута» в акаунті.
- **IPv6** — безкоштовні глобально унікальні адреси, NAT для них не потрібен.

## NAT Gateway: вихід в інтернет без входу {#nat}

Серверам застосунку в приватних підмережах іноді потрібно **виходити** в інтернет: завантажити оновлення ОС, викликати API платіжного партнера. Але **вхідних** з'єднань з інтернету бути не повинно. Для цього — **NAT Gateway**:

- **Класичний (zonal) NAT Gateway** створюється в **публічній** підмережі конкретної зони з Elastic IP. У таблицях маршрутів **приватних** підмереж: `0.0.0.0/0 → nat-…`.
- Трафік назовні виходить з адреси NAT, відповіді повертаються, а **нові з'єднання ззовні неможливі**.
- Керований AWS, масштабується до десятків Gbps, **без Security Groups** (їх налаштовують на серверах).
- **Платний**: за кожну годину роботи **і** за кожен оброблений гігабайт.
- Один NAT Gateway працює в **одній зоні**. Для високої доступності — **по NAT Gateway у кожній зоні**, і приватна підмережа кожної зони маршрутизується на «свій» NAT. Інакше при втраті зони з NAT інші зони втратять вихід в інтернет, а трафік між зонами ще й коштує грошей.

:::note 🆕 Regional NAT Gateway (з листопада 2025)
AWS додав **регіональний** режим NAT Gateway: один NAT на всю VPC, що сам розширюється на потрібні зони і не потребує публічної підмережі. Це спрощує мережу. Але на іспиті частіше зустрічається класична схема «**NAT Gateway у публічній підмережі кожної AZ**» — відповідай за нею, якщо в питанні не сказано інше.
:::

**NAT instance** — застарілий варіант: звичайний сервер EC2, що виконує роль NAT (треба вимкнути перевірку *Source/Destination check*). Дешевший, але ти сам відповідаєш за його доступність, масштабування й оновлення. На іспиті — майже завжди програє NAT Gateway, крім питань «найдешевше для тестового середовища, доступність не важлива».

**Egress-only Internet Gateway** — «NAT для IPv6»: сервери з IPv6 можуть виходити в інтернет, але ззовні з'єднання до них неможливі.

## DNS усередині VPC

Кожна VPC має вбудований DNS-резолвер AWS (**Route 53 Resolver**, адреса — база VPC плюс два, наприклад `10.0.0.2`). Два налаштування VPC: **enableDnsSupport** (резолвер увімкнено) і **enableDnsHostnames** (сервери отримують DNS-імена). Обидва потрібні для приватних DNS-зон і для interface endpoints.

Логіка рішень:

- **Три рівні** (публічний, застосунок, дані): кожен наступний рівень закритіший за попередній — це **глибокий захист** (defense in depth).
- **Дві зони** (для prod краще три): втрата зони не зупиняє магазин.
- **Діапазон з запасом:** `/16` на VPC і `/24` на підмережі — вистачить на роки. Між рівнями залишені «дірки» (`10.0.2–9`, `10.0.12–19`), щоб додати третю зону.
- **Без перетинів:** офіс Хмаринки має `192.168.1.0/24`, майбутня dev-VPC отримає `10.1.0.0/16`. Тоді їх можна буде з'єднати.

:::deep 🔬 Глибше: як VPC працює «під капотом»
VPC — повністю програмна мережа: немає фізичних комутаторів, які ти налаштовуєш. Кожен сервер має **мережевий інтерфейс (ENI)** з приватною IP-адресою в підмережі; AWS на рівні своєї інфраструктури (Nitro) доставляє пакети лише туди, куди дозволяють маршрути і правила. Тому в VPC немає broadcast-трафіку, а «підслухати» чужий трафік неможливо. «Маршрутизатор VPC» (друга адреса підмережі) — теж віртуальний, і саме він застосовує таблиці маршрутів. Internet Gateway виконує трансляцію адрес 1:1: сервер «думає», що має лише приватну адресу, а IGW підміняє її на публічну при виході в інтернет.
:::

#### 💡 Запам'ятай

- **VPC** — ізольована мережа в регіоні, охоплює всі AZ; CIDR від **/16 до /28**.
- **Підмережа** — в **одній AZ**; AWS резервує **5 адрес**.
- **Публічна підмережа** = маршрут `0.0.0.0/0 → Internet Gateway`. Приватна — без нього.
- Доступ з інтернету потребує: **IGW + маршрут + публічна IP + дозволи SG/NACL**.
- **NAT Gateway** — вихід в інтернет для приватних підмереж без вхідних з'єднань; стоїть у **публічній** підмережі; для HA — **по одному в кожній AZ**; платний за годину і гігабайт; без Security Groups.
- **Elastic IP** — статична публічна IPv4; усі публічні IPv4 платні.
- **Egress-only IGW** — вихідний доступ для IPv6.
- Найспецифічніший маршрут перемагає; маршрут `local` є завжди.

#### 🎯 Як питають на іспиті

- Сервери в приватній підмережі мають завантажувати оновлення з інтернету, але бути недоступними ззовні → **NAT Gateway у публічній підмережі + маршрут 0.0.0.0/0 → NAT у приватній**
- Архітектура має пережити втрату AZ, а приватні сервери — не втратити інтернет → **NAT Gateway у кожній AZ з окремими таблицями маршрутів**
- Сервер у публічній підмережі не доступний з інтернету, хоча має публічну IP → **перевір маршрут до IGW, Security Group і NACL**
- Постійна публічна адреса, яку можна швидко перенести на інший сервер → **Elastic IP**
- IPv6-сервери мають виходити в інтернет, але бути недоступними ззовні → **Egress-only Internet Gateway**
- Найдешевший вихід в інтернет для тестового середовища, доступність не важлива → **одна NAT Gateway на всю VPC (або NAT instance)**
- Великий рахунок за NAT Gateway, бо сервери качають багато даних з S3 → **gateway VPC endpoint для S3**
- Скільки адрес доступно в підмережі /24 → **251**

#### ⚠️ Пастки

- NAT Gateway ставлять у **публічну** підмережу, а маршрут на нього прописують у таблиці **приватної**.
- Підмережа — в **одній** AZ, а не в кількох.
- Назва «public-subnet» нічого не гарантує — вирішує таблиця маршрутів.
- Автоматична публічна IP змінюється після stop/start — для постійної адреси потрібен Elastic IP.
- NAT Gateway не має Security Group і не пропускає вхідні з'єднання з інтернету.

## ✅ Перевір себе

:::quiz
? Що робить підмережу в VPC публічною?
- Назва підмережі містить слово public
+ Її таблиця маршрутів має маршрут 0.0.0.0/0 на Internet Gateway
- Вона розташована в першій зоні доступності регіону
- Вона має діапазон адрес /24

? Сервери застосунку в приватних підмережах двох AZ мають звертатися до API платіжного партнера в інтернеті. Потрібна висока доступність. Яке рішення правильне?
- Одна NAT Gateway у приватній підмережі AZ a
- Internet Gateway у кожній приватній підмережі

- Elastic IP на кожному сервері застосунку
= NAT Gateway розміщують у публічних підмережах, а приватні підмережі маршрутизують на них. По NAT у кожній AZ — щоб втрата однієї зони не відрізала інтернет іншим. Elastic IP зробили б сервери доступними ззовні.

? Новий сервер EC2 у публічній підмережі має публічну IP-адресу, Security Group дозволяє HTTP з 0.0.0.0/0, але сайт не відкривається з інтернету. VPC створена вручну. Що найімовірніше забули?
+ Прикріпити Internet Gateway до VPC або додати маршрут 0.0.0.0/0 на нього
- Створити NAT Gateway
- Увімкнути DNS hostnames
- Додати другу зону доступності
= Для доступу з інтернету потрібні IGW, маршрут на нього, публічна адреса і дозволи SG/NACL. NAT Gateway — для вихідного трафіку приватних підмереж, а не для вхідного.

? Скільки IP-адрес можна призначити ресурсам у підмережі 10.0.1.0/24?
- 256
- 254
+ 251
- 250
= У /24 — 256 адрес, AWS резервує 5 (перші чотири й останню). Доступно 251.

? Компанія хоче, щоб IPv6-сервери могли звертатися до інтернету, але ніхто з інтернету не міг ініціювати з'єднання до них. Що використати?
- NAT Gateway
+ Egress-only Internet Gateway
- Elastic IP
- Virtual Private Gateway
= NAT Gateway працює для IPv4. Для IPv6 (де всі адреси публічні) роль «лише вихід» виконує Egress-only Internet Gateway.

? Яке твердження про NAT Gateway правильне?
- До нього прикріплюють Security Group для фільтрації трафіку
- Він дозволяє серверам з інтернету ініціювати з'єднання до приватних серверів
+ Класичний NAT Gateway працює в одній AZ, тому для HA потрібен NAT у кожній AZ
- Він безкоштовний, платити треба лише за Elastic IP
= Zonal NAT Gateway живе в одній зоні і не має Security Groups; він пропускає лише вихідні з'єднання та відповіді на них. Тарифікується погодинно й за оброблені гігабайти.

? Компанія планує з'єднати VPC з офісною мережею 10.0.0.0/16 через VPN. Який діапазон обрати для нової VPC?
- 10.0.0.0/16
- 10.0.128.0/17
+ 10.1.0.0/16
- 10.0.0.0/8
= Діапазони мереж, які з'єднуються, не повинні перетинатися. 10.0.128.0/17 і 10.0.0.0/8 перетинаються з 10.0.0.0/16, а 10.1.0.0/16 — ні.
