> 🎬 **Історія Хмаринки.** Тепер у Хмаринки кілька серверів сайту в двох зонах. Але покупці знають лише одну адресу — `khmarynka.ua`. Хто вирішить, на який сервер відправити кожен запит? Хто помітить, що сервер у зоні b «завис», і перестане слати туди людей? Хто візьме на себе HTTPS, щоб серверам не возитися з сертифікатами? І як відправити `api.khmarynka.ua` на одні сервери, а `/admin` — на інші, з окремим входом? Усе це — робота **балансувальника навантаження**.

> 🖼️ **Образ.** Балансувальник — адміністратор на рецепції великого ресторану. Гості (запити) приходять до одних дверей, а він розсаджує їх по вільних столиках (серверах), обходячи ті, де офіціант захворів (health checks). **ALB** — адміністратор, що читає записку гостя («я на бізнес-ланч», «я з дітьми») і веде у відповідний зал. **NLB** — швейцар на вході величезного стадіону: не читає записок, але пропускає мільйони людей за секунду і завжди стоїть на тому самому місці (статична адреса). **GWLB** — пункт огляду: кожен гість спершу проходить через рамку металошукача (файрвол), а лише потім — у зал.

## Навіщо балансувальник {#why}

**Elastic Load Balancing (ELB)** — керовані балансувальники AWS. Вони:

- **розподіляють** запити між серверами (targets) у **кількох AZ**;
- постійно роблять **health checks** і відправляють трафік лише на здорові цілі;
- дають **одну точку входу** (DNS-ім'я), за якою сервери можна додавати й прибирати (Auto Scaling);
- **завершують TLS** (сертифікати ACM), знімаючи шифрування з серверів;
- самі **масштабуються** й високодоступні — достатньо обрати підмережі щонайменше у двох AZ.

Будова:

- **Listener** — «на якому протоколі й порту слухати» (HTTPS:443).
- **Rules** — правила: «якщо шлях `/api/*` → відправ у target group api».
- **Target group** — група цілей (сервери EC2, IP-адреси, функції Lambda, контейнери ECS) з налаштуваннями health check.
- Балансувальник буває **internet-facing** (публічний, у публічних підмережах) або **internal** (лише всередині VPC — між шарами застосунку).

## Application Load Balancer (L7) {#alb}

**ALB** працює з **HTTP/HTTPS** (а також HTTP/2, **gRPC**, **WebSocket**) і бачить **вміст запиту**. Тому вміє розумну маршрутизацію:

| Умова правила | Приклад |
|---|---|
| **Host** (ім'я домену) | `api.khmarynka.ua` → target group api; `khmarynka.ua` → web |
| **Path** (шлях) | `/images/*` → сервери зображень; `/api/*` → API |
| **HTTP-заголовок, метод, query string** | `?version=beta` → нова версія |
| **IP джерела** | `/admin/*` лише з офісної мережі |

Дії правил:

- **forward** — у target group, зокрема **зважено між кількома** (90% — стара версія, 10% — нова: blue/green і канаркові релізи);
- **redirect** — наприклад, **HTTP → HTTPS**;
- **fixed-response** — повернути готову відповідь (сторінка «технічні роботи», 404);
- **authenticate** — вимагати вхід через **Cognito** або будь-який **OIDC**-провайдер ще до того, як запит дійде до застосунку.

Інші можливості ALB:

- **Кілька сертифікатів** на одному listener завдяки **SNI**: `khmarynka.ua`, `khmarynka.pl`, `api.khmarynka.ua` — кожен зі своїм сертифікатом.
- **Цілі:** EC2, IP-адреси, **функції Lambda**, контейнери ECS з **динамічними портами** (кілька контейнерів на одному сервері).
- **Sticky sessions** — прив'язати користувача до одного сервера cookie (якщо застосунок тримає сесію на сервері; краще — винести сесії в кеш).
- **Security Group** на самому ALB; **WAF**; журнали доступу в S3.
- Застосунок бачить IP клієнта в заголовку **X-Forwarded-For** (бо TCP-з'єднання приходить від ALB).
- **Статичної IP-адреси немає** — лише DNS-ім'я.

## Network Load Balancer (L4) {#nlb}

**NLB** працює з **TCP, UDP і TLS** на транспортному рівні. Не бачить URL і заголовків, зате:

- витримує **мільйони запитів за секунду** з **наднизькою затримкою**;
- має **статичну IP-адресу в кожній AZ** (можна призначити свої **Elastic IP**) — для клієнтів, що вносять адреси в білі списки;
- **зберігає IP клієнта** (для цілей-інстансів);
- лежить в основі **PrivateLink**: власний сервіс для інших VPC публікують саме через NLB ([розділ 15](#ch/vpc-connect/privatelink));
- цілі: EC2, IP-адреси (зокрема сервери в офісі через VPN/DX) і навіть **ALB** — так можна поєднати статичні IP NLB з розумною маршрутизацією ALB;
- підтримує Security Groups і завершення TLS.

Для чого: ігрові сервери, IoT, VoIP, фінансові системи з мінімальною затримкою, будь-які не-HTTP протоколи, статичні IP.

## Gateway Load Balancer (L3) {#gwlb}

**GWLB** — для **віртуальних мережевих апаратів сторонніх виробників**: файрволів нового покоління, систем виявлення й запобігання вторгненням (IDS/IPS), глибокої інспекції пакетів. Він **прозоро** пропускає весь трафік через парк таких апаратів (протокол **GENEVE**, порт **6081**), розподіляє навантаження між ними й прибирає нездорові. У VPC-споживачах трафік спрямовують на **GWLB endpoint** через таблиці маршрутів.

На іспиті: «пропустити весь трафік VPC через файрвол-апарат стороннього вендора, масштабовано» → **Gateway Load Balancer**. (Керований файрвол AWS без сторонніх апаратів — **AWS Network Firewall**, [розділ 12](#ch/protection/firewalls).)

**Classic Load Balancer (CLB)** — застарілий, у нових рішеннях не обирають.

## Порівняння {#compare}

| | **ALB** | **NLB** | **GWLB** |
|---|---|---|---|
| Рівень | 7 (HTTP/HTTPS, gRPC, WebSocket) | 4 (TCP, UDP, TLS) | 3 (IP-пакети, GENEVE) |
| Маршрутизація | Хост, шлях, заголовки, метод, IP | Порт і протокол | Весь трафік через апарати |
| Статична IP | ❌ (лише DNS) | ✅ по одній на AZ, Elastic IP | — |
| Продуктивність | Висока | **Екстремальна**, мінімальна затримка | Висока |
| Цілі | EC2, IP, **Lambda**, ECS | EC2, IP, **ALB** | Апарати (EC2) |
| WAF | ✅ | ❌ | ❌ |
| Автентифікація користувачів | ✅ Cognito / OIDC | ❌ | ❌ |
| Типові задачі | Веб, API, мікросервіси, контейнери | Ігри, IoT, статичні IP, PrivateLink | Сторонні файрволи, IDS/IPS |

## Важливі налаштування {#settings}

- **Health checks:** протокол, шлях (`/health`), інтервал, кількість успіхів/невдач. Добра перевірка дивиться, чи застосунок справді працює (може звернутися до бази), а не лише чи відкритий порт.
- **Cross-zone load balancing:** розподіляти трафік рівномірно між **усіма** цілями в усіх AZ, а не між зонами порівну. **ALB** — увімкнено завжди й безкоштовно. **NLB і GWLB** — **вимкнено** за замовчуванням; якщо ввімкнути — трафік між AZ платний.
- **Deregistration delay** (connection draining) — перш ніж прибрати ціль (scale-in, оновлення), балансувальник чекає завершення поточних запитів (за замовчуванням **300 секунд**, можна 0–3600).
- **TLS:** завершувати на балансувальнику (сертифікат ACM), а для вимоги «шифрувати на всьому шляху» — **знову шифрувати** до цілей (HTTPS до серверів). NLB може пропустити TLS наскрізь без розшифрування (TCP listener) — тоді сертифікат на серверах.
- **Коди помилок балансувальника:** **502** — ціль дала некоректну відповідь або обірвала з'єднання; **503** — **немає здорових цілей**; **504** — ціль **не відповіла вчасно** (таймаут).

:::mnemo 🧠 Одним рядком
**HTTP і розумна маршрутизація → ALB. Швидкість, TCP/UDP, статичні IP → NLB. Сторонні файрвол-апарати → GWLB.** WAF — лише на ALB (з трьох).
:::

:::lab 🧪 Спробуй у справжньому AWS: ALB над двома серверами
**Вартість:** ALB і два маленькі сервери на 30–40 хвилин — кілька центів з кредитів. **Час:** 35 хвилин.
1. Запусти **два** сервери як у [розділі 19](#ch/ec2) (з user data, що показує `hostname`), у **різних** AZ, у публічних підмережах. Security Group серверів: HTTP 80 **лише від Security Group балансувальника** (створи `sg-lab-alb` з HTTP 80 з 0.0.0.0/0 заздалегідь).
2. **EC2 → Target groups → Create**: тип Instances, HTTP:80, health check path `/`. Зареєструй обидва сервери.
3. **Load balancers → Create → Application Load Balancer**: internet-facing, дві публічні підмережі в різних AZ, SG `sg-lab-alb`, listener HTTP:80 → твоя target group.
4. Коли стан Active, відкрий DNS-ім'я ALB і кілька разів онови сторінку — відповідатимуть різні сервери.
5. Зайди на один сервер і виконай `sudo systemctl stop nginx`. Через хвилину в target group він стане **unhealthy**, а сайт працюватиме далі — лише з другим сервером.
6. Listener → **Add rule**: умова Path `/sale*` → дія **Return fixed response** 200, текст «Розпродаж скоро!». Відкрий `/sale` на DNS-імені ALB.
**Прибери за собою:** видали ALB, target group, обидва сервери і Security Groups.
:::

#### 💡 Запам'ятай

- ELB: listener → rules → target groups з health checks; щонайменше **2 AZ**; internet-facing або internal.
- **ALB (L7):** маршрутизація за хостом, шляхом, заголовками, методом, IP; зважені target groups (blue/green); redirect HTTP→HTTPS; fixed response; **автентифікація Cognito/OIDC**; **SNI**; цілі — EC2, IP, **Lambda**, ECS; **WAF**; **без статичної IP**.
- **NLB (L4):** TCP/UDP/TLS, мільйони запитів/с, **статична IP на AZ (Elastic IP)**, зберігає IP клієнта, основа **PrivateLink**, може мати ціллю ALB.
- **GWLB (L3):** GENEVE 6081, прозорий прогін трафіку через **сторонні апарати безпеки**.
- **Cross-zone:** ALB — завжди; NLB/GWLB — вимкнено за замовчуванням (платно між AZ).
- **Deregistration delay** — 300 с; помилки: **502** — погана відповідь цілі, **503** — немає здорових цілей, **504** — таймаут.

#### 🎯 Як питають на іспиті

- Маршрутизувати `/api` і `/images` на різні групи серверів → **ALB path-based routing**
- Кілька доменів з різними сертифікатами на одному балансувальнику → **ALB з SNI**
- Поступово перевести 10% трафіку на нову версію без DNS → **ALB weighted target groups**
- Автентифікувати користувачів до того, як запит дійде до застосунку → **ALB + Cognito / OIDC**
- Клієнти вносять IP-адресу балансувальника в білий список → **NLB з Elastic IP** (або Global Accelerator)
- TCP/UDP, мільйони запитів за секунду, мінімальна затримка → **NLB**
- Пропустити трафік через файрвол-апарат стороннього вендора з масштабуванням → **Gateway Load Balancer**
- Функція Lambda має відповідати на HTTP-запити за балансувальником → **ALB з ціллю Lambda**
- Захистити застосунок за балансувальником від SQL injection → **WAF на ALB** (WAF не ставиться на NLB)
- Потрібні і статичні IP, і маршрутизація за шляхом → **NLB з ціллю ALB** (або Global Accelerator перед ALB)
- Користувачі отримують 503 від ALB → **немає здорових цілей: перевір health checks і Security Groups**
- Сервери видаляються при scale-in, а поточні запити обриваються → **налаштувати deregistration delay**

#### ⚠️ Пастки

- ALB **не має** статичної IP — будь-який варіант «призначити Elastic IP на ALB» неправильний.
- WAF **не** працює з NLB і GWLB.
- У NLB cross-zone вимкнений за замовчуванням: при нерівній кількості серверів у зонах навантаження розподіляється нерівно.
- CLB — застарілий, не обирай для нових рішень.
- Security Group серверів має дозволяти трафік **від балансувальника** (краще — з посиланням на його SG), інакше health checks провалюються.

## ✅ Перевір себе

:::quiz
? Вебзастосунок має відправляти запити до `/api/*` на одну групу серверів, а решту — на іншу, і використовувати сертифікати для трьох доменів. Який балансувальник обрати?
+ Application Load Balancer з path-based правилами і SNI
- Network Load Balancer з TLS listener
- Gateway Load Balancer
- Classic Load Balancer
= ALB працює на рівні 7: бачить шлях і хост, підтримує кілька сертифікатів на одному listener через SNI. NLB не бачить шляхів, GWLB — для апаратів безпеки, CLB застарілий.

? Банк-партнер дозволяє з'єднання лише з двох-трьох фіксованих IP-адрес, які він внесе у свій файрвол. Застосунок працює в одному регіоні на TCP. Що обрати?
- Application Load Balancer з Elastic IP
+ Network Load Balancer з Elastic IP у кожній AZ
- CloudFront distribution
- Route 53 weighted routing
= NLB має статичну IP в кожній AZ, і їх можна замінити своїми Elastic IP. ALB не підтримує статичних IP, а в CloudFront адреси змінюються.

? Компанія має закон, що вимагає пропускати весь вхідний і вихідний трафік VPC через файрвол-апарати сертифікованого стороннього виробника з автоматичним масштабуванням. Що використати?
- AWS WAF
+ Gateway Load Balancer з парком апаратів вендора
- Network ACL
- Application Load Balancer з правилами
= GWLB прозоро розподіляє весь трафік між віртуальними апаратами сторонніх вендорів (GENEVE, порт 6081) і стежить за їхнім здоров'ям. WAF працює лише з HTTP, NACL — прості правила без апаратів.

? Користувачі отримують від ALB помилку 503 Service Unavailable. Що найімовірніше?
- Сервер повернув некоректну відповідь
+ У target group немає здорових цілей
- Застосунок відповідає занадто повільно
- Сертифікат прострочено
= 503 від балансувальника зазвичай означає, що немає зареєстрованих або здорових цілей. Некоректна відповідь — 502, таймаут — 504.

? Сервери за NLB розподілені нерівно: 2 в AZ a і 6 в AZ b. Сервери в AZ a перевантажені. Що допоможе?
+ Увімкнути cross-zone load balancing на NLB
- Додати Security Group на NLB
- Змінити health check на HTTP
- Перейти на Classic Load Balancer
= Без cross-zone кожен вузол NLB ділить трафік лише між цілями своєї зони, тож зона з меншою кількістю серверів перевантажується. У NLB cross-zone вимкнений за замовчуванням (увімкнення додає плату за трафік між AZ); в ALB — увімкнений завжди.

? Команда хоче, щоб запити до вебзастосунку проходили автентифікацію через Amazon Cognito ще до того, як потраплять на сервери, без змін у коді застосунку. Що налаштувати?
- NLB з TLS listener
+ Правило ALB з дією authenticate-cognito
- Security Group з обмеженням по IP
- CloudFront geo restriction
= ALB вміє автентифікувати користувачів через Cognito User Pool або OIDC і лише потім пересилати запит цілям, передаючи дані користувача в заголовках.

? Які твердження про Application Load Balancer правильні? (Оберіть 2)
+ Може мати функцію Lambda як ціль
- Має статичну IP-адресу, яку можна замінити на Elastic IP
+ Підтримує AWS WAF
- Працює лише з протоколом UDP
- Потребує cross-zone load balancing, який вимкнено за замовчуванням
= ALB підтримує цілі Lambda і інтеграцію з WAF. Статичних IP у нього немає, UDP він не обробляє, а cross-zone у ALB увімкнений завжди.
:::
