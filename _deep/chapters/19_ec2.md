> 🎬 **Історія Хмаринки.** Мережа готова — час переселяти сам сайт. Тарас відкриває консоль EC2 і бачить понад вісімсот типів серверів: `t4g.micro`, `m7i.large`, `c8g.4xlarge`, `r7iz`, `i4i`, `p5`… «Який з них наш?» Олена ставить інше питання: «Як зробити, щоб новий сервер за п'ять хвилин ставав таким самим, як старий, з усіма програмами?» Відповіді — у будові EC2: типи, образи, скрипти запуску, життєвий цикл і розміщення.

> 🖼️ **Образ.** EC2 — автопрокат. **Сімейство інстансу** — клас авто: малолітражка на щодень (T), універсал (M), спорткар (C), вантажівка з величезним кузовом (R — багато пам'яті), фургон-рефрижератор з власним складом (I — швидкі локальні диски), болід з реактивним двигуном (P/G — графічні прискорювачі). **AMI** — авто, в яке вже поклали твої речі й налаштували сидіння. **User data** — записка на сидінні: «Перед першою поїздкою заправ і ввімкни навігатор».

## Типи інстансів: як читати назву {#types}

Назва типу кодує все важливе. Розберемо `m7g.2xlarge`:

- **m** — **сімейство** (для чого сервер);
- **7** — **покоління** (що більше, то новіше і зазвичай вигідніше);
- **g** — **атрибути**: g — Graviton (ARM), a — AMD, i — Intel, d — локальні NVMe-диски, n — посилена мережа, e — більше пам'яті чи сховища, flex — «гнучкі» дешевші варіанти;
- **2xlarge** — **розмір**: nano, micro, small, medium, large, xlarge, 2xlarge … 48xlarge, metal. Кожен наступний розмір приблизно подвоює ресурси (і ціну).

| Сімейство | Призначення | Типові задачі |
|---|---|---|
| **T** (t3, t4g) | Загальне, **burstable** | Невеликі сайти, dev/test, мікросервіси з низьким середнім навантаженням |
| **M** (m7g, m7i) | Загальне, збалансоване | Сервери застосунків, бекенди, середні бази |
| **C** (c7g, c8g) | **Обчислення** (compute optimized) | Кодування відео, пакетна обробка, HPC, ігрові сервери, ML-інференс на CPU, високонавантажені вебсервери |
| **R, X, z** | **Пам'ять** (memory optimized) | Бази й кеші в пам'яті, SAP HANA, аналітика великих наборів у RAM |
| **I, D, H** | **Сховище** (storage optimized): швидкі локальні NVMe чи великі HDD | NoSQL, OLTP з великими IOPS, сховища даних, розподілені файлові системи |
| **P, G, Inf, Trn, F** | **Прискорювачі** (accelerated): GPU, чипи Inferentia/Trainium, FPGA | Навчання й запуск ML-моделей, графіка, рендеринг |

:::deep 🔬 Глибше: burstable-інстанси (T) і CPU-кредити
Сервери сімейства T мають **базовий рівень** CPU (наприклад, 20% ядра). Поки навантаження нижче базового — сервер **накопичує кредити**; коли потрібно більше — **витрачає** їх і працює на повну. Для сайту, що більшу частину доби відпочиває, це дуже вигідно. Але якщо кредити закінчаться, продуктивність падає до базової. У режимі **unlimited** (типовий для t3/t4g) сервер може працювати понад базу й без кредитів — з доплатою. Якщо навантаження постійно високе — T не підходить, бери M чи C.
:::

**Як обрати на практиці:** почни з типу за профілем навантаження (сайт — M або C, кеш — R), запусти, подивись метрики і скоригуй. **AWS Compute Optimizer** проаналізує реальну роботу і порадить правильний розмір (right-sizing). На іспиті назви конкретних розмірів не потрібні — потрібне **сімейство за задачею**.

## AMI: образ сервера {#ami}

**AMI** (Amazon Machine Image) — шаблон, з якого запускається сервер: ОС, налаштування, встановлені програми, опис дисків.

- **Джерела:** AMI від AWS (Amazon Linux 2023, Windows Server), від спільноти, з **AWS Marketplace** (готове ПЗ з ліцензією — файрволи, бази, CMS), **власні**.
- **Власний «золотий» образ** (golden AMI): встановив і налаштував застосунок → створив AMI → нові сервери стартують **за хвилини вже готовими**. Це прискорює масштабування і гарантує однаковість.
- **AMI — регіональний.** Щоб запустити такий самий сервер в іншому регіоні (наприклад, для DR), AMI **копіюють** у той регіон. AMI можна **ділити** з іншими акаунтами.
- **EC2 Image Builder** автоматизує створення, тестування і регулярне оновлення (патчі) золотих образів.

## User data і метадані {#userdata}

**User data** — скрипт, який сервер виконує **при першому запуску** (від імені root). Приклад для сервера Хмаринки:

```bash
#!/bin/bash
dnf install -y nginx
DB_HOST=$(aws ssm get-parameter --name /khmarynka/prod/db-host --query Parameter.Value --output text)
echo "DB_HOST=$DB_HOST" >> /etc/khmarynka.env
systemctl enable --now nginx
```

Типова архітектурна дилема: **ставити все в user data** (гнучко, але сервер довго стартує) чи **запікати в AMI** (швидкий старт, але образ треба оновлювати). Для швидкого масштабування — більше в AMI, у user data — лише налаштування середовища.

**Instance Metadata Service (IMDS)** — внутрішня адреса `169.254.169.254`, з якої сервер дізнається про себе: свій ID, тип, зону, IP-адреси і — головне — **тимчасові облікові дані своєї IAM-ролі**. Використовуй **IMDSv2**: він вимагає токен сесії і захищає від атак, коли зловмисник змушує застосунок звернутися до метаданих (SSRF). У launch template можна **вимагати** IMDSv2.

Що відбувається при **stop/start**:

- автоматична **публічна IP змінюється** (Elastic IP лишається);
- приватна IP **зберігається**;
- дані на дисках **EBS зберігаються**, а на **instance store** — **зникають**;
- сервер опиняється на іншому фізичному хості — так лікують проблеми обладнання.

**Hibernate** — «сплячий режим»: вміст оперативної пам'яті зберігається на (обов'язково **зашифрований**) кореневий диск EBS. Після пробудження застосунок продовжує з того самого місця з «теплим» кешем, без довгої ініціалізації.

**Termination protection** — захист від випадкового видалення.

### Перевірки стану (status checks)

- **System status check** — проблема на боці **AWS**: фізичний хост, живлення, мережа. Лікування: **stop/start** (переїзд на інший хост) або автоматичне відновлення — більшість сучасних інстансів відновлюються самі, а для гарантії є аларм CloudWatch з дією **recover** (сервер переїжджає на новий хост, зберігаючи ID, IP-адреси й метадані).
- **Instance status check** — проблема **всередині** сервера: ОС зависла, закінчилась пам'ять, помилка мережі в ОС. Лікування — перезавантаження, виправлення конфігурації (це твоя зона відповідальності).
- **Attached EBS status check** — проблема з підключеним диском.

## Мережа й розміщення інстансів {#placement}

- **ENI** (Elastic Network Interface) — мережева карта сервера. Додаткову ENI можна **перечепити** на інший сервер разом з її приватною IP і MAC — старий прийом для швидкого failover і ліцензій, прив'язаних до MAC.
- **ENA** (Enhanced Networking) — висока пропускна здатність і низька затримка, на сучасних типах увімкнена за замовчуванням.
- **EFA** (Elastic Fabric Adapter) — для **HPC і розподіленого ML**: застосунки (MPI, NCCL) спілкуються в обхід ОС з наднизькою затримкою.

**Placement groups** — як розставити сервери фізично:

| Стратегія | Як розміщує | Навіщо | Обмеження |
|---|---|---|---|
| **Cluster** | Поруч, в одній AZ, в одній частині мережі | **Найменша затримка й найвища пропускна** між серверами: HPC, розподілене навчання ML | Одна AZ — усі разом ризикують однаково |
| **Spread** | Кожен сервер на **окремому обладнанні** (окремі стійки) | Кілька **критичних** серверів не повинні відмовити разом | Максимум **7 запущених інстансів на AZ** у групі |
| **Partition** | Групи-«партиції» на окремих стійках, до 7 партицій на AZ | Великі розподілені системи з реплікацією: **Hadoop, HDFS, Cassandra, Kafka** | Сотні інстансів; застосунок знає, в якій він партиції |

## Сервери сайту Хмаринки {#design}

- Тип **m7g.large** (Graviton, 2 vCPU, 8 GiB) — збалансовано й вигідно; застосунок на Java/Node.js/Python працює на ARM без змін.
- Власний **golden AMI** на базі Amazon Linux 2023 з уже встановленим застосунком; оновлюється щотижня через Image Builder.
- **User data** лише підтягує параметри середовища з Parameter Store.
- **IAM-роль** з правами на читання фото в S3 і секрету бази; **IMDSv2 обов'язковий**.
- **Приватні підмережі** у двох AZ, доступ адміністраторів — лише Session Manager.
- Кількість серверів змінюватиме Auto Scaling ([розділ 23](#ch/autoscaling)), а як за них платити — [наступний розділ](#ch/ec2-pricing).

:::lab 🧪 Спробуй у справжньому AWS: вебсервер за п'ять хвилин
**Вартість:** тип з позначкою *Free tier eligible* (наприклад, `t3.micro` чи `t4g.micro`) — у межах кредитів безкоштовного плану; якщо видалити сервер одразу, це центи. Бонус: запуск EC2 — одне з п'яти завдань, за які нараховують **$20 кредитів**. **Час:** 20 хвилин.
1. **EC2 → Launch instance**. Назва: `khmarynka-web-lab`.
2. AMI: **Amazon Linux 2023** (для t4g — версія arm64). Тип: `t3.micro` або `t4g.micro`.
3. Key pair: **Proceed without a key pair** (зайдемо через браузер).
4. Network: твоя VPC або default VPC, **публічна** підмережа, Auto-assign public IP — **Enable**. Security group: створи нову з правилом **HTTP (80)**, Source — **My IP**.
5. **Advanced details → Metadata version: V2 only (token required)**. У **User data** встав:
```bash
#!/bin/bash
dnf install -y nginx
echo "<h1>Хмаринка на EC2: $(hostname -f)</h1>" > /usr/share/nginx/html/index.html
systemctl enable --now nginx
```
6. **Launch**. Через хвилину відкрий у браузері публічну IP сервера (http://…) — побачиш сторінку.
7. **Connect → EC2 Instance Connect** (якщо не підключається — додай у SG правило SSH з My IP) і виконай запит до метаданих з токеном IMDSv2:
```bash
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/placement/availability-zone
```
8. **Instance state → Stop**, потім **Start** — порівняй публічну IP до і після.
**Прибери за собою:** **Instance state → Terminate** і перевір, що кореневий диск EBS зник (Elastic Block Store → Volumes). Видали Security Group.
:::

#### 💡 Запам'ятай

- Запуск EC2: **AMI + тип + мережа + SG + сховище + IAM-роль + user data + key pair** → зручно зберегти в **launch template**.
- Назва типу: **сімейство + покоління + атрибути + розмір** (`m7g.2xlarge`); **g** = Graviton.
- **T** — burstable (кредити CPU); **M** — загальне; **C** — обчислення; **R/X** — пам'ять; **I/D** — локальне сховище; **P/G/Inf/Trn** — прискорювачі.
- **AMI регіональний** — копіюй в інший регіон; **golden AMI** = швидкий старт.
- **User data** — скрипт першого запуску; **IMDSv2** — безпечні метадані й облікові дані ролі.
- **Stop/start**: нова публічна IP (крім EIP), EBS зберігається, instance store — зникає. **Hibernate** — RAM на зашифрований EBS.
- **System check** — проблема AWS (stop/start, recover); **instance check** — проблема в ОС (твоя).
- Placement: **cluster** — затримка; **spread** — ізоляція (до 7 на AZ); **partition** — Hadoop/Cassandra/Kafka.

#### 🎯 Як питають на іспиті

- In-memory база чи кеш потребує багато RAM → **memory optimized (R, X)**
- Кодування відео, наукові розрахунки, пакетна обробка з високим CPU → **compute optimized (C)**
- Навчання ML-моделей на GPU → **accelerated (P, G, Trn)**
- Дуже високі IOPS на локальних дисках для NoSQL → **storage optimized (I)**
- Найкраще співвідношення ціни й продуктивності для сумісного з ARM застосунку → **Graviton**
- Нові сервери мають стартувати швидко вже з усім ПЗ → **golden AMI**
- Запустити той самий сервер в іншому регіоні → **copy AMI в інший регіон**
- HPC, мінімальна затримка між вузлами → **cluster placement group + EFA**
- Кілька критичних серверів не повинні відмовити одночасно через обладнання → **spread placement group**
- Hadoop / Cassandra / Kafka на сотнях серверів з ізоляцією стійок → **partition placement group**
- Сервер не проходить system status check → **stop/start або CloudWatch alarm з дією recover**
- Швидко продовжити роботу з «теплою» пам'яттю після зупинки → **EC2 Hibernate**
- Захистити облікові дані ролі від SSRF-атак через метадані → **вимагати IMDSv2**

#### ⚠️ Пастки

- Instance store **зникає** при stop, terminate чи збої хоста — не для важливих даних.
- Зупинений сервер не коштує, але його **диски EBS коштують**.
- Spread placement group — максимум **7 запущених інстансів на AZ**.
- Cluster placement group — в **одній** AZ, тобто не про високу доступність.
- AMI не «глобальний»: без копіювання в іншому регіоні його не видно.

## ✅ Перевір себе

:::quiz
? Компанія запускає базу даних в оперативній пам'яті, якій потрібні сотні гігабайт RAM при помірному навантаженні на CPU. Яке сімейство інстансів обрати?
- Compute optimized (C)
+ Memory optimized (R або X)
- Storage optimized (I)
- Burstable (T)
= Memory optimized інстанси мають найбільше пам'яті на vCPU — для in-memory баз, кешів і аналітики в пам'яті. C — для інтенсивних обчислень, I — для локальних дисків з високими IOPS.

? Застосунок на EC2 під час масштабування стартує 15 хвилин, бо user data встановлює все ПЗ з нуля. Як найкраще прискорити запуск нових серверів?
+ Створити golden AMI з уже встановленим ПЗ і запускати сервери з нього
- Збільшити тип інстансу
- Перенести скрипт з user data в cron
- Використати instance store замість EBS
= Золотий образ містить усе потрібне, тож сервер готовий за хвилину-дві. User data лишають лише для налаштувань середовища.

? Сервер EC2 не проходить system status check. Що найімовірніше допоможе?
- Перевстановити застосунок
+ Зупинити і запустити інстанс (або налаштувати alarm з дією recover), щоб він переїхав на інший фізичний хост
- Перезавантажити ОС командою reboot
- Змінити Security Group
= System status check сигналізує про проблему інфраструктури AWS (хост, живлення, мережа). Stop/start переносить сервер на інший хост; дія recover робить це автоматично, зберігаючи ID і IP. Reboot лишає сервер на тому самому хості.

? Науковий застосунок на 16 серверах обмінюється величезними обсягами даних між вузлами і потребує мінімальної затримки мережі. Що обрати?
+ Cluster placement group і інстанси з Elastic Fabric Adapter
- Spread placement group у трьох AZ
- Partition placement group
- Інстанси в різних регіонах
= Cluster placement group розміщує сервери поруч в одній AZ для найменшої затримки й найбільшої пропускної здатності; EFA дає HPC-застосункам обхід ОС. Spread і partition — про ізоляцію від збоїв, а не про швидкість.

+ Instance store

= Instance store — фізичні диски хоста, дані на них зникають при stop, terminate чи збої. EBS і EFS зберігають дані незалежно від стану сервера.

? Служба безпеки хоче захистити облікові дані IAM-ролі на серверах від атак типу SSRF через сервіс метаданих. Що зробити?
+ Вимагати IMDSv2 (token required) для всіх інстансів
- Вимкнути IAM-ролі і використовувати access keys
- Відкрити доступ до 169.254.169.254 у Security Group
- Використовувати лише публічні підмережі
= IMDSv2 вимагає токен сесії, отриманий PUT-запитом, що блокує більшість SSRF-атак. Access keys — гірше за ролі, а Security Groups не керують доступом до метаданих.
