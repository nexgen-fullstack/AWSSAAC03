> 🎬 **Історія Хмаринки.** Залишки «старого світу» в офісі: мережеве сховище (NAS) на 8 ТБ з фото й документами за десять років; бухгалтерія, яка звикла до мережевої папки зі сканами і не хоче нічого міняти; стара програма резервного копіювання, що досі пише на **магнітні стрічки** (!), які кур'єр щотижня везе в банківську комірку; і постачальники, що надсилають прайс-листи через **SFTP**. Як перенести дані в AWS швидко й без втрат, а тим, хто не готовий мінятися, дати хмару «під виглядом» звичних інструментів?

> 🖼️ **Образ.** **Storage Gateway** — перекладач-посередник в офісі: офісні програми говорять звичною мовою (мережева папка, диск, стрічка), а посередник тихо зберігає все в хмарі, тримаючи найпотрібніше під рукою (локальний кеш). **DataSync** — вантажна компанія з власними швидкими фурами, що перевозить твої архіви мережею і звіряє кожну коробку. **Transfer Family** — поштове відділення в хмарі, що приймає посилки у звичному для партнерів форматі SFTP. **Snowball** — фура-сейф, яку привозять до дверей, коли мережею везти занадто довго.

## Карта рішень {#map}

| Задача | Сервіс |
|---|---|
| Офісні програми працюють з хмарним сховищем через **звичні протоколи** (NFS, SMB, iSCSI, стрічки) з **локальним кешем** — **постійно** | **AWS Storage Gateway** |
| **Перенести** або **синхронізувати** великі обсяги даних **мережею** | **AWS DataSync** |
| Партнери надсилають файли по **SFTP / FTPS / FTP / AS2**, зберігати в S3 чи EFS | **AWS Transfer Family** |
| Мережею занадто довго: сотні ТБ, повільний канал, жорсткий дедлайн | **Фізичне перенесення** (Snowball, Data Transfer Terminal, партнери) |
| Прискорити завантаження в S3 з далеких країн | **S3 Transfer Acceleration** ([розділ 27](#ch/s3/upload)) |
| Постійний приватний канал з офісу | **Direct Connect / VPN** ([розділ 16](#ch/hybrid-network)) |
| Бази даних і сервери | **DMS, MGN** ([розділ 33](#ch/migration)) |

## AWS Storage Gateway {#storage-gateway}

**Storage Gateway** — віртуальна машина (VMware, Hyper-V, KVM) в офісі або сервер EC2, що з'єднує локальні застосунки з хмарним сховищем. Чотири типи:

<figure class="diagram" data-caption="Типи Storage Gateway: як офіс бачить хмару">
<div class="grid2">
<div class="gcard"><b>📁 S3 File Gateway</b>Офіс бачить мережеву папку <strong>NFS або SMB</strong> (з Active Directory). Кожен файл стає <strong>об'єктом у S3</strong>, «гарячі» файли — у локальному кеші.<small>Далі працюють lifecycle, Glacier, аналітика по S3</small></div>
<div class="gcard"><b>💽 Volume Gateway</b>Офіс бачить <strong>блочні диски iSCSI</strong>.<small><strong>Cached</strong>: основні дані в S3, у кеші — гарячі.<br><strong>Stored</strong>: усі дані локально, асинхронні бекапи в S3 як знімки EBS</small></div>
<div class="gcard"><b>📼 Tape Gateway</b>Віртуальна <strong>стрічкова бібліотека (VTL)</strong> для наявного бекап-ПЗ (Veeam, NetBackup, Commvault…).<small>Стрічки — в S3, архів — у Glacier / Deep Archive. Фізичні стрічки більше не потрібні</small></div>
<div class="gcard"><b>🪟 FSx File Gateway</b>Локальний кеш для <strong>FSx for Windows File Server</strong>.<small>З жовтня 2024 недоступний новим клієнтам</small></div>
</div>
<figcaption>Спільне для всіх: застосунки в офісі не змінюються, а дані живуть у надійному й масштабованому сховищі AWS.</figcaption>
</figure>

:::mnemo 🧠 Cached чи Stored?
**Cached** — «основне в хмарі, під рукою лише гаряче»: економить місце в офісі. **Stored** — «усе в офісі, хмара — страховка»: мінімальна затримка до всіх даних локально, бекап в AWS. У питанні «основні дані в S3, локально лише часто використовувані» → Cached. «Усі дані мають бути доступні локально з мінімальною затримкою» → Stored.
:::

## AWS DataSync {#datasync}

**DataSync** — керований сервіс **онлайн-перенесення** і **синхронізації** даних:

- **Джерела:** NFS, SMB, HDFS, самокеровані об'єктні сховища, інші хмари — через **агента** (віртуальна машина в офісі); а також сервіси AWS між собою (без агента).
- **Призначення:** **S3** (будь-який клас, зокрема Glacier), **EFS**, усі **FSx**.
- **Швидко:** оптимізований протокол, паралельність — у рази швидше за самописні скрипти; до 10 Gbps на агента.
- **Надійно:** шифрування TLS, **перевірка цілісності** (контрольні суми), збереження метаданих і прав доступу.
- **Керовано:** розклад (щоночі синхронізувати зміни), фільтри файлів, **обмеження пропускної здатності** (щоб не «забити» канал офісу вдень), журнали й звіти.
- Працює через інтернет, VPN або **Direct Connect**.

Типові сценарії: разова міграція NAS в S3 чи EFS; регулярна синхронізація на час переходу; перенесення даних для аналітики; копіювання між регіонами (EFS → EFS, S3 → S3).

## AWS Transfer Family {#transfer}

**Transfer Family** — керовані сервери **SFTP, FTPS, FTP** і **AS2** з даними в **S3** або **EFS**:

- партнери працюють **як раніше** — тими самими клієнтами й скриптами, змінюється лише адреса сервера;
- користувачі — у самому сервісі, в Active Directory або в **власному провайдері** (через Lambda/API Gateway);
- endpoint публічний або **у VPC** (зі своїми Elastic IP для білих списків партнерів);
- файли потрапляють у S3 → **подія** запускає обробку (Lambda, Step Functions).

## Фізичне перенесення: коли мережа не встигає {#offline}

Швидко порахувати, скільки йтимуть дані мережею:

:::calc 🧮 Скільки днів мережею?
**Час ≈ обсяг (біти) ÷ реальна швидкість.** 1 ТБ ≈ 8 × 10¹² біт.
- **100 ТБ через 1 Gbps** при ~80% завантаженні каналу: 800 000 000 000 000 біт ÷ 800 000 000 біт/с ≈ 1 000 000 с ≈ **11–12 днів**.
- Ті самі **100 ТБ через 100 Mbps**: ≈ **115 днів** — майже чотири місяці.
- **8 ТБ Хмаринки через 200 Mbps** (офісний канал, ~70% вільно): ≈ 8 × 8 × 10¹² ÷ 1,4 × 10⁸ ≈ 460 000 с ≈ **5–6 днів**. Прийнятно для DataSync з обмеженням швидкості вдень.
Орієнтир: якщо мережею це займе **понад тиждень-два**, а дедлайн жорсткий, розглядай фізичне перенесення.
:::

- **AWS Snowball Edge** — захищений фізичний пристрій (десятки–сотні ТБ), який привозять, ти копіюєш дані локально, повертаєш — AWS завантажує їх у S3. Також — обчислення на краю (edge computing) там, де немає мережі.
- 🆕 З **7 листопада 2025 року** Snowball Edge **недоступний новим клієнтам**. AWS радить **DataSync** (онлайн), **AWS Data Transfer Terminal** (фізичні локації AWS, куди привозиш свої носії і швидко завантажуєш дані в хмару) або партнерів. На іспиті Snowball усе ще може бути правильною відповіддю на питання «сотні ТБ, повільний канал, тиждень на все».

:::lab 🧪 Спробуй у справжньому AWS: DataSync між двома bucket
**Вартість:** DataSync бере невелику плату за кожен перенесений ГБ — для кількох МБ це частки цента. **Час:** 20 хвилин.
1. Створи два bucket: `khmarynka-src-<цифри>` і `khmarynka-dst-<цифри>`. Завантаж у перший кілька файлів.
2. **DataSync → Tasks → Create task**. Source location: **Amazon S3** → перший bucket (дозволь консолі створити IAM-роль). Destination: **Amazon S3** → другий bucket, клас **Standard**.
3. Settings: Verify data — **Verify only the data transferred**; Transfer mode — **Transfer only data that has changed**. Schedule — **Not scheduled**. Create.
4. **Start** → дочекайся Success. Подивись звіт: скільки файлів, байтів, час, результат перевірки.
5. Додай ще один файл у перший bucket і запусти задачу знову — перенесеться лише новий файл (інкрементально).
**Прибери за собою:** видали задачу і локації DataSync, очисти й видали обидва bucket, видали створену IAM-роль DataSync.
:::

#### 💡 Запам'ятай

- **Storage Gateway** — постійний гібридний доступ з локальним кешем: **S3 File Gateway** (NFS/SMB → об'єкти S3), **Volume Gateway** (iSCSI: **Cached** — основне в S3; **Stored** — усе локально, бекап в S3), **Tape Gateway** (VTL → S3/Glacier), FSx File Gateway (закритий для нових).
- **DataSync** — онлайн-перенесення і синхронізація: NFS/SMB/HDFS/об'єкти/інші хмари ↔ S3, EFS, FSx; агент; перевірка цілісності, метадані, розклад, обмеження швидкості.
- **Transfer Family** — керовані SFTP/FTPS/FTP/AS2 поверх S3 чи EFS; партнери нічого не змінюють.
- **Фізичне перенесення** — коли мережею понад тиждень-два: Snowball Edge (🆕 закритий для нових клієнтів з 07.11.2025), **Data Transfer Terminal**, партнери.
- Рахуй: 100 ТБ через 1 Gbps ≈ 11–12 днів.

#### 🎯 Як питають на іспиті

- On-prem застосунки зберігають файли в S3 через NFS/SMB з локальним кешем → **S3 File Gateway**
- Замінити фізичні стрічки, залишивши наявне бекап-ПЗ → **Tape Gateway**
- iSCSI-томи: основні дані в хмарі, локально лише кеш → **Volume Gateway (Cached)**
- Усі дані мають бути локально з мінімальною затримкою, бекап в AWS → **Volume Gateway (Stored)**
- Перенести 50 ТБ з NAS в S3 або EFS мережею, за розкладом, з перевіркою цілісності → **AWS DataSync**
- Регулярно синхронізувати файлову систему офісу з EFS під час міграції → **DataSync за розкладом**
- Партнери надсилають файли по SFTP, зберігати треба в S3 → **AWS Transfer Family**
- Сотні терабайтів, повільний канал, дедлайн — тиждень → **фізичне перенесення (Snowball Edge; для нових клієнтів — Data Transfer Terminal або партнери)**
- Перенести дані з on-prem HDFS у S3 для аналітики → **DataSync**
- Скопіювати дані між EFS у двох регіонах → **DataSync** (або EFS Replication)

#### ⚠️ Пастки

- **DataSync** — перенесення і синхронізація; **Storage Gateway** — постійний гібридний доступ; **Transfer Family** — протоколи для партнерів. Не міняй їх місцями.
- Snowball — **офлайн**, DataSync — **онлайн**.
- Direct Connect не допоможе в терміновій задачі: його підключення займає тижні.
- Volume Gateway Stored ≠ Cached: питання завжди підказує, де мають жити **основні** дані.

## ✅ Перевір себе

:::quiz
? Компанія хоче, щоб офісні сервери зберігали файли в Amazon S3 через звичну мережеву папку SMB з правами Active Directory, а часто використовувані файли були доступні локально без затримок. Що обрати?
+ AWS Storage Gateway — S3 File Gateway
- AWS DataSync
- AWS Transfer Family
- Volume Gateway (Stored)
= S3 File Gateway надає NFS/SMB-папки, зберігає файли як об'єкти S3 і тримає локальний кеш. DataSync переносить дані, а не дає постійний доступ; Transfer Family — для SFTP/FTP; Volume Gateway — блочні iSCSI-диски.

? Резервне копіювання в компанії робиться наявним ПЗ на фізичні стрічки, які щотижня вивозять. Потрібно позбутися стрічок, не змінюючи бекап-ПЗ і процеси. Що обрати?
- S3 File Gateway
+ Tape Gateway з архівуванням у Glacier Deep Archive
- DataSync з розкладом
- AWS Backup
= Tape Gateway емулює стрічкову бібліотеку для наявного ПЗ, а віртуальні стрічки зберігає в S3 і архівує в Glacier/Deep Archive. ПЗ «думає», що пише на стрічки.

? Потрібно перенести 60 ТБ з локального NAS в Amazon EFS. Канал — 1 Gbps, строк — місяць, потрібна перевірка цілісності та збереження прав доступу. Що обрати?
+ AWS DataSync з агентом в офісі
- AWS Snowball Edge
- Скрипт rsync на EC2
- AWS Transfer Family
= 60 ТБ через 1 Gbps — близько тижня, що вкладається в строк. DataSync переносить мережею з перевіркою цілісності й збереженням метаданих. Скрипт — більше роботи і менше гарантій.

? Компанія має 400 ТБ даних, інтернет-канал 100 Mbps і лише тиждень на перенесення в S3. Як перенести дані (для клієнта, що вже користувався Snow)?
- DataSync через наявний канал
- S3 Transfer Acceleration
+ Фізичні пристрої AWS Snowball Edge
- Site-to-Site VPN
= 400 ТБ через 100 Mbps — понад рік. Лише фізичне перенесення вкладається в строк. Для нових клієнтів AWS пропонує Data Transfer Terminal або партнерів, бо Snowball Edge з листопада 2025 року їм недоступний.

? Постачальники роками надсилають файли на FTP-сервер компанії по SFTP і не хочуть нічого змінювати. Компанія переносить сервер в AWS і хоче зберігати файли в S3 без керування серверами. Що обрати?
+ AWS Transfer Family з SFTP-endpoint і даними в S3
- S3 File Gateway
- EC2 з самостійно налаштованим SFTP-сервером
- Amazon S3 static website hosting
= Transfer Family — керований SFTP/FTPS/FTP/AS2-сервер, що пише прямо в S3 чи EFS. Партнери змінюють лише адресу; сервери підтримувати не треба.

? Компанія використовує iSCSI-диски в офісі. Усі дані мають бути доступні локально з мінімальною затримкою, а в AWS потрібна асинхронна резервна копія, яку можна відновити як том EBS. Що обрати?
- Volume Gateway (Cached)
+ Volume Gateway (Stored)
- S3 File Gateway
- Tape Gateway
= Stored-режим тримає всі дані локально і асинхронно зберігає знімки в AWS (їх можна відновити як EBS). Cached тримає основні дані в S3, а локально — лише кеш.

? Які твердження про AWS DataSync правильні? (Оберіть 2)
+ Перевіряє цілісність перенесених даних
- Надає постійний NFS-доступ до S3 для офісних застосунків
+ Може переносити дані за розкладом і з обмеженням пропускної здатності
- Працює лише між сервісами AWS
- Потребує фізичного пристрою для перенесення
= DataSync — онлайн-перенесення з перевіркою цілісності, розкладом і обмеженням швидкості; з агентом працює з локальними і сторонніми сховищами. Постійний доступ з кешем — це Storage Gateway.
:::
