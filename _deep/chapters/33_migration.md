> 🎬 **Історія Хмаринки.** Олена ставить дедлайн: «До наступного сезону розпродажів у підсобці не має лишитися жодного сервера». А там — сайт з базою MySQL, NAS з фото, складська програма на Windows з ліцензією «на ядро», файлова шафа бухгалтерії, стара CRM, якою ніхто не користується, і сервер звітів, про який ніхто не пам'ятає, навіщо він. Переносити все «як є»? Переписати все з нуля? Правильна відповідь — **для кожної системи свою стратегію**, план хвиль і перевірений інструмент. Це і є міграція — одна з найпрактичніших тем для архітектора.

> 🖼️ **Образ.** Переїзд у новий будинок. Щось **викидаєш** (retire), щось поки **лишаєш** у старій квартирі (retain), щось **перевозиш як є** (rehost), щось перевозиш **разом з шафою** (relocate), щось перевозиш і **трохи ремонтуєш** (replatform), щось **купуєш нове** замість старого (repurchase), а щось **перебудовуєш** під новий будинок (refactor). Переїзд ніхто не робить за один вечір: спершу оцінка, потім хвилі, в кожній — пробне перевезення і лише потім остаточне.

## Три фази міграції {#phases}

1. **Assess (оцінка)** — що є, скільки коштує зараз, скільки коштуватиме в AWS, навіщо переїжджати (бізнес-обґрунтування). Інструменти: інвентаризація серверів і залежностей, **Migration Evaluator** (оцінка вартості і правильних розмірів у AWS).
2. **Mobilize (підготовка)** — **landing zone** (акаунти, мережа, безпека — Control Tower, [розділ 10](#ch/organizations/control-tower)), навчання команди, детальний план: яка система, за якою стратегією, в якій хвилі.
3. **Migrate & Modernize** — перенесення хвилями, тестування, перемикання (cutover), оптимізація після переїзду.

## Сім стратегій: 7R {#7r}

| Стратегія | Суть | Приклад | Інструменти AWS |
|---|---|---|---|
| **Retire** | Вимкнути непотрібне | Сервер звітів, яким не користуються | — (економія одразу) |
| **Retain** | Поки залишити як є | Система, яку міняють через рік; жорсткі вимоги | Гібрид: VPN/DX, Storage Gateway |
| **Rehost** («lift and shift») | Перенести сервер **як є** на EC2 | Складська програма без змін коду | **AWS Application Migration Service (MGN)** |
| **Relocate** | Перенести **гіпервізор** цілими віртуальними машинами | Сотні VM на VMware без змін інструментів | **VMware Cloud on AWS**, **Amazon Elastic VMware Service** |
| **Replatform** («lift, tinker and shift») | Невеликі оптимізації при переносі | MySQL → **Amazon RDS / Aurora**; застосунок → контейнери чи Beanstalk | **DMS**, ECS, Beanstalk |
| **Repurchase** | Перейти на готовий **SaaS** | Стара CRM → хмарна CRM | AppFlow (для даних) |
| **Refactor / Re-architect** | Переписати під cloud-native | Моноліт → мікросервіси, serverless, події | Lambda, Step Functions, DynamoDB… |

Як обирати: **rehost** — найшвидший і найдешевший шлях переїзду (часто перший крок, а оптимізація — потім); **replatform** — розумний компроміс (керовані бази без переписування); **refactor** — найбільша вигода в довгостроковій перспективі, але найдовше і найдорожче; **retire** — найдешевша міграція з усіх.

## AWS Application Migration Service (MGN) {#mgn}

**MGN** — основний інструмент **rehost**:

1. На вихідний сервер (фізичний, VMware, Hyper-V, інша хмара) ставиться **агент реплікації**.
2. Агент **безперервно реплікує диски на рівні блоків** у недорогу проміжну зону (staging area) в AWS.
3. **Тестовий запуск** — копія сервера стартує в AWS для перевірки, не зупиняючи оригінал.
4. **Cutover** — у погоджене вікно: остання синхронізація, запуск робочого сервера в AWS, перемикання DNS. Простій — хвилини.
5. MGN автоматично конвертує сервер для роботи на EC2 (драйвери, завантажувач) і може виконати дії після запуску (встановити агентів, налаштувати).

## AWS DMS: міграція баз даних {#dms}

**AWS Database Migration Service** переносить бази з **мінімальним простоєм**:

- **Full load** — копія всіх наявних даних;
- **CDC** (change data capture) — **безперервна реплікація змін**, поки стара база працює і приймає замовлення;
- у зручний момент — перемикання застосунку на нову базу (простій — хвилини).

Робоча частина — **replication instance** (або **DMS Serverless**), між ними — **source** і **target endpoints**. Цілі: RDS, Aurora, Redshift, DynamoDB, S3, Kinesis, OpenSearch, DocumentDB та інші. Є перевірка (validation) збіжності даних.

### Гомогенна чи гетерогенна

- **Гомогенна** — той самий рушій: MySQL → RDS/Aurora MySQL, PostgreSQL → Aurora PostgreSQL, Oracle → RDS for Oracle. Достатньо DMS (або нативних інструментів бази).
- **Гетерогенна** — різні рушії: **Oracle → Aurora PostgreSQL**, SQL Server → MySQL. Спершу треба **конвертувати схему і код** (таблиці, збережені процедури, функції) — **DMS Schema Conversion** (у консолі) або **AWS Schema Conversion Tool (SCT)** (настільний застосунок). Потім дані переносить DMS. SCT конвертує й схеми **сховищ даних** (Oracle, Teradata, Netezza → Redshift).
- Для SQL Server → PostgreSQL без переписування T-SQL є ще **Babelfish for Aurora PostgreSQL** ([розділ 35](#ch/aurora)).

## Інші інструменти переїзду

- **Дані й файли:** **DataSync** (мережею), **Snowball / Data Transfer Terminal** (фізично), **Transfer Family**, **Storage Gateway** для гібридного періоду — [розділ 30](#ch/hybrid-storage).
- **VMware:** **VMware Cloud on AWS** і **Amazon Elastic VMware Service** — ті самі інструменти vSphere, але в AWS (relocate).
- **AWS Elastic Disaster Recovery (DRS)** — та сама технологія безперервної реплікації, але для **аварійного відновлення**: сервери з офісу чи іншого регіону реплікуються в AWS з RPO в секунди і RTO в хвилини ([розділ 42](#ch/resilience)).
- **Мейнфрейми** — AWS Mainframe Modernization.
- 🆕 **AWS Transform** — сервіс з AI-агентами для масової модернізації (VMware, .NET, мейнфрейми). А старі **Migration Hub** і **Application Discovery Service** з листопада 2025 недоступні новим клієнтам — на іспиті їх назви ще можуть зустрітися.

## План переїзду Хмаринки {#plan}

| Система | Стратегія | Як |
|---|---|---|
| Сервер звітів (ніхто не користується) | **Retire** | Вимкнути, архів даних — у S3 Glacier |
| Стара CRM | **Repurchase** | Хмарна CRM; історію даних — експортом |
| Фото на NAS (8 ТБ) | Перенесення даних | **DataSync** у S3 з нічною синхронізацією до cutover |
| База MySQL замовлень | **Replatform** | **DMS** (full load + CDC) → **Aurora MySQL** |
| Сайт (моноліт) | **Replatform** | Контейнерний образ → **ECS на Fargate** за ALB |
| Складська програма (Windows, ліцензія на ядра) | **Rehost** | **MGN** → EC2 на **Dedicated Host** (BYOL); пізніше — заміна |
| Файлова шафа бухгалтерії | **Replatform** | **FSx for Windows** + DataSync; AD — з довірою |
| Обробка замовлень (після переїзду) | **Refactor** | Step Functions + Lambda + SQS ([розділи 31–32](#ch/events)) |

**Хвилі:** 1) landing zone, мережа, VPN; 2) retire і repurchase — швидкі перемоги; 3) дані (DataSync, DMS у режимі CDC); 4) сайт і база — cutover уночі з планом відкату (стара база ще тиждень отримує зміни у зворотному напрямку); 5) склад; 6) оптимізація витрат і рефакторинг.

:::note 📌 Правила успішного cutover
- Кожна хвиля — з **тестовим запуском** і **планом відкату**.
- Понизь **TTL** DNS-записів за кілька днів до перемикання — щоб зміна поширилась за хвилини ([розділ 17](#ch/route53/health)).
- Перемикай трафік поступово, якщо можна (**Route 53 weighted** 10% → 50% → 100%).
- Після переїзду — **правильний розмір** (Compute Optimizer), Savings Plans, вимкнення старого обладнання.
:::

1. **Вправа на папері.** Для кожної системи обери стратегію 7R: (а) сайт-візитка на WordPress, (б) Oracle-база ERP з тисячами збережених процедур, яку треба перевести на PostgreSQL, (в) 300 віртуальних машин VMware, які треба перенести за місяць без змін, (г) поштовий сервер Exchange, (д) застосунок, що має лишатися в офісі через закон. #### 💡 Запам'ятай

- Фази: **Assess → Mobilize → Migrate & Modernize**; спершу — **landing zone**.
- **7R:** Retire, Retain, **Rehost** (MGN), **Relocate** (VMware), **Replatform** (RDS, Aurora, контейнери), **Repurchase** (SaaS), **Refactor** (cloud-native).
- **MGN** — безперервна блокова реплікація серверів, тестовий запуск, cutover за хвилини.
- **DMS** — **full load + CDC**, мінімальний простій; **гомогенна** міграція — лише DMS; **гетерогенна** — спершу **SCT / DMS Schema Conversion**, потім DMS.
- Дані — DataSync/Snowball/Transfer Family; DR серверів — **Elastic Disaster Recovery**.
- Cutover: тест, план відкату, низький TTL, поступове перемикання.

#### 🎯 Як питають на іспиті

- Перенести сотні серверів «як є» в EC2 швидко і з мінімальним простоєм → **AWS Application Migration Service (MGN)**
- Oracle → Aurora PostgreSQL з мінімальним простоєм → **SCT / DMS Schema Conversion (схема) + DMS (дані з CDC)**
- MySQL on-prem → RDS MySQL з мінімальним простоєм → **DMS з full load + CDC** (SCT не потрібен)
- Перенести дані сховища Teradata в Redshift → **SCT (схема) + DMS/агенти SCT (дані)**
- Перенести віртуальні машини VMware без зміни інструментів → **VMware Cloud on AWS** (relocate)
- Невелика оптимізація при переїзді: база переходить у керований сервіс → **Replatform (RDS / Aurora)**
- Замінити власну CRM на хмарну → **Repurchase**
- Вимкнути сервери, якими ніхто не користується → **Retire**
- DR для серверів в офісі з RPO в секунди → **AWS Elastic Disaster Recovery**
- Переписати моноліт на мікросервіси й serverless → **Refactor / Re-architect**

#### ⚠️ Пастки

- **SCT не потрібен** для гомогенних міграцій (MySQL → MySQL).
- DMS мігрує **дані**, а не схему для різних рушіїв — схему конвертує SCT/DMS Schema Conversion.
- Rehost переносить і всі неефективності — плануй оптимізацію після переїзду.
- Без плану відкату і тестового запуску cutover — лотерея.

## ✅ Перевір себе

:::quiz
? Компанія має 200 серверів Linux і Windows у власному дата-центрі і хоче перенести їх в AWS за два місяці без змін у застосунках і з мінімальним простоєм. Що обрати?
+ AWS Application Migration Service (MGN)
- AWS DMS
- AWS DataSync
- Переписати застосунки на Lambda
= MGN безперервно реплікує диски серверів у AWS і дозволяє виконати cutover за хвилини — класичний rehost. DMS мігрує бази, DataSync — файли.

? Потрібно перенести базу Oracle у Amazon Aurora PostgreSQL з мінімальним простоєм. База містить багато збережених процедур. Які інструменти використати? (Оберіть 2)
+ AWS SCT або DMS Schema Conversion для конвертації схеми і коду
+ AWS DMS з full load і CDC для перенесення даних
- AWS DataSync для файлів бази
- AWS MGN для сервера бази
- Amazon S3 Transfer Acceleration
= Гетерогенна міграція: спершу конвертуються схема і процедури (SCT/DMS Schema Conversion), потім DMS переносить дані з безперервною реплікацією змін. MGN перенесе сервер «як є», але не змінить рушій.

? Компанія переносить MySQL з власного сервера в Amazon RDS for MySQL. Простій має бути мінімальним. Що потрібно?
- AWS SCT для конвертації схеми, потім DMS
+ AWS DMS з full load і CDC; SCT не потрібен
- Експорт у CSV і завантаження вручну на вихідних
- AWS MGN
= Гомогенна міграція (той самий рушій) не потребує конвертації схеми. DMS копіює дані й реплікує зміни, поки стара база працює, тож перемикання займає хвилини.

? Під час міграції компанія переносить базу з власного сервера в Amazon RDS, а застосунок — у контейнери, не переписуючи код. Як називається ця стратегія?
- Rehost
+ Replatform
- Refactor
- Repurchase
= Replatform («lift, tinker and shift») — невеликі оптимізації при переносі, зокрема перехід на керовані сервіси без зміни архітектури застосунку.

? Компанія має 500 віртуальних машин VMware vSphere і хоче перенести їх в AWS, зберігши наявні інструменти й процеси адміністраторів. Що обрати?
- AWS MGN для кожної VM з конвертацією в EC2
+ VMware Cloud on AWS (або Amazon Elastic VMware Service)
- Amazon EKS
- AWS Lambda
= Relocate: гіпервізор VMware працює в AWS, віртуальні машини переносяться без конвертації, адміністратори працюють звичними інструментами vSphere.

? Під час оцінки виявилось, що 15% серверів ніхто не використовує вже рік. Яка стратегія для них найвигідніша?
+ Retire
- Retain
- Rehost
- Relocate
= Retire — вимкнути непотрібне. Це найдешевша «міграція»: жодних витрат на перенесення і зменшення рахунку одразу.

? Під час DMS-міграції стара база продовжує приймати замовлення. Що гарантує, що нові замовлення потраплять у нову базу до перемикання?
- Full load, запущений повторно щогодини
+ Change data capture (CDC) — безперервна реплікація змін
- Validation у DMS
- Multi-AZ у новій базі
= CDC відстежує зміни в джерелі й безперервно застосовує їх у цільовій базі, тож на момент cutover різниця — секунди.
