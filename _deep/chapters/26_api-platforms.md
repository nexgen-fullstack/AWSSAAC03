> 🎬 **Історія Хмаринки.** Хмаринка запускає мобільний застосунок, а кур'єрські служби й продавці-партнери хочуть працювати з магазином через **API**. Потрібні: вхідні двері для тисяч запитів, перевірка токенів, ліміти «не більше 100 запитів за секунду для безкоштовних партнерів», кеш, захист від зловживань — і все це без серверів. Паралельно маркетолог хоче «просто задеплоїти» маленький сайт акцій, не вникаючи в інфраструктуру, а бухгалтерія — щомісяця переганяти мільйони записів у звіти. Сьогодні — про **API Gateway** і кілька «платформ», що знімають з тебе рутину.

> 🖼️ **Образ.** **API Gateway** — рецепція бізнес-центру: перевіряє перепустки (авторизація), рахує відвідувачів і не пускає зайвих (throttling), видає типові довідки з полички без походу в кабінети (кеш), відправляє кожного у потрібний кабінет (інтеграції). **Elastic Beanstalk** — ресторан «під ключ»: приносиш рецепти (код), а зал, кухню і персонал (сервери, балансувальник, масштабування) облаштовують за тебе. **AWS Batch** — цех з чергою великих замовлень, що сам наймає робітників, коли замовлень багато.

## Amazon API Gateway {#apigw}

**Amazon API Gateway** — керовані «вхідні двері» для API: приймає HTTP-запити, перевіряє їх і передає далі — у **Lambda**, у будь-який **HTTP-сервіс**, прямо в **сервіси AWS** (наприклад, покласти повідомлення в SQS без жодного коду) або в **приватні** ресурси VPC через **VPC Link** (NLB/ALB). Serverless, масштабується автоматично, оплата за запити.

### Три типи API

| Тип | Для чого | Можливості |
|---|---|---|
| **REST API** | Повнофункціональні API | **Кешування** відповідей, **API keys і usage plans**, **WAF**, валідація й трансформація запитів, приватні API, канаркові релізи стадій |
| **HTTP API** | Прості й дешеві API, проксі до Lambda чи HTTP | **Дешевше і швидше**, вбудована перевірка **JWT** (Cognito, будь-який OIDC); менше функцій |
| **WebSocket API** | **Двосторонній** зв'язок у реальному часі | Чати, сповіщення, онлайн-ігри, дашборди, що оновлюються самі |

### Типи endpoint

- **Edge-optimized** — запити заходять через мережу CloudFront (для клієнтів по всьому світу).
- **Regional** — для клієнтів у тому ж регіоні (або якщо ставиш свій CloudFront попереду).
- **Private** — API доступний **лише з VPC** через interface endpoint, з resource policy (внутрішні API компанії).

### Безпека і контроль

- **Авторизація:** **IAM** (підписані запити — для сервісів і внутрішніх клієнтів), **Cognito User Pools** (токени користувачів застосунку), **Lambda authorizer** (власна логіка: перевірити токен стороннього провайдера, заголовки, ключі), для HTTP API — **JWT authorizer**.
- **Throttling:** за замовчуванням близько **10 000 запитів за секунду** на акаунт у регіоні (з піками до 5 000 «сплеску»). Понад ліміт — відповідь **429 Too Many Requests**. Можна задати ліміти для стадій і методів.
- **API keys + usage plans** (REST) — **окремі ліміти й квоти для кожного клієнта**: «безкоштовний тариф — 100 запитів/с і 1 млн на місяць, платний — 1 000 запитів/с». Важливо: API key — інструмент обліку й лімітів, **а не** надійна автентифікація.
- **WAF** на REST API, власні домени з сертифікатами **ACM**, **mTLS**.

### Продуктивність і релізи

- **Кешування** (REST): відповіді зберігаються на заданий TTL — менше навантаження на бекенд і швидші відповіді.
- **Таймаут інтеграції** — за замовчуванням **29 секунд** (для regional і private REST API його можна збільшити); розмір запиту — до **10 MB**. Довгі операції роблять асинхронно: прийняти запит, покласти в чергу, повернути «прийнято».
- **Стадії** (`dev`, `prod`) зі змінними стадій і **canary release** — частина трафіку стадії йде на нову версію.

## AWS Elastic Beanstalk {#beanstalk}

**Elastic Beanstalk** — PaaS: завантажуєш код (Java, .NET, Node.js, Python, PHP, Ruby, Go або Docker-образ), а Beanstalk сам створює й налаштовує **EC2, Auto Scaling, балансувальник, моніторинг**, оновлює платформу. Ти керуєш застосунком, а не інфраструктурою — але всі ресурси видно в акаунті, і їх можна тонко налаштувати.

- **Середовища:** *web server* (за балансувальником) і *worker* (обробляє чергу SQS — фонові задачі).
- **Політики розгортання:**

| Політика | Як | Простій | Ризик / вартість |
|---|---|---|---|
| **All at once** | Усі сервери оновлюються разом | Так, короткий | Найшвидше, найризикованіше |
| **Rolling** | Партіями | Ні, але менша потужність під час оновлення | Відкат повільний |
| **Rolling with additional batch** | Спершу додає нову партію, потім оновлює | Ні, потужність збережена | Трохи дорожче |
| **Immutable** | Нові сервери в новій ASG, потім заміна | Ні | Найбезпечніший відкат, дорожче на час оновлення |
| **Traffic splitting** | Частина трафіку на нові сервери (канарка) | Ні | Перевірка на реальних користувачах |
| **Blue/green** | Окреме нове середовище + **swap URL** | Ні | Миттєвий відкат; повна копія середовища |

На іспиті: «розробники хочуть просто розгорнути вебзастосунок, не займаючись інфраструктурою» → **Elastic Beanstalk**. Але пам'ятай: Beanstalk **не serverless** — він керує EC2 за тебе.

:::note 🆕 AWS App Runner
Сервіс «запусти контейнер чи код як вебзастосунок одним кліком» — **AWS App Runner** — з **30 квітня 2026 року закритий для нових клієнтів**. AWS радить для нових проєктів **Amazon ECS Express Mode** (спрощене розгортання контейнерних вебзастосунків на ECS з балансувальником і масштабуванням) або Elastic Beanstalk.
:::

## AWS Batch {#batch}

**AWS Batch** — керована черга й планувальник **пакетних задач** будь-якої тривалості:

- описуєш **job definition** (контейнерний образ, CPU, пам'ять), кладеш задачі в **job queue**;
- Batch сам підбирає і запускає ресурси в **compute environment** — **EC2** (зокрема **Spot**) або **Fargate** — і прибирає їх після роботи;
- **array jobs** (тисячі схожих задач одним запитом), **залежності** між задачами, пріоритети черг, повтори.

**Batch чи Lambda?** Lambda — коротко (до 15 хв), на подію. Batch — довго, великі обсяги, черги й залежності, дешево на Spot. **Batch чи Step Functions?** Step Functions оркеструють кроки процесу; Batch виконує важкі обчислення (і Step Functions можуть запускати задачі Batch).

## AWS Amplify {#amplify}

**AWS Amplify** — інструменти й хостинг для **фронтенду і мобільних застосунків**: підключаєш git-репозиторій — Amplify збирає і розгортає сайт (React, Vue, Next.js) з CDN і HTTPS, створює preview-середовища для гілок; бекенд — автентифікація (Cognito), дані, сховище, функції. Для команд фронтенду, яким потрібен **full-stack** без глибокого занурення в AWS. Поруч — **AWS Device Farm**: тестування застосунків на сотнях **реальних** телефонів і браузерів.

## Що обрати {#choose}

| Задача | Сервіс |
|---|---|
| Serverless REST API з кешем, API keys, лімітами для клієнтів | **API Gateway REST API** + Lambda |
| Простий дешевий HTTP-проксі до Lambda з JWT | **API Gateway HTTP API** |
| Двосторонній зв'язок у реальному часі | **API Gateway WebSocket API** (або AppSync) |
| GraphQL, підписки в реальному часі | **AWS AppSync** |
| «Просто задеплоїти» вебзастосунок з коду без роботи з інфраструктурою | **Elastic Beanstalk** |
| Тисячі пакетних задач, довгих, з чергами, на Spot | **AWS Batch** |
| Хостинг фронтенду з CI/CD з git + бекенд для мобільного застосунку | **AWS Amplify** |

:::lab 🧪 Спробуй у справжньому AWS: HTTP API перед Lambda
**Вартість:** API Gateway і Lambda — у межах безкоштовних лімітів для кількох запитів. **Час:** 15 хвилин. Потрібна функція `khmarynka-hello` з [розділу 25](#ch/lambda) (або створи нову з тим самим кодом).
1. **API Gateway → Create API → HTTP API → Build**. Integration: **Lambda** → `khmarynka-hello`. Назва: `khmarynka-api`.
2. Route: метод **GET**, шлях `/hello` → інтеграція з функцією. Stage: `$default`, auto-deploy. Create.
3. Скопіюй **Invoke URL** і відкрий у браузері `<Invoke URL>/hello` — побачиш сторінку від Lambda.
4. **Protect → Throttling** → задай для маршруту rate **2**, burst **2** запити/с. Швидко онови сторінку багато разів — отримаєш **429** (`Too Many Requests`).
5. Подивись у **Monitor**: кількість запитів, помилки 4xx.
6. Для порівняння відкрий **Create API → REST API** і подивись опції, яких немає в HTTP API: API keys, usage plans, кешування стадії (не створюй).
**Прибери за собою:** видали HTTP API; функцію — якщо більше не потрібна.
:::

#### 💡 Запам'ятай

- **API Gateway:** REST (кеш, API keys + **usage plans**, WAF, валідація, приватні API), **HTTP** (дешевше, JWT), **WebSocket** (двосторонній).
- Endpoints: **edge-optimized, regional, private** (лише з VPC).
- Авторизація: **IAM**, **Cognito**, **Lambda authorizer**, JWT (HTTP API).
- Throttling ~**10 000 запитів/с** на акаунт у регіоні → **429**; таймаут інтеграції **29 с** за замовчуванням; payload до 10 MB.
- Інтеграції: Lambda, HTTP, **сервіси AWS напряму** (SQS, DynamoDB…), **VPC Link** до приватних ALB/NLB.
- **AppSync** — GraphQL і підписки.
- **Elastic Beanstalk** — PaaS над EC2; політики: all at once, rolling, rolling with additional batch, **immutable**, traffic splitting, **blue/green (swap URL)**.
- **AWS Batch** — пакетні задачі будь-якої тривалості на EC2/Spot/Fargate. **Amplify** — фронтенд і мобільні з CI/CD.
- 🆕 App Runner закритий для нових клієнтів (з 30.04.2026).

#### 🎯 Як питають на іспиті

- Serverless REST API → **API Gateway + Lambda (+ DynamoDB)**
- Різні ліміти запитів і квоти для різних клієнтів API → **API Gateway usage plans + API keys**
- Кешувати відповіді API, щоб зменшити навантаження на бекенд → **API Gateway caching (REST API)**
- Власна перевірка токенів стороннього провайдера → **Lambda authorizer**
- Користувачі застосунку входять через Cognito і викликають API → **Cognito User Pool authorizer**
- Двосторонній чат у реальному часі → **API Gateway WebSocket API**
- API має бути доступний лише зсередини VPC → **private REST API + interface endpoint + resource policy**
- Приймати замовлення через API і не губити їх у пік → **API Gateway → SQS (напряму) → обробка асинхронно**
- Клієнти отримують 429 → **спрацював throttling: підняти ліміти або налаштувати usage plans**
- Розробники хочуть лише завантажити код, а сервери, балансувальник і масштабування створюються самі → **Elastic Beanstalk**
- Нова версія з мінімальним ризиком і миттєвим відкатом у Beanstalk → **blue/green (swap environment URL)** або immutable
- Тисячі пакетних задач з чергами і Spot → **AWS Batch**
- Хостинг SPA-фронтенду з автоматичним розгортанням з git → **AWS Amplify Hosting**

#### ⚠️ Пастки

- API key у API Gateway — не автентифікація, а облік і ліміти.
- Кешування, usage plans і WAF — у **REST** API, не в HTTP API.
- Таймаут інтеграції API Gateway обмежений (29 с за замовчуванням) — довгі задачі робимо асинхронно.
- Elastic Beanstalk — не serverless: під ним EC2.
- Batch — не для відповідей користувачу в реальному часі.

## ✅ Перевір себе

:::quiz
? Компанія продає доступ до свого API трьом тарифам: Free (10 запитів/с), Pro (100 запитів/с), Enterprise (1 000 запитів/с), з місячними квотами. Що використати?
- Lambda reserved concurrency для кожного тарифу
+ API Gateway REST API з API keys і usage plans
- Три окремі Application Load Balancers
- AWS WAF rate-based rules для кожного клієнта
= Usage plans задають ліміти швидкості й квоти для груп API keys — саме тарифи для клієнтів. Reserved concurrency обмежує функцію, а не клієнтів, WAF — захист, а не тарифікація.

? API каталогу товарів отримує тисячі однакових GET-запитів на хвилину, і бекенд перевантажений. Дані змінюються раз на годину. Як найпростіше зменшити навантаження?
+ Увімкнути кешування на стадії REST API в API Gateway
- Перейти з REST API на WebSocket API
- Додати Lambda authorizer
- Збільшити таймаут інтеграції
= Кеш API Gateway віддає збережені відповіді протягом TTL без звернення до бекенду. Інші варіанти не зменшують кількість звернень до бекенду.

? Мобільний застосунок використовує Amazon Cognito для входу користувачів. Як дозволити виклики API лише автентифікованим користувачам з мінімальними зусиллями?
- Lambda authorizer, що вручну перевіряє паролі
+ Cognito User Pool authorizer в API Gateway
- API key для кожного користувача
- IAM-користувач для кожного покупця
= API Gateway вміє перевіряти токени Cognito User Pool без жодного коду. Lambda authorizer потрібен для нестандартних перевірок, API keys не автентифікують, а IAM-користувачі — не для тисяч клієнтів.

? Під час розпродажу бекенд обробки замовлень не встигає, і клієнти отримують помилки. Замовлення не можна втрачати, а відповідь «прийнято» має приходити швидко. Яка архітектура найкраща?
+ API Gateway інтегрується напряму з Amazon SQS; воркери (Lambda чи контейнери) обробляють чергу
- Збільшити таймаут API Gateway до 10 хвилин
- API Gateway викликає Lambda синхронно з provisioned concurrency
- Замінити API Gateway на Classic Load Balancer
= Черга розв'язує прийом і обробку: API миттєво кладе замовлення в SQS, а обробники беруть їх у своєму темпі. Жодне замовлення не губиться, піки згладжуються.

? Розробники хочуть завантажити Java-застосунок і отримати готове середовище з балансувальником, Auto Scaling і моніторингом, не налаштовуючи інфраструктуру вручну. Що обрати?
+ AWS Elastic Beanstalk
- AWS CloudFormation з ручними шаблонами
- Amazon EC2 з вручну налаштованою ASG
- AWS Batch
= Elastic Beanstalk — PaaS, що сам створює й обслуговує EC2, ASG, балансувальник і моніторинг під код. CloudFormation — інструмент IaC, але шаблони треба писати самому.

? Команда оновлює застосунок у Elastic Beanstalk і хоче миттєвого відкату без простою, навіть ціною повної копії середовища на час релізу. Яку стратегію обрати?
- All at once
- Rolling
+ Blue/green з перемиканням URL середовищ (swap URL)
- Rolling with additional batch
= Blue/green створює окреме нове середовище; після перевірки URL міняються місцями, а відкат — це повторна заміна URL. All at once має простій, rolling — повільний відкат.

? Щовечора потрібно виконати 10 000 обчислювальних задач тривалістю від 20 хвилин до 3 годин, з залежностями між деякими з них, якомога дешевше. Що обрати?
- AWS Lambda
+ AWS Batch з compute environment на Spot
- API Gateway WebSocket API
- AWS Amplify
= Batch керує чергами, залежностями й ресурсами для довгих пакетних задач і дозволяє використовувати Spot. Lambda обмежена 15 хвилинами.
:::
