> 🎬 **Історія Хмаринки.** RDS for MySQL добре служить Хмаринці, але зростання ставить нові питання. На розпродажах п'ять read replicas не встигають, і додавати шосту доводиться вручну. Перемикання Multi-AZ триває хвилину-дві — для магазину це сотні втрачених кошиків. Тестувальники щотижня чекають годину на копію бойової бази. А Олена вже думає про Німеччину і про вимогу «переживемо аварію цілого регіону з втратою не більше секунди даних». Усе це — сильні сторони **Amazon Aurora**.

> 🖼️ **Образ.** Звичайна база — кухар, який сам записує кожне замовлення в єдиний зошит на столі. **Aurora** — кухар, який лише диктує, а записує **розподілений архів**: шість писарів у трьох окремих будівлях одночасно заносять кожен рядок, і запис вважається збереженим, щойно встигли четверо. Помічники-кухарі (репліки) читають з того самого архіву — їм не треба копіювати зошит, тому вони завжди майже в курсі, а стати головним можуть за секунди.

## Чим Aurora відрізняється від RDS {#architecture}

**Amazon Aurora** — реляційна база, **сумісна з MySQL і PostgreSQL** (ті самі драйвери й запити), але з власною хмарною архітектурою. За даними AWS — до **5× швидша** за стандартний MySQL і до **3×** за PostgreSQL на тому самому залізі.

Головне — **розподілене сховище кластера** (cluster volume):

- дані зберігаються в **6 копіях у 3 AZ** (по дві в кожній);
- запис підтверджується, коли його зберегли **4 з 6** копій; читання — з **3 з 6**: система переживає втрату цілої AZ і ще однієї копії без втрати даних;
- сховище **росте автоматично** до **256 TiB** (з 2025 року; раніше 128 TiB) — ніякого виділення місця наперед;
- **самовідновлюється**: пошкоджені блоки автоматично відновлюються з інших копій;
- бекапи — **безперервні** в S3, без впливу на продуктивність.

## Endpoints: куди підключатися {#endpoints}

- **Cluster (writer) endpoint** — завжди на поточний **writer**: INSERT, UPDATE, DELETE. Після failover сам перемикається на новий writer.
- **Reader endpoint** — **балансує читання** між усіма репліками.
- **Custom endpoints** — власні групи реплік: наприклад, дві великі репліки для звітів бухгалтерії окремо від реплік для сайту.
- **Instance endpoints** — до конкретного інстансу (для діагностики).

Правило: застосунок **пише через writer endpoint**, **читає через reader** (або custom) endpoint.

## Висока доступність і масштабування {#ha}

- **Failover:** якщо writer падає, одна з реплік стає writer'ом — зазвичай **до ~30 секунд**. Порядок обирається **failover tiers** (пріоритети 0–15). Без реплік Aurora створить новий writer, але це довше.
- **Aurora Auto Scaling** — автоматично додає і прибирає репліки за навантаженням (CPU чи кількість з'єднань) — те, чого бракувало в RDS.
- Масштабування **запису** — вертикальне (більший клас writer'а) або **Aurora Serverless v2**; для горизонтального шардування запису PostgreSQL є **Aurora Limitless Database**.

## Aurora Serverless v2 {#serverless}

**Aurora Serverless v2** автоматично й миттєво змінює потужність бази в одиницях **ACU** (Aurora Capacity Unit; 1 ACU ≈ 2 GiB пам'яті плюс відповідні CPU і мережа):

- масштабується дрібними кроками за секунди, без переривання з'єднань;
- з кінця 2024 року може опускатися до **0 ACU**: база «засинає» (auto-pause), коли немає з'єднань, — платиш лише за сховище; пробудження — до ~15 секунд;
- serverless і звичайні (provisioned) інстанси можна **змішувати** в одному кластері (наприклад, provisioned writer і serverless-репліки для піків).

Для чого: **непередбачуване** або **переривчасте** навантаження, нові застосунки без історії навантаження, dev/test, бази багатьох клієнтів SaaS.

## Aurora Global Database {#global}

**Global Database** — один основний регіон і до **10 вторинних** (з травня 2025; раніше 5):

- реплікація **на рівні сховища**, типова затримка **менше 1 секунди**;
- у вторинних регіонах — репліки для **швидкого локального читання** (до 16 у кожному);
- **керований failover/switchover**: вторинний регіон стає основним зазвичай **менш ніж за хвилину** (RTO), втрата даних — близько секунди (RPO);
- **write forwarding** — застосунок у вторинному регіоні може надсилати записи, які пересилаються в основний.

Не плутай з **cross-region read replica** Aurora MySQL (логічна реплікація через binlog): вона повільніша (секунди–хвилини) і менш керована. Для мінімальних RPO/RTO між регіонами — **Global Database**.

## Особливі можливості {#features}

- **Backtrack** — «перемотати» кластер назад у часі (до **72 годин**) **без** відновлення з бекапу — хвилини замість години. **Лише Aurora MySQL.**
- **Cloning** — миттєва копія кластера за принципом copy-on-write: нові дані пишуться окремо, спільні — не дублюються. Тестове середовище на свіжих бойових даних за хвилини і майже без додаткових витрат на сховище.
- **Aurora I/O-Optimized** — конфігурація без плати за операції вводу-виводу (дорожчі інстанси й сховище): вигідно, коли I/O становить понад ~25% витрат на Aurora.
- **Babelfish for Aurora PostgreSQL** — розуміє **T-SQL** і протокол SQL Server: застосунки з Microsoft SQL Server переходять на Aurora PostgreSQL майже без змін коду.
- **Aurora Machine Learning** — ML-прогнози прямо в SQL (виклики SageMaker AI, Comprehend, Bedrock) без знань ML.
- **Zero-ETL integration з Amazon Redshift** — дані Aurora майже в реальному часі з'являються в Redshift для аналітики без ETL-конвеєрів.
- **Database Activity Streams** — потік дій з базою для аудиту безпеки.
- **Aurora DSQL** (з 2025) — розподілена serverless SQL-база, сумісна з PostgreSQL, **active-active у кількох регіонах** з сильною консистентністю.

## Aurora для Хмаринки {#design}

- **Aurora MySQL**, writer + 2 репліки в трьох AZ; **reader endpoint** — для каталогу, **custom endpoint** «reports» на двох великих репліках — для бухгалтерії.
- **Aurora Auto Scaling**: від 2 до 8 реплік за CPU — розпродажі без ручних дій.
- **RDS Proxy** перед кластером для функцій Lambda.
- **Global Database** з вторинним регіоном eu-west-1 — коли бізнес вирішить, що регіональна аварія критична.
- **Cloning** — щотижнева копія для тестувальників; **Backtrack** на 24 години — від «випадкового DELETE без WHERE».
- **Serverless v2 з мінімумом 0 ACU** — для dev і тестових баз, що простоюють уночі.
- **Zero-ETL** в Redshift — для аналітики ([розділ 39](#ch/analytics)).

#### 💡 Запам'ятай

- Aurora — сумісна з **MySQL і PostgreSQL**, власне **сховище: 6 копій у 3 AZ**, росте до **256 TiB**, самовідновлюється.
- До **15 Aurora Replicas** на спільному сховищі (мілісекунди затримки), **Aurora Auto Scaling**, failover **до ~30 с**.
- Endpoints: **writer**, **reader**, **custom** (групи реплік), instance.
- **Serverless v2** — масштаб в ACU, до **0 ACU** з auto-pause, для непередбачуваного й переривчастого навантаження.
- **Global Database** — до **10** вторинних регіонів, реплікація сховища **&lt; 1 с**, RTO **&lt; 1 хв**, write forwarding.
- **Backtrack** (лише MySQL, до 72 год), **Cloning** (copy-on-write), **I/O-Optimized** (без плати за I/O), **Babelfish** (T-SQL), **Aurora ML**, **zero-ETL з Redshift**, **DSQL** (active-active).

#### 🎯 Як питають на іспиті

- Максимальна доступність і продуктивність реляційної бази з мінімальним адмініструванням → **Amazon Aurora**
- Репліки мають додаватися автоматично під час піків читання → **Aurora Auto Scaling**
- Розділити аналітичні звіти і вебтрафік на різні групи реплік → **Aurora custom endpoints**
- Найшвидша реплікація між регіонами, RPO ~1 с, RTO &lt; 1 хв → **Aurora Global Database**
- Швидке локальне читання для користувачів у кількох регіонах → **Aurora Global Database (secondary regions)**
- Непередбачувані сплески або база, що простоює вночі → **Aurora Serverless v2**
- Швидко повернути кластер на стан годину тому без відновлення з бекапу → **Aurora Backtrack (лише MySQL)**
- Швидко створити копію бойової бази для тестів → **Aurora Cloning**
- Великі витрати на операції вводу-виводу → **Aurora I/O-Optimized**
- Міграція з SQL Server без переписування T-SQL → **Babelfish for Aurora PostgreSQL**
- Аналітика в Redshift на даних Aurora без ETL → **zero-ETL integration**
- ML-прогнози звичайними SQL-запитами без знань ML → **Aurora Machine Learning**

#### ⚠️ Пастки

- **Backtrack — лише Aurora MySQL**; для PostgreSQL — PITR або клон.
- Global Database (реплікація сховища) ≠ cross-region read replica (логічна, повільніша).
- Застосунок має **писати** через writer endpoint і **читати** через reader — інакше репліки не працюють на тебе.
- Serverless v2 з мінімумом 0 ACU прокидається до ~15 секунд — для API з жорсткими вимогами затримки мінімум варто тримати вище нуля.
