> 🎬 **Історія Хмаринки.** Тарас ледь не зробив класичну помилку: щоб сайт міг читати фото з S3, він збирався вписати ключі доступу прямо в конфігурацію сервера. Потім з'явилися ще три задачі. Бухгалтерська фірма-партнер хоче щомісяця забирати звіти з акаунта Хмаринки. Співробітників стає більше, і всі хочуть входити своїм робочим акаунтом Microsoft, а не окремим паролем AWS. А мобільний застосунок має пускати **покупців**, яких тисячі. Усі чотири задачі розв'язує одна ідея: **тимчасові права замість постійних ключів**.

> 🖼️ **Образ.** **Роль** — це форма з бейджем, яку видають на рецепції на один день. Одягнув форму «Склад» — проходиш на склад, але поки ти в ній, доступу до бухгалтерії немає. Форма діє кілька годин, потім сама «розчиняється» — вкрасти її безглуздо. Хто має право отримати форму, записано в журналі рецепції (**trust policy**), а куди вона пускає — на бейджі (**permissions policy**). А видає форми вахтер **STS**.

## IAM-роль: права без постійних ключів {#role}

**IAM role** — особа в акаунті з набором прав, але **без пароля і без постійних ключів**. Роль не належить комусь конкретному: її **беруть на себе** (assume) ті, кому це дозволено, і отримують **тимчасові облікові дані**.

Кожна роль має дві політики:

1. **Trust policy (політика довіри)** — **хто** може взяти роль: сервіс AWS (EC2, Lambda), користувач чи роль іншого акаунта, федеративний користувач.
2. **Permissions policy (політика дозволів)** — **що** можна робити в ролі.

Приклад trust policy, що дозволяє серверам EC2 брати роль:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "ec2.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}
```

### STS — вахтер, що видає тимчасові ключі

**AWS STS** (Security Token Service) видає тимчасові облікові дані: **Access Key ID**, **Secret Access Key** і **Session Token** з часом дії — від 15 хвилин до кількох годин (для ролі типово 1 година, максимум — до 12 годин за налаштуванням ролі). Коли строк мине, ключі стають непотрібними, а SDK сам отримає нові.

Головні виклики STS:

| Виклик | Хто використовує | Приклад |
|---|---|---|
| `AssumeRole` | Користувачі й ролі (свого чи іншого акаунта), сервіси | Перемкнутися в роль адміністратора прод-акаунта |
| `AssumeRoleWithSAML` | Співробітники через корпоративний каталог (SAML 2.0) | Вхід через Active Directory / Entra ID |
| `AssumeRoleWithWebIdentity` | Застосунки з токеном OIDC (Google, Facebook, Kubernetes) | Pod у EKS отримує права AWS; для мобільних застосунків AWS радить Cognito |
| `GetSessionToken` | IAM user, що підтверджує MFA | Тимчасові ключі «з MFA» для CLI |

## Ролі для сервісів AWS {#service-roles}

Найчастіше роль потрібна **програмі**, що працює в AWS:

- **EC2 — instance profile.** Роль «прикріплюють» до сервера через instance profile. Застосунок на сервері бере тимчасові ключі з **сервісу метаданих інстансу** (IMDS) — SDK робить це автоматично. Ключі ротуються самі. Використовуй **IMDSv2** (з токенами сесії) — він захищає від атак, коли зловмисник змушує застосунок звернутися до адреси метаданих.
- **Lambda — execution role.** Права функції: читати чергу, писати в базу, писати логи.
- **ECS — task role.** Права конкретного контейнера (окремо від **task execution role**, якою ECS тягне образ і пише логи).
- **Service-linked roles** — ролі, які сервіси AWS створюють для себе самі (наприклад, для Auto Scaling). Їх не редагують.

Приклад з Хмаринки: сайт на EC2 має роль `web-server-role` з дозволом `s3:GetObject` на `khmarynka-photos/*`. Жодних ключів у конфігурації — нічого красти.

## Доступ між акаунтами {#cross-account}

Партнерська бухгалтерська фірма (акаунт `444455556666`) має забирати звіти з bucket Хмаринки (`111122223333`). Два способи:

**Спосіб 1: роль в акаунті Хмаринки.** Створюємо роль `partner-reports-reader`, у trust policy довіряємо акаунту партнера, у permissions policy — читання звітів. Партнер у своєму акаунті дозволяє своїм людям `sts:AssumeRole` на ARN цієї ролі. Потрібні дозволи **з обох боків**.

**Спосіб 2: resource-based політика** на самому bucket — дозвіл principal-у з акаунта партнера. Партнер звертається до bucket зі своїми правами, не беручи роль.

| | Роль (AssumeRole) | Політика ресурсу |
|---|---|---|
| Для яких сервісів | Будь-яких | Лише тих, що мають resource-based політики: S3, SQS, SNS, KMS, Lambda, Secrets Manager, ECR… |
| Права того, хто звертається | Тимчасово замінюються правами ролі | Лишаються його власними (зручно, коли треба одночасно працювати з ресурсами в обох акаунтах) |

### Проблема «заплутаного заступника» і ExternalId

Уяви SaaS-сервіс аналітики, що працює з акаунтами сотень клієнтів через ролі. Зловмисник, теж клієнт цього сервісу, вказує в налаштуваннях **ARN ролі Хмаринки** — і сервіс «з добрих намірів» отримує доступ до чужих даних. Це **confused deputy**. Захист — **ExternalId**: секретний ідентифікатор, який сервіс видає кожному клієнту і який перевіряється в trust policy ролі:

```json
"Condition": { "StringEquals": { "sts:ExternalId": "khmarynka-7f3a91" } }
```

Для сервісів AWS, що звертаються до твоїх ресурсів (наприклад, SNS пише в чергу), та сама проблема розв'язується умовами `aws:SourceArn` і `aws:SourceAccount`.

## Межі прав (permission boundaries) {#boundary}

Тарас хоче, щоб розробники самі створювали ролі для своїх функцій Lambda — без нього. Але якщо розробник може створювати ролі, він може створити роль з `AdministratorAccess` і взяти її — ескалація привілеїв.

**Permission boundary** — політика-«стеля», прикріплена до користувача чи ролі: **ефективні права = перетин** звичайної політики і межі. Межа сама нічого не дозволяє — лише обмежує.

Рецепт делегування: розробникам дозволено `iam:CreateRole` **лише за умови**, що до нової ролі прикріплено визначену permission boundary (умова `iam:PermissionsBoundary`). Тепер будь-яка роль, створена розробником, не перевищить стелі — навіть якщо він прикріпить їй `AdministratorAccess`.

## ABAC: доступ за тегами {#abac}

Класичний підхід — **RBAC** (за ролями): для кожного проєкту — своя політика. Коли проєктів сотні, політик стає забагато. **ABAC** (attribute-based access control) — одна політика на всіх, що порівнює **теги** особи і ресурсу: «дозволити керувати серверами, якщо тег `Team` сервера збігається з тегом `Team` користувача».

```json
"Condition": { "StringEquals": { "aws:ResourceTag/Team": "${aws:PrincipalTag/Team}" } }
```

Новий проєкт — нові теги, а політика та сама. На іспиті: «масштабоване керування доступом для багатьох команд без постійного редагування політик» → ABAC.

## Співробітники: єдиний вхід і федерація {#workforce}

### IAM Identity Center

**AWS IAM Identity Center** (колишня назва — AWS Single Sign-On) — рекомендований спосіб впускати **співробітників** в AWS:

- **один вхід** (портал доступу) у **всі акаунти** організації і в бізнес-застосунки (Salesforce, Microsoft 365 тощо);
- **джерело користувачів** — на вибір: вбудований каталог Identity Center, **Active Directory** (через AWS Managed Microsoft AD або AD Connector) або **зовнішній провайдер** (Microsoft Entra ID, Okta, Google Workspace) через **SAML 2.0**, з автоматичною синхронізацією користувачів і груп через **SCIM**;
- **permission sets** — шаблони прав («Developer», «ReadOnly», «Billing»), які Identity Center перетворює на ролі в потрібних акаунтах;
- у консоль і CLI люди отримують **тимчасові** облікові дані — жодних постійних ключів.

### SAML-федерація напряму з IAM

Старіший спосіб: у кожному акаунті створюють **SAML identity provider** і ролі; корпоративний каталог (наприклад, AD FS) видає SAML-підтвердження, а STS міняє його на тимчасові ключі (`AssumeRoleWithSAML`). Працює, але для багатьох акаунтів Identity Center значно простіший.

### AWS Directory Service: Active Directory в AWS

Багато компаній живуть на **Microsoft Active Directory** (AD). AWS пропонує три варіанти:

| Варіант | Що це | Коли обирати |
|---|---|---|
| **AWS Managed Microsoft AD** | Справжній Microsoft AD, керований AWS, у двох зонах | Потрібен повноцінний AD в AWS; **довіра (trust)** з локальним AD; застосунки, що потребують AD (FSx for Windows, RDS for SQL Server з Windows-автентифікацією, WorkSpaces) |
| **AD Connector** | Проксі, що пересилає запити до **твого** локального AD; нічого не зберігає в AWS | Використати наявний on-prem AD без копіювання даних у хмару |
| **Simple AD** | Недорогий AD-сумісний каталог (на базі Samba) | Малі середовища з базовими функціями, без довіри з іншими AD |

### IAM Roles Anywhere

Сервер у **власному** дата-центрі Хмаринки (складська програма) має писати в S3. Замість постійних ключів — **IAM Roles Anywhere**: сервер доводить свою особу **сертифікатом X.509** (від корпоративного центру сертифікації чи AWS Private CA) і отримує тимчасові облікові дані ролі.

## Клієнти застосунку: Amazon Cognito {#cognito}

Співробітників — десятки, а покупців мобільного застосунку — тисячі. Для **клієнтів** застосунків є **Amazon Cognito**. У нього дві окремі частини, і їх постійно плутають:

| | **User pool** — «хто ти» | **Identity pool** — «ключі до AWS» |
|---|---|---|
| Що робить | Реєстрація і вхід користувачів: email і пароль, MFA, відновлення пароля, вхід через Google/Facebook/Apple або корпоративний SAML/OIDC | Міняє токен входу (з user pool, соцмережі, SAML) на **тимчасові AWS-credentials** через STS |
| Що видає | **JWT-токени** (ID, access, refresh) | Тимчасові ключі ролі IAM |
| З чим інтегрується | **Application Load Balancer** і **API Gateway** перевіряють токени | Прямі виклики S3, DynamoDB тощо з мобільного застосунку |
| Особливості | Готові сторінки входу, тригери Lambda (наприклад, перевірка при реєстрації) | Гостьовий (неавтентифікований) доступ, різні ролі для різних груп |

1. Увійди як адміністратор (не root) → **IAM** → **Roles** → **Create role**.

3. Дозволи: `ReadOnlyAccess`. Назва ролі: `auditor-readonly`. Create.
4. Відкрий роль і скопіюй посилання **Link to switch roles in console** — відкрий його. Ти в консолі від імені ролі (назва ролі видно вгорі праворуч). Спробуй створити bucket S3 — отримаєш відмову: права ролі лише на читання, а свої права адміністратора ти тимчасово «відклав».
5. Натисни **Switch back**, відкрий **CloudShell** і виконай (підстав свій номер акаунта):
```bash
aws sts get-caller-identity
aws iam get-role --role-name auditor-readonly --query "Role.AssumeRolePolicyDocument"
```
Друга команда покаже trust policy ролі.
6. Подивись у **CloudTrail → Event history** події `SwitchRole` і `AssumeRole` — видно, хто і коли брав роль.
**Прибери за собою:** IAM → Roles → видали `auditor-readonly`.

#### 💡 Запам'ятай

- **Роль** = trust policy (хто може взяти) + permissions policy (що можна). Облікові дані — **тимчасові**, від STS.
- **EC2 → instance profile**, **Lambda → execution role**, **ECS → task role**. Ключі на серверах і в коді — ніколи.
- Взявши роль, principal працює лише з її правами; resource-based політика дозволяє зберегти власні.
- Крос-акаунтний доступ: роль з trust policy для іншого акаунта **або** resource-based політика; дозволи потрібні з **обох** боків.
- **ExternalId** — захист від confused deputy для сторонніх сервісів.
- **Permission boundary** — стеля прав; делегування створення ролей без ескалації.
- **ABAC** — доступ за тегами, одна політика на багато команд.
- **Identity Center** — співробітники, багато акаунтів, SSO, permission sets, зовнішній IdP через SAML + SCIM.
- **Cognito User Pool** — вхід клієнтів (JWT); **Identity Pool** — тимчасові AWS-ключі клієнтам.
- **Managed Microsoft AD** — справжній AD з trust; **AD Connector** — проксі до on-prem AD; **Simple AD** — дешевий базовий.

#### 🎯 Як питають на іспиті

- Застосунок на EC2 має читати S3 без збереження ключів → **IAM role через instance profile**
- Надати іншому акаунту доступ до ресурсів → **IAM role з trust policy для того акаунта (sts:AssumeRole)** або **resource-based policy**
- Сторонній SaaS-вендор отримує доступ через роль, треба захист від confused deputy → **умова sts:ExternalId у trust policy**
- Розробники мають створювати ролі, але не ширші за певні права → **permission boundary**
- Сотні команд, доступ до ресурсів своєї команди без окремої політики на кожну → **ABAC (теги + умови)**
- Єдиний вхід співробітників у багато акаунтів через Okta / Entra ID → **IAM Identity Center + зовнішній IdP (SAML, SCIM)**
- Реєстрація і вхід користувачів мобільного застосунку, вхід через соцмережі → **Cognito User Pool**
- Користувачі застосунку мають напряму вантажити файли в S3, кожен у свою папку → **Cognito Identity Pool + політика з cognito-identity sub**
- Використати наявний on-prem Active Directory без копіювання в AWS → **AD Connector**
- Повноцінний AD в AWS з довірою до локального AD → **AWS Managed Microsoft AD**
- Локальні сервери мають отримувати тимчасові AWS-ключі без збережених секретів → **IAM Roles Anywhere**
- ALB має пускати до застосунку лише автентифікованих користувачів → **ALB authentication з Cognito User Pool**

#### ⚠️ Пастки

- Cognito **User Pool** не видає AWS-ключів — для прямого доступу до S3/DynamoDB потрібен **Identity Pool**.
- **Identity Center** — для співробітників і акаунтів AWS; **Cognito** — для клієнтів застосунку. Не навпаки.
- Permission boundary і SCP **не дають** прав — лише обмежують.
- Для крос-акаунтного доступу мало дозволу лише на одному боці.
- Instance profile ≠ access keys на сервері: навіть «зашифровані» ключі на EC2 — гірше за роль.

## ✅ Перевір себе

:::quiz
? Функція Lambda має записувати дані в таблицю DynamoDB. Як правильно надати їй права?
- Зберегти access keys IAM-користувача в змінних середовища функції
+ Надати execution role функції політику з дозволом на запис у таблицю
- Зробити таблицю DynamoDB публічною
- Прикріпити до функції Security Group
= Execution role — роль, яку Lambda бере під час виконання; права задаються її політикою, облікові дані тимчасові й керуються AWS. Ключі в змінних середовища — довгострокові секрети, яких треба уникати.

? Аудиторська компанія (окремий акаунт AWS) має регулярно читати журнали з bucket компанії. Потрібне рішення без передачі довгострокових ключів. Що обрати?
- Створити IAM-користувача для аудиторів і передати їм ключі
+ Створити в акаунті компанії роль з trust policy для акаунта аудиторів і правами на читання bucket
- Зробити bucket публічним на час аудиту
- Скопіювати журнали в акаунт аудиторів вручну щомісяця
= Крос-акаунтна роль дає тимчасові облікові дані через STS AssumeRole. Акаунт аудиторів також має дозволити своїм людям sts:AssumeRole на ARN ролі. Жодних постійних ключів і публічного доступу.

? SaaS-компанія працює з акаунтами багатьох клієнтів через IAM-ролі. Як захистити клієнтів від атаки confused deputy?
- Використовувати лише resource-based політики
+ Вимагати в trust policy ролі умову sts:ExternalId з унікальним значенням для кожного клієнта
- Дозволити AssumeRole лише з MFA
- Обмежити тривалість сесії 15 хвилинами
= ExternalId — секретний ідентифікатор, який вендор видає кожному клієнту. Навіть знаючи ARN чужої ролі, інший клієнт не зможе змусити вендора взяти її без правильного ExternalId.

? Керівник розробки хоче, щоб розробники самі створювали IAM-ролі для своїх застосунків, але щоб ці ролі ніколи не мали прав ширших за визначений набір. Що використати?
+ Permission boundary, обов'язкову для ролей, які створюють розробники
- Service control policy на рівні ролі
- Окрему IAM-групу для кожної ролі
- Inline-політику з Deny на всі дії IAM
= Дозвіл iam:CreateRole з умовою, що до ролі прикріплена певна permission boundary, дає делегувати створення ролей без ризику ескалації: ефективні права ролі не перевищать межу.

? Мобільний застосунок має дозволяти користувачам входити через Google і потім напряму завантажувати фото в S3, кожен — лише у свій префікс. Які компоненти потрібні? (Оберіть 2)
+ Amazon Cognito User Pool для входу через Google
+ Amazon Cognito Identity Pool для видачі тимчасових AWS-credentials з обмеженням префіксу
- IAM Identity Center для кожного покупця
- IAM-користувач для кожного покупця
- AWS Managed Microsoft AD
= User Pool автентифікує користувачів (зокрема через Google), Identity Pool міняє токен на тимчасові ключі ролі; політика з ${cognito-identity.amazonaws.com:sub} обмежує префікс. Identity Center і IAM-користувачі — не для тисяч клієнтів.

? Компанія хоче, щоб співробітники входили в 30 акаунтів AWS через наявний Okta, з правами за групами і без IAM-користувачів у кожному акаунті. Що обрати з найменшими зусиллями?
- Cognito User Pool з федерацією Okta
+ IAM Identity Center з Okta як зовнішнім провайдером і permission sets
- SAML-провайдер і ролі вручну в кожному з 30 акаунтів
- AD Connector до Okta
= Identity Center централізовано керує доступом співробітників до багатьох акаунтів: Okta як джерело (SAML + SCIM), permission sets перетворюються на ролі в акаунтах. Ручна SAML-федерація в кожному акаунті — багато роботи.

? Компанія має локальний Active Directory і хоче, щоб співробітники входили в AWS зі своїми обліковими даними AD, не копіюючи каталог у хмару. Що обрати?
+ AD Connector
- Simple AD
- AWS Managed Microsoft AD з окремою копією всіх користувачів
- Amazon Cognito Identity Pool
= AD Connector — проксі, що перенаправляє запити автентифікації до локального AD і нічого не зберігає в AWS. Simple AD — окремий незалежний каталог, Managed AD — повноцінний AD у хмарі.
:::
